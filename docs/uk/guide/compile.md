# Компіляція

Якщо ви нічого більше не робите, програми typelisp виконуються в інтерпретаторі. Крім того, є два
способи компіляції в нативний код і один спосіб збереження середовища. Подробиці специфікації наведено в
[Довіднику із синтаксису, розділ 10](../reference/syntax.md#10-компіляція).

| Спосіб | Як | Результат |
|---|---|---|
| JIT-компіляція | `(compile name)` | Функція в поточному сеансі замінюється нативним кодом |
| AOT-компіляція | `typl -c src.typl` або `(compile-file "src.typl" "out")` | Самодостатній виконуваний файл |
| Дамп | `(dump "file.typld")` | Зберігає визначення; `typl --image` знову запускається з того самого середовища |

## 1. Підготовка

Компіляція використовує LLVM 22. Якщо ви зібрали `typl` за [README.md](../../../README.md), додаткова
підготовка не потрібна.

Виконувані файли, створені AOT-компіляцією, зв'язуються зі статичною бібліотекою `libtypelisp_front.a`.
Релізна збірка `typl` (зокрема встановлена через `cargo install`) несе цю бібліотеку в собі, тож
підготовка не потрібна. Під час першої компіляції вона записує бібліотеку в
`~/.typelisp/lib/<build ID>/` (або в `$TYPELISP_HOME/lib/<build ID>/`, якщо задано змінну середовища
`TYPELISP_HOME`) і відтоді використовує цю копію. `typl --remove-lib` видаляє її (з `--others` — ті,
що записані іншими версіями `typl`; з `--all` — усі). Налагоджувальна збірка `typl` використовує
бібліотеку з `target/debug/` репозиторію, у якому її зібрано. Щоб використати бібліотеку, розташовану
деінде, вкажіть її каталог через `--lib-dir` під час запуску `typl` (розділ 3.2).
У macOS для компонування використовуються Xcode Command Line Tools.

## 2. JIT-компіляція

Це перетворює вже визначену функцію на нативний код на місці.

```lisp
(defun fib ((n int)) int
  (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2)))))

(compile fib)
(fib 30)           ; from here on, calls run the compiled code
```

- `name` не обчислюється. Пишіть назву функції як є (не як рядок). Для методу пишіть її з назвою типу,
  як-от `(compile point::norm)`.
- Функції, які вона викликає, компілюються разом із нею.
- **Узагальнені функції скомпілювати не можна.** Копія для кожного типу створюється в кожному місці
  використання. Натомість компілюйте функцію, що викликає її з конкретними типами.
- `trace`, `step`, `disassemble`, `compile`, `compile-file` і `dump` — це операції інтерпретатора, тож
  функцію, яка їх викликає, скомпілювати не можна. Спроба скомпілювати її дає помилку з поясненням
  причини.

Щоб подивитися на результат компіляції, використовуйте `disassemble`.

```lisp
(disassemble fib)          ; the host machine code
(disassemble fib true)     ; LLVM IR
```

## 3. Збирання виконуваного файлу AOT-компіляцією

### 3.1 Написання програми

Як точку входу визначте **функцію `main` без аргументів**.

```lisp
(use std::env::command-line-args)
;; hello.typl
(defun fib ((n int)) int
  (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2)))))

(defun main () ()
  (println "args: ~a" (command-line-args))
  (println "fib(25) = ~a" (fib 25)))

(main)
```

`(main)` наприкінці файлу потрібен, щоб `main` викликалася, коли ви запускаєте `typl hello.typl`.
`compile-file` пропускає цей завершальний `(main)`, тож той самий файл працює і в інтерпретаторі, і з
AOT-компіляцією.

### 3.2 Компіляція

З командного рядка використовуйте `typl -c` (`typl --compile` — те саме).

```sh
$ typl -c hello.typl            # makes hello
$ typl -c hello.typl -o fib     # names the executable fib
$ ./hello a b
args: #(./hello a b)
fib(25) = 75025
```

Без `-o` виконуваний файл називається за вихідним файлом без `.typl` і розміщується в тому самому каталозі,
що й вихідний файл. Якщо ім'я вихідного файлу не закінчується на `.typl`, `-o` обов'язковий. З `-c`
(`--compile`) не можна вказувати `--image` і `--feature`.

З `--release` `typl` робить **релізне збирання**, яке вилучає `eprint`/`eprintln` (вивід у стандартний потік помилок для налагодження; [Друк](../reference/functions/printing.md)) разом з їхніми аргументами. Вилучене все одно проходить перевірку типів, тож помилка типів у ньому призводить до провалу компіляції. `--release` — опція `typl` загалом: вона діє однаково не лише для `-c`, а й під час запуску файлу, у REPL і для `typl test`. `compile-file`, викликаний усередині `typl`, запущеного з `--release`, теж робить релізне збирання, а з коду, що виконується через `eval` усередині зібраного так виконуваного файлу, `eprint`/`eprintln` теж вилучаються.

```sh
$ typl --release -c hello.typl
$ typl -c hello.typl --release     # те саме, якщо написати після -c
```

`-O0`, `-O1`, `-O2` і `-O3` задають **рівень оптимізації**. Типово — `-O0`, без оптимізації. Починаючи з `-O1`, компілятор спершу виконує прості оптимізації — наприклад, замінює змінну, зв'язану лише з літералом, її значенням або заздалегідь обчислює цілочислову арифметику над константами, — а решту залишає оптимізації LLVM на рівні з тією самою назвою. На будь-якому рівні результати обчислень однакові. Як і `--release`, це опція `typl` загалом: крім виконуваного файлу, який створює `-c`, вона діє на код, що компілюється під час запуску файлу, у REPL і в `typl test`, а також на викликаний там `compile-file`. Код, який виконує інтерпретатор, не оптимізується.

```sh
$ typl -O2 -c hello.typl
$ typl -c hello.typl -O2     # те саме, якщо написати після -c
```

Те саме можна зробити, викликавши `compile-file` з REPL або з програми.

```sh
$ typl
typl> (compile-file "hello.typl" "hello")
typl> :quit
$ ./hello a b
args: #(./hello a b)
fib(25) = 75025
```

Якщо ви збираєте неодноразово, можна покласти цей один рядок у файл і запускати його через
`typl build.typl`.

```lisp
;; build.typl
(compile-file "hello.typl" "hello")
```

Імена файлів розв'язуються від **поточного каталогу, у якому запущено `typl`**, а не від розташування
`build.typl`.

Щоб зв'язати `libtypelisp_front.a`, розташовану не там, де її шукає `typl`, вкажіть її каталог через
`--lib-dir`. Це діє і для `typl -c`, і для `compile-file`.

```sh
$ typl --lib-dir ~/lib/typelisp -c hello.typl
$ typl --lib-dir ~/lib/typelisp build.typl
```

Якщо в указаному каталозі немає `libtypelisp_front.a`, `typl` зупиняється з помилкою. Файл працює лише з
тим `typl`, що зібраний разом із ним. Після перебудови `typl` скопіюйте його знову.

### 3.3 Що може містити AOT-скомпільований файл

- Верхній рівень вхідного файлу може містити лише визначення (`defun` `defvar`
  `defparameter` `defconstant` `defmacro` `defsignature` `defstruct` `defenum` `deftype` `deftrait`
  `impl` `defffi`, `(unsafe (def-c-struct ...))`) та `use` `module`. Вирази верхнього рівня на кшталт
  `(println ...)` не дозволені, за винятком завершального `(main)`. Робіть роботу всередині `main`.
- Без `main` без аргументів компіляція завершується помилкою.
- Файли підключених через `use` модулів теж компілюються й об'єднуються в один виконуваний файл.
- Бібліотеки, названі через `:library` у `defffi`, зв'язуються автоматично ([FFI для C](ffi.md)).
- Кожну функцію стандартної бібліотеки можна використовувати з AOT-компіляцією. `eval` теж можна
  використовувати, але тоді перевіряльник типів та інтерпретатор потрапляють у виконуваний файл, що
  робить його більшим і повільнішим у запуску. Програми, які не викликають `eval`, їх не містять.

### 3.4 Як поводиться виконуваний файл

- `(command-line-args)` повертає `Vector<string>` тієї самої форми, чи запущено як
  `typl hello.typl a b`, чи як `./hello a b`. Перший елемент — назва програми.
- Код завершення задається через `(exit n)`. Якщо `main` повертається нормально, він дорівнює 0.
- У разі `panic` програма друкує повідомлення й завершується з ненульовим кодом.

### 3.5 Ресурси виконуваного файлу

У `typl -c` є опції, що задають, які ресурси виконуваний файл може використовувати під час роботи.

```sh
$ typl --heap-cells 100000 -c hello.typl    # закріпити арену cons на 100000 комірок
$ typl -c hello.typl --max-memory 64M       # виділяти не більше 64 МіБ
$ typl -c hello.typl --no-cons              # не використовувати cons-комірки
```

- `--heap-cells N` закріплює місткість арени cons-комірок на `N` комірках. Арена далі не росте: якщо збирання сміття не може звільнити жодної комірки, програма зупиняється з помилкою виконання. Без цієї опції арена починається з 65536 комірок і росте за потреби.
- `--max-memory SIZE` обмежує загальний обсяг пам'яті, який виділяє виконуваний файл. Враховується все: арена cons, рядки, такі значення, як вектори й геш-таблиці, і пам'ять самого середовища виконання. `SIZE` — кількість байтів, після якої може стояти `K`, `M` або `G` (у 1024, 1024² і 1024³ раза). Про виділення, яке перевищило б межу, повідомляється, і програма завершується з кодом виходу 1. Це завершення не можна перехопити через `catch`. Без цієї опції межі немає.
- `--no-cons` створює виконуваний файл, який не використовує cons-комірок. У нього немає арени cons, тож програма, що робить щось, для чого потрібні cons-комірки, — **помилка компіляції**, яка показує цю операцію й ланцюжок функцій від `main`, що до неї веде. Cons-комірки потрібні, щоб побудувати список `Sexpr` (зокрема квотований список і список, побудований квазіквотуванням) або аргумент `&rest`, а також для `read`, `eval` і `macroexpand`. Операції над числами, рядками, векторами, геш-таблицями, структурами, каналами тощо, а також `print`/`println`/`format` їх не використовують. Не можна вказувати разом із `--heap-cells`; пишеться після `-c`.

`--max-memory` пишеться після `-c`. `--heap-cells` можна писати до або після `-c`, і тоді це місткість арени cons виконуваного файлу. Арена cons входить у межу пам'яті, тож за межі, у яку арена не вміщується, програма зупиняється, не почавшись.

### 3.6 Компіляція у WebAssembly

З `--target wasm32-wasip1` команда `typl -c` створює замість виконуваного файлу модуль WebAssembly (команду WASI preview 1). Без `-o` він має назву вихідного файлу, з `.wasm` замість `.typl`.

```sh
$ typl -c hello.typl --target wasm32-wasip1      # створює hello.wasm
$ wasmtime hello.wasm a b                        # запуск у середовищі з підтримкою WASI
args: #(hello.wasm a b)
fib(25) = 75025
```

- `typl`, встановлений через `install.sh`, можна використовувати як є. Для встановлення через `cargo install` потрібна підготовка (вона ж підходить для розділу 3.7). Спершу виконайте `rustup target add wasm32-wasip1 wasm32-unknown-unknown` через rustup. Потім встановіть його з `--features wasm` (`cargo install --locked --path . --features wasm`).
  У `typl`, встановленого без цього, немає середовища виконання WebAssembly, і `--target` дає помилку. Для налагоджувальної збірки `typl` у репозиторії натомість виконайте `scripts/build-wasm-runtime.sh` у репозиторії.
- Компонування використовує компонувальник тулчейна rustup (`rust-lld`), тож rustup потрібен і під час компіляції.
- Модуль поводиться як виконуваний файл: стандартний вивід, стандартний потік помилок і код виходу, `(command-line-args)`,
  читання й запис файлів, `throw`/`catch`/`panic`, задачі, канали та `sleep`, а також `eval` працюють.
  Задачі виконуються по черзі в одному потоці. Читати й писати файли можна лише в каталогах,
  які середовище відкриває модулю (у wasmtime їх задають через `--dir`).
- Програма, що використовує те, чого немає у WebAssembly, — це **помилка компіляції**. Помилка показує, що використано,
  і ланцюжок функцій від `main`, який до цього веде. Недоступні: сокети (TCP, UDP, Unix-сокети,
  TLS, розв’язання імен), потоки ОС (`Thread`), функції C (`defffi`), `get-internal-run-time`, `machine-instance`, `software-version`, `file-author`
  і `ed`.
- У WASI немає способу дізнатися часовий пояс, тож місцевий час невідомий. `decode-universal-time` і `encode-universal-time` без `zone`, а також `get-decoded-time` спричиняють panic під час виконання. Із заданим `zone` вони працюють.
- `--heap-cells`, `--max-memory`, `--no-cons`, `-O<N>` і `--release` діють так само, як для виконуваного файлу.

### 3.7 Запуск у браузері або в Node.js

З `--target wasm32-unknown-unknown` команда `typl -c` створює модуль WebAssembly, який завантажується й запускається з JavaScript. Поруч із модулем (`hello.wasm`), у тій самій теці, з’являється JavaScript, що його завантажує й запускає (`hello.mjs`). Підготовка та сама, що й у розділі 3.6.

```sh
$ typl -c hello.typl --target wasm32-unknown-unknown   # створює hello.wasm і hello.mjs
$ node hello.mjs                                       # запуск у Node.js
args: #()
fib(25) = 75025
```

З іншого JavaScript викличте `run` із `hello.mjs`. `write` отримує вивід як текст (`fd` дорівнює 1 для стандартного виводу і 2 для стандартного потоку помилок). Значення `run` — код виходу.

```js
import { run } from './hello.mjs';
const code = await run({ write: (fd, text) => { /* наприклад, показати на сторінці */ } });
```

- Без `write` Node.js пише у стандартний вивід і стандартний потік помилок, а браузер — у консоль, рядок за рядком.
- У браузері віддавайте `hello.wasm` через HTTP з того самого місця, що й `hello.mjs` (з `file://` його не завантажити).
- `sleep` чекає за допомогою `Atomics.wait`. Браузер дозволяє це лише всередині Worker на сторінці з ізоляцією cross-origin, тож програму, що використовує `sleep`, запускайте у Worker.
- Місцевий час (`decode-universal-time` без `zone` тощо) обчислюється за часовим поясом, який повідомляє `Date` з JavaScript.
- Окрім того, що не можна використовувати в розділі 3.6, операції з файлами й каталогами, змінні середовища, `(command-line-args)`, домашній каталог і `dribble` дають **помилку компіляції**. Стандартний ввід читається як порожній.

### 3.8 Компіляція для мікроконтролера (Cortex-M, RISC-V)

З `--target thumbv7em-none-eabihf` команда `typl -c` створює виконуваний файл (ELF) для плати Cortex-M4F або M7 без операційної системи. Без `-o` він отримує ім'я вихідного файлу із заміною `.typl` на `.elf`. З `--target thumbv8m.main-none-eabihf` — для плати з Cortex-M33. З `--target riscv32imac-unknown-none-elf` — для плати з 32-бітним ядром RISC-V (розширення M, A і C). З `--target thumbv6m-none-eabi` — для плати з Cortex-M0+ (M0). У QEMU немає плати з Cortex-M0+, тому виконуваний файл для неї запускається на `mps2-an385` — Cortex-M3, що виконує ті самі інструкції як є (розкладка без `--linker-script` теж береться від цієї плати).

```sh
$ typl -c hello.typl --target thumbv7em-none-eabihf          # створює hello.elf
$ qemu-system-arm -M mps2-an386 -nographic \
    -semihosting-config enable=on,target=native -kernel hello.elf   # запустити на Cortex-M4 у QEMU
$ typl -c hello.typl --target thumbv8m.main-none-eabihf
$ qemu-system-arm -M mps2-an505 -nographic \
    -semihosting-config enable=on,target=native -kernel hello.elf   # запустити на Cortex-M33 у QEMU
$ typl -c hello.typl --target thumbv6m-none-eabi
$ qemu-system-arm -M mps2-an385 -nographic \
    -semihosting-config enable=on,target=native -kernel hello.elf   # запустити на Cortex-M3 у QEMU
$ typl -c hello.typl --target riscv32imac-unknown-none-elf
$ qemu-system-riscv32 -M virt -bios none -nographic \
    -semihosting-config enable=on,target=native -kernel hello.elf   # запустити на RISC-V у QEMU
```

- `typl`, встановлений через `install.sh`, можна використовувати одразу. Щоб встановити через `cargo install`, виконайте `rustup target add thumbv7em-none-eabihf thumbv8m.main-none-eabihf thumbv6m-none-eabi riscv32imac-unknown-none-elf`, потім встановіть з `--features embedded` (`--features wasm,embedded` для обох). З налагоджувальною збіркою `typl` у репозиторії виконайте `scripts/build-embedded-runtime.sh`. Для компонування використовується компонувальник із toolchain rustup.
- Пам'ять плати задається через `--linker-script FILE`. Файл пишеться як `memory.x` з `cortex-m-rt`: адреси й розміри FLASH і RAM. Рядок на кшталт `_typelisp_stack_size = 32K;` задає, скільки RAM займає стек (типово 64KiB); решта RAM — купа. Без цієї опції використовується розкладка `mps2-an386` (для Cortex-M33 — `mps2-an505`) з QEMU.

  ```
  MEMORY
  {
    FLASH : ORIGIN = 0x08000000, LENGTH = 512K
    RAM : ORIGIN = 0x20000000, LENGTH = 128K
  }
  _typelisp_stack_size = 16K;
  ```

  Для RISC-V типово використовується розкладка `virt` з QEMU. Заданий файл також називає через `REGION_ALIAS`, як `memory.x` з `riscv-rt`, область, куди йде кожен вид секцій.

  ```
  MEMORY
  {
    FLASH : ORIGIN = 0x20010000, LENGTH = 4M - 64K
    RAM : ORIGIN = 0x80000000, LENGTH = 16K
  }
  REGION_ALIAS("REGION_TEXT", FLASH);
  REGION_ALIAS("REGION_RODATA", FLASH);
  REGION_ALIAS("REGION_DATA", RAM);
  REGION_ALIAS("REGION_BSS", RAM);
  REGION_ALIAS("REGION_HEAP", RAM);
  REGION_ALIAS("REGION_STACK", RAM);
  _typelisp_stack_size = 4K;
  ```

- На платі з невеликою RAM замість `--linker-script` можна задати `--ram SIZE` (`16K` тощо) — лише обсяг RAM для даних, купи й стека. RAM типової розкладки отримує цей розмір, а стек займає не більше чверті. На платі, де й код лежить у RAM, як `virt` для RISC-V, код іде в залишок RAM плати. Те, що середовище виконання виділяє спочатку, зменшується під розмір купи. Разом із `--linker-script` використовувати не можна.

- На платі немає операційної системи, тож стек, що переповнюється, ніщо не зупинить. Тому виконуваний файл під час входу в кожну функцію програми перевіряє, скільки лишилося стека; якщо замало, він пише `stack overflow: the program needs more than the ... bytes of the stack` і завершується з кодом 1. Щоб збільшити стек, збільште `_typelisp_stack_size` у файлі `--linker-script` або `--ram`. `--no-stack-check` прибирає цю перевірку (файл трохи менший і швидший, але переповнений стек може мовчки зіпсувати купу). В обох випадках, якщо стек переповниться всередині середовища виконання й вийде за своє дно, перед повідомленням про наступний panic чи HardFault виводиться `stack overflow: the stack has run past its bottom into the heap`.

- `--board-functions` вибирає, хто надає вивід, ввід, завершення й годинник (функції плати).
  - `semihosting` (типово): через semihosting, для запуску в QEMU (`-semihosting-config enable=on`) або під налагоджувачем.
  - `c`: плата надає їх як функції C. Передайте через `--link FILE` об'єктний файл або статичну бібліотеку з визначеннями функцій нижче (`--link` можна повторювати; бібліотека виробника, яку викликає `defffi`, передається так само).

  ```c
  void     typelisp_host_write(int32_t fd, const uint8_t *p, size_t len); // fd 1 — стандартний вивід, 2 — стандартний вивід помилок
  size_t   typelisp_host_read(int32_t fd, uint8_t *p, size_t len);        // fd 0; кількість прочитаних байтів, 0 наприкінці
  void     typelisp_host_exit(int32_t code);                              // не повертається
  uint64_t typelisp_host_now_us(void);                                    // мікросекунди годинника, що ніколи не йде назад
  int64_t  typelisp_host_unix_us(void);                                   // мікросекунди з 1970-01-01
  void     typelisp_host_sleep_us(uint64_t us);                           // чекає us мікросекунд
  ```

- Регістри плати (периферія, відображена в пам'ять) читаються через `volatile-read-u8`, `volatile-read-u16` і `volatile-read-u32` та записуються через `volatile-write-u8`, `volatile-write-u16` і `volatile-write-u32`. Адреса передається як `int` або ціле фіксованої ширини, наприклад `u16`, а прочитане значення має тип своєї ширини (`u8` тощо). Кожна форма читає або пише рівно один раз, там, де вона написана; компілятор не викидає й не переставляє її. Усі вони доступні лише всередині `unsafe`. Від'ємна адреса або адреса, не кратна ширині, — помилка часу виконання до читання чи запису.

  ```lisp
  ;; UART 0 плати mps2-an386 у QEMU: дані 0x40004000, стан 0x40004004, керування 0x40004008
  (defun put-byte ((c u32)) ()
    (unsafe
      (loop (when (= (logand (volatile-read-u32 #x40004004) 1) 0) (break)))   ; чекати, поки триває передавання
      (volatile-write-u32 #x40004000 c)))

  (defun main () ()
    (unsafe (volatile-write-u32 #x40004008 1))                               ; увімкнути передавання
    (put-byte 104) (put-byte 105) (put-byte 10))                             ; "hi" і новий рядок
  ```

- Функцію, що викликається при надходженні переривання, пишуть як `defun` з атрибутом `#[interrupt(N)]` (переривання периферії `N`) або на кшталт `#[exception(SysTick)]`. Переривання вмикається через `(enable-interrupt N)`. Обробник виконується одразу; лише якщо воно надійшло посеред роботи середовища виконання, він виконується після її закінчення. Обробник не може чекати (`sleep` — помилка компіляції). Подробиці — у розділі 3.17 [довідника із синтаксису](../reference/syntax.md). На Cortex-M0+ `N` — від 0 до 31, а `#[exception(NAME)]` може називати лише `NonMaskableInt`, `SVCall`, `PendSV` і `SysTick`. Для RISC-V `N` — номер переривання в `mcause` (від 0 до 31: 3 — програмне переривання, 7 — таймер, 11 — зовнішні переривання), а `#[exception(NAME)]` використовувати не можна.

  ```lisp
  (use std::board::enable-interrupt)

  #[interrupt(5)]
  (defun on-five () ()
    (println "interrupt 5"))

  (defun main () ()
    (enable-interrupt 5)
    (unsafe (volatile-write-u32 #xE000E200 (as u32 32))))   ; самим викликати переривання 5 (регістр очікуваних переривань NVIC)
  ```

- Середовище виконання запускає програму (таблиця векторів і підготовка RAM) і виділяє пам'ять. HardFault (на RISC-V — виняток) або необроблене переривання завершує програму з кодом виходу panic (1).
- `throw`/`catch`/`panic`, великі числа, дроби й числа з рухомою комою, а також задачі, канали й `sleep` поводяться так само, як у виконуваному файлі. Задачі виконуються по черзі на єдиному ядрі. Функції C (`defffi`) можна використовувати.
- Програма, що використовує те, чого немає на платі, дає **помилку компіляції**: окрім того, що не можна використовувати в розділі 3.7, це `eval` і `macroexpand`. Місцевий час невідомий (як у розділі 3.6).
- Арена cons починається з 1024 комірок і зростає за потреби. `--heap-cells`, `--max-memory`, `--no-cons`, `-O<N>` і `--release` працюють як звичайно.

### 3.9 Компіляція для Arduino Uno (AVR)

З `--target avr-atmega328p` створюється виконуваний файл (ELF) для мікроконтролера Arduino Uno (ATmega328P). Наступна програма блимає світлодіодом плати.

```lisp
(defconstant (PINB int) #x23)
(defconstant (DDRB int) #x24)
(defconstant (LED u8) 32)                         ; PB5

(defun wait-a-bit () ()
  (let ((i (the u32 0)))
    (while (< i (the u32 400000))
      (unsafe (volatile-read-u8 PINB))
      (setf i (+ i 1)))
    ()))

(defun main () ()
  (unsafe (volatile-write-u8 DDRB LED))           ; зробити виходом
  (while true
    (unsafe (volatile-write-u8 PINB LED))         ; перемкнути
    (wait-a-bit)))
```

```sh
$ typl -c blink.typl --target avr-atmega328p -O2   # створює blink.elf
$ qemu-system-avr -M uno -display none -serial stdio -bios blink.elf   # запустити в QEMU
```

- Середовища виконання немає, тому програма, яка його використовує, — це **помилка компіляції**. У помилці зазначено, що потрібно і через які функції до цього доходять. Можна використовувати: обчислення з цілими фіксованої ширини (від `i8` до `u32`), `f32`, `f64`, `bool` і `char`, виклики функцій (зокрема рекурсивні), умови, цикли, `defvar` і `defconstant` з такими значеннями, `volatile-read-u8` та подібні, а також виклики функцій C.
- Не можна використовувати: значення в купі, як-от рядки, списки й структури; `catch` і виклики значень-функцій; виклики функцій C, що приймають рядок або функцію; математичні функції чисел з рухомою комою, як-от `sin` і `expt` (`sqrt` та округлення, як-от `floor`, використовувати можна).
- Обробник переривання записують як `#[interrupt(N)]` ([Синтаксис](../reference/syntax.md), розділ 3.17). `N` — номер переривання ATmega328P від 1 до 25, якщо рахувати скидання за 0 (переповнення таймера 1 — 13). Див. приклад нижче.
- Ділення на 0 зупиняє мікроконтролер на місці (переривання теж більше не приходять). Так само діє `/` найменшого знакового значення на `-1`.
- `int` використовувати не можна (помилка компіляції): у нього немає фіксованої ширини. Використовуйте тип фіксованої ширини, наприклад `i16` або `u16`. Адреси теж можна обчислювати в цілих фіксованої ширини. Те, що визначається під час компіляції, використовувати можна, наприклад адресу, записану числом, і `int` з `defconstant`.
- Якщо під час рекурсії не вистачає стека, мікроконтролер зупиняється.
- Функцію C оголошують через `defffi`, а об'єктний файл, скомпільований для AVR, передають через `--link FILE`.
- Цикл, який нічого не робить, зникає починаючи з `-O1`. У циклі очікування читайте, наприклад, регістр.
- Коли `main` завершується, мікроконтролер зупиняється.
- Розташування пам'яті змінюється за допомогою `--linker-script FILE`. Без нього це 32 КіБ флеш-пам'яті без останніх 512 байтів завантажувача та 2 КіБ RAM. Адреси RAM записуються з доданим `0x800000`, наприклад `0x800100`.
- Обчислення з `f32` і `f64` виконують допоміжні функції. До флеш-пам'яті потрапляють ті, що використовуються (для `f64` вони більші).
- Для компонування, як і в розділі 3.8, використовується компонувальник із набору інструментів rustup.

Приклад, що блимає світлодіодом за перериванням таймера. Переривання дозволяють у регістрі самого пристрою.

```lisp
(defconstant (PINB int) #x23)
(defconstant (DDRB int) #x24)
(defconstant (LED u8) 32)
(defconstant (TIMSK1 int) #x6F)
(defconstant (TCCR1B int) #x81)
(defvar (ticks u16) 0)

#[interrupt(13)]                                  ; переповнення таймера 1
(defun on-overflow () ()
  (unsafe (volatile-write-u8 PINB LED))           ; перемкнути
  (setf ticks (+ ticks 1))
  ())

(defun main () ()
  (unsafe (volatile-write-u8 DDRB LED)
          (volatile-write-u8 TIMSK1 1)            ; дозволити переривання переповнення
          (volatile-write-u8 TCCR1B 3))           ; лічити з 1/64 частоти
  (while true))
```

- Програма з обробником приймає переривання, щойно ініціалізовано її глобальні змінні. Налаштовуйте пристрої на початку `main`.
- `enable-interrupt` і `#[exception(NAME)]` використовувати не можна (помилка компіляції).
- Поки обробник виконується, інші переривання чекають. Як і будь-яка інша функція, обробник не може використовувати середовище виконання.
- Одне читання чи запис глобальної змінної обробник не перериває, навіть для значення у два байти й більше. Заради цього переривання забороняються під час читання змінної, яку пише обробник, і під час запису змінної, яку обробник читає або пише, і про таку змінну під час компіляції виводиться попередження. Між читанням і записом під час оновлення (`(setf n (+ n 1))`) переривання прийти може. Щоб оновити змінну, яку пише й обробник, прочитайте та збережіть регістр стану (адреса `#x5F`), запишіть у нього 0, щоб зупинити переривання, а потім запишіть збережене значення назад.
- Переривання без обробника зупиняє мікроконтролер.

## 4. Дампи

Визначення поточного сеансу можна зберегти в один файл і наступного разу запустити з нього.

```sh
$ typl
typl> (defun sq ((n i32)) i32 (* n n))
typl> (compile sq)
true
typl> (dump "session.typld")
true
typl> :quit
$ typl --image session.typld
typl> (sq 9)
81
```

Це працює й для запуску файлу, як-от `typl --image session.typld prog.typl`.

- Зберігаються **визначення**. Вирази, обчислені в сеансі, не зберігаються.
- Функції, які ви `compile`-нули, зберігаються в скомпільованому вигляді.
- Глобальні змінні відновлюються **повторним запуском їхніх ініціалізаторів**, а не зі значеннями, які
  вони мали під час запису дампу.
- Дамп не можна завантажити через `typl` іншої версії, ніж та, що його записала (це помилка).

Якщо ви запускаєте файл і з нього робите `(dump ...)`, визначення цього файлу лежать у модулі з назвою
файлу. Функція, визначена в `dp.typl`, називається `dp::sq`, а щоб викликати її з іншого файлу, потрібен
`pub` ([Модулі та розкладання по файлах](modules.md)).

## 5. Про скомпільовані файли модулів

Формату на кшталт `.fasl` у Common Lisp, що записує скомпільований результат кожного модуля у файл,
немає. `compile-file` збирає виконуваний файл безпосередньо з вихідного коду. Жодних проміжних
файлів не залишається.
