# Компиляция

Если ничего специально не делать, программы typelisp выполняются интерпретатором. Кроме того, есть два способа
компиляции в машинный код и один способ сохранить окружение. Подробности спецификации — в
[главе 10 справочника по синтаксису](../reference/syntax.md#10-компиляция).

| Способ | Как | Результат |
|---|---|---|
| JIT-компиляция | `(compile name)` | Функция в текущем сеансе заменяется машинным кодом |
| AOT-компиляция | `typl -c src.typl` или `(compile-file "src.typl" "out")` | Самостоятельный исполняемый файл |
| Дамп | `(dump "file.typld")` | Сохраняет определения; `typl --image` запускается снова с тем же окружением |

## 1. Подготовка

Компиляция использует LLVM 22. Если вы собрали `typl` по [README.md](../../../README.md), никакой дополнительной
подготовки не нужно.

Исполняемые файлы, получаемые AOT-компиляцией, компонуются со статической библиотекой `libtypelisp_front.a`.
Релизная сборка `typl` (включая установленную через `cargo install`) несёт эту библиотеку внутри себя, поэтому
подготовка не нужна. При первой компиляции она записывает библиотеку в `~/.typelisp/lib/<идентификатор сборки>/` (или
в `$TYPELISP_HOME/lib/<идентификатор сборки>/`, если задана переменная окружения `TYPELISP_HOME`) и дальше использует
эту копию. `typl --remove-lib` удаляет её (с `--others` — записанные другими версиями `typl`; с `--all` — все).
Отладочная сборка `typl` использует библиотеку в `target/debug/` репозитория, где она была собрана. Чтобы
использовать библиотеку, лежащую в другом месте, укажите её каталог через `--lib-dir` при запуске `typl`
(раздел 3.2). В macOS для компоновки используются Xcode Command Line Tools.

## 2. JIT-компиляция

Превращает уже определённую функцию в машинный код прямо на месте.

```lisp
(defun fib ((n int)) int
  (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2)))))

(compile fib)
(fib 30)           ; с этого момента вызовы выполняют скомпилированный код
```

- `name` не вычисляется. Пишите имя функции как есть (не строкой). Для метода пишите его с именем типа, как
  `(compile point::norm)`.
- Вызываемые функции компилируются вместе с ней.
- **Обобщённые функции компилировать нельзя.** Для каждого типа в каждом месте использования создаётся своя копия.
  Вместо этого компилируйте функцию, которая вызывает её с конкретными типами.
- `trace`, `step`, `disassemble`, `compile`, `compile-file` и `dump` — операции интерпретатора, поэтому функцию,
  которая их вызывает, скомпилировать нельзя. Попытка даёт ошибку с объяснением причины.

Чтобы посмотреть результат компиляции, используйте `disassemble`.

```lisp
(disassemble fib)          ; машинный код хоста
(disassemble fib true)     ; LLVM IR
```

## 3. Сборка исполняемого файла AOT-компиляцией

### 3.1 Написание программы

В качестве точки входа определите **функцию `main` без аргументов**.

```lisp
(use std::env::command-line-args)
;; hello.typl
(defun fib ((n int)) int
  (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2)))))

(defun main () ()
  (println "args: ~a" (command-line-args))
  (println "fib(25) = ~a" (fib 25)))

(main)
```

`(main)` в конце файла нужен для того, чтобы `main` вызывалась при запуске `typl hello.typl`. `compile-file`
пропускает этот завершающий `(main)`, так что один и тот же файл работает и в интерпретаторе, и при AOT-компиляции.

### 3.2 Компиляция

В командной строке используйте `typl -c` (`typl --compile` — то же самое).

```sh
$ typl -c hello.typl            # создаёт hello
$ typl -c hello.typl -o fib     # называет исполняемый файл fib
$ ./hello a b
args: #(./hello a b)
fib(25) = 75025
```

Без `-o` исполняемый файл получает имя исходного файла без `.typl` и помещается в тот же каталог, что и исходный файл.
Если имя исходного файла не оканчивается на `.typl`, `-o` обязателен. С `-c` (`--compile`) нельзя указывать
`--image` и `--feature`.

С `--release` `typl` делает **релизную сборку**, которая удаляет `eprint`/`eprintln` (вывод в стандартный поток ошибок для отладки; [Печать](../reference/functions/printing.md)) вместе с их аргументами. Удаляемое всё равно проходит проверку типов, так что ошибка типов в нём приводит к провалу компиляции. `--release` — опция `typl` в целом: она действует одинаково не только для `-c`, но и при запуске файла, в REPL и для `typl test`. `compile-file`, вызванный внутри `typl`, запущенного с `--release`, тоже делает релизную сборку, а из кода, выполняемого через `eval` внутри собранного так исполняемого файла, `eprint`/`eprintln` тоже удаляются.

```sh
$ typl --release -c hello.typl
$ typl -c hello.typl --release     # то же самое, если написать после -c
```

`-O0`, `-O1`, `-O2` и `-O3` задают **уровень оптимизации**. По умолчанию — `-O0`, без оптимизации. Начиная с `-O1`, компилятор сначала выполняет простые оптимизации — например, заменяет переменную, связанную только с литералом, её значением или заранее вычисляет целочисленную арифметику над константами, — а остальное оставляет оптимизации LLVM на уровне с тем же именем. На любом уровне результаты вычислений одинаковы. Как и `--release`, это опция `typl` в целом: помимо исполняемого файла, который создаёт `-c`, она действует на код, компилируемый при запуске файла, в REPL и в `typl test`, а также на вызванный там `compile-file`. Код, который выполняет интерпретатор, не оптимизируется.

```sh
$ typl -O2 -c hello.typl
$ typl -c hello.typl -O2     # то же самое, если написать после -c
```

То же самое можно сделать, вызвав `compile-file` из REPL или из программы.

```sh
$ typl
typl> (compile-file "hello.typl" "hello")
typl> :quit
$ ./hello a b
args: #(./hello a b)
fib(25) = 75025
```

Если вы собираете часто, можно поместить эту строку в файл и запускать его командой `typl build.typl`.

```lisp
;; build.typl
(compile-file "hello.typl" "hello")
```

Имена файлов разрешаются относительно **текущего каталога, в котором был запущен `typl`**, а не относительно
местоположения `build.typl`.

Чтобы скомпоновать с `libtypelisp_front.a`, лежащей не там, где её ищет `typl`, укажите её каталог через `--lib-dir`.
Это действует и для `typl -c`, и для `compile-file`.

```sh
$ typl --lib-dir ~/lib/typelisp -c hello.typl
$ typl --lib-dir ~/lib/typelisp build.typl
```

Если в указанном каталоге нет `libtypelisp_front.a`, `typl` останавливается с ошибкой. Файл работает только с тем
`typl`, который был собран вместе с ним. После пересборки `typl` скопируйте его заново.

### 3.3 Что может содержать файл для AOT-компиляции

- Верхний уровень входного файла может содержать только определения (`defun` `defvar`
  `defparameter` `defconstant` `defmacro` `defsignature` `defstruct` `defenum` `deftype` `deftrait`
  `impl` `defffi`, `(unsafe (def-c-struct ...))`), а также `use` и `module`. Выражения верхнего уровня
  вроде `(println ...)` не допускаются, кроме завершающего `(main)`. Размещайте работу внутри `main`.
- Без `main` без аргументов компиляция завершается ошибкой.
- Файлы подключённых через `use` модулей тоже компилируются и объединяются в один исполняемый файл.
- Библиотеки, указанные через `:library` в `defffi`, компонуются автоматически ([FFI для C](ffi.md)).
- Все функции стандартной библиотеки можно использовать при AOT-компиляции. `eval` тоже, но тогда в исполняемый файл
  попадают проверка типов и интерпретатор, отчего он становится больше и медленнее запускается. Программы, не
  вызывающие `eval`, их не содержат.

### 3.4 Поведение исполняемого файла

- `(command-line-args)` возвращает `Vector<string>` одинаковой формы, запускать ли `typl hello.typl a b` или
  `./hello a b`. Первый элемент — имя программы.
- Код завершения задаётся через `(exit n)`. Если `main` возвращается нормально, он равен 0.
- При `panic` программа выводит сообщение и завершается с ненулевым кодом.

### 3.5 Ресурсы исполняемого файла

У `typl -c` есть опции, которые задают, какие ресурсы исполняемый файл может использовать во время работы.

```sh
$ typl --heap-cells 100000 -c hello.typl    # закрепить арену cons на 100000 ячеек
$ typl -c hello.typl --max-memory 64M       # выделять не больше 64 МиБ
$ typl -c hello.typl --no-cons              # не использовать cons-ячейки
```

- `--heap-cells N` закрепляет ёмкость арены cons-ячеек на `N` ячейках. Арена больше не растёт: если сборка мусора не может освободить ни одной ячейки, программа останавливается с ошибкой времени выполнения. Без этой опции арена начинается с 65536 ячеек и растёт по мере надобности.
- `--max-memory SIZE` ограничивает общий объём памяти, который выделяет исполняемый файл. Учитывается всё: арена cons, строки, такие значения, как векторы и хеш-таблицы, и память самой среды выполнения. `SIZE` — число байтов, за которым может стоять `K`, `M` или `G` (в 1024, 1024² и 1024³ раз). О выделении, которое превысило бы границу, сообщается, и программа завершается с кодом выхода 1. Это завершение нельзя перехватить через `catch`. Без этой опции границы нет.
- `--no-cons` создаёт исполняемый файл, который не использует cons-ячейки. У него нет арены cons, поэтому программа, делающая что-то, для чего нужны cons-ячейки, — **ошибка компиляции**, которая показывает эту операцию и цепочку функций от `main`, ведущую к ней. Cons-ячейки нужны, чтобы построить список `Sexpr` (в том числе квотированный список и список, построенный квазиквотированием) или аргумент `&rest`, а также для `read`, `eval` и `macroexpand`. Операции над числами, строками, векторами, хеш-таблицами, структурами, каналами и т. п., а также `print`/`println`/`format` их не используют. Нельзя указывать вместе с `--heap-cells`; пишется после `-c`.

`--max-memory` пишется после `-c`. `--heap-cells` можно писать до или после `-c`, и тогда это ёмкость арены cons исполняемого файла. Арена cons входит в границу памяти, поэтому при границе, в которую арена не помещается, программа останавливается, не начавшись.

### 3.6 Компиляция в WebAssembly

С `--target wasm32-wasip1` команда `typl -c` создаёт вместо исполняемого файла модуль WebAssembly (команду WASI preview 1). Без `-o` он называется как исходный файл, с `.wasm` вместо `.typl`.

```sh
$ typl -c hello.typl --target wasm32-wasip1      # создаёт hello.wasm
$ wasmtime hello.wasm a b                        # запуск в среде с поддержкой WASI
args: #(hello.wasm a b)
fib(25) = 75025
```

- `typl`, установленный через `install.sh`, можно использовать как есть. Для установки через `cargo install` нужна подготовка (она же годится для раздела 3.7). Сначала выполните `rustup target add wasm32-wasip1 wasm32-unknown-unknown` через rustup. Затем установите его с `--features wasm` (`cargo install --locked --path . --features wasm`).
  У `typl`, установленного без этого, нет среды выполнения WebAssembly, и `--target` даёт ошибку. Для отладочной сборки `typl` в репозитории вместо этого выполните `scripts/build-wasm-runtime.sh` в репозитории.
- Компоновка использует компоновщик тулчейна rustup (`rust-lld`), поэтому rustup нужен и при компиляции.
- Модуль ведёт себя как исполняемый файл: стандартный вывод, стандартный поток ошибок и код выхода, `(command-line-args)`,
  чтение и запись файлов, `throw`/`catch`/`panic`, задачи, каналы и `sleep`, а также `eval` работают.
  Задачи выполняются по очереди в одном потоке. Читать и писать файлы можно только в каталогах,
  которые среда открывает модулю (в wasmtime они задаются через `--dir`).
- Программа, использующая то, чего нет в WebAssembly, — это **ошибка компиляции**. В ошибке показано, что использовано,
  и цепочка функций от `main`, которая к этому ведёт. Недоступны: сокеты (TCP, UDP, Unix-сокеты,
  TLS, разрешение имён), потоки ОС (`Thread`), функции C (`defffi`), `get-internal-run-time`, `machine-instance`, `software-version`, `file-author`
  и `ed`.
- В WASI нет способа узнать часовой пояс, поэтому местное время неизвестно. `decode-universal-time` и `encode-universal-time` без `zone`, а также `get-decoded-time` вызывают panic во время выполнения. С заданным `zone` они работают.
- `--heap-cells`, `--max-memory`, `--no-cons`, `-O<N>` и `--release` действуют так же, как для исполняемого файла.

### 3.7 Запуск в браузере или в Node.js

С `--target wasm32-unknown-unknown` команда `typl -c` создаёт модуль WebAssembly, который загружается и запускается из JavaScript. Рядом с модулем (`hello.wasm`), в той же папке, появляется JavaScript, который его загружает и запускает (`hello.mjs`). Подготовка та же, что в разделе 3.6.

```sh
$ typl -c hello.typl --target wasm32-unknown-unknown   # создаёт hello.wasm и hello.mjs
$ node hello.mjs                                       # запуск в Node.js
args: #()
fib(25) = 75025
```

Из другого JavaScript вызовите `run` из `hello.mjs`. `write` получает вывод в виде текста (`fd` равен 1 для стандартного вывода и 2 для стандартного потока ошибок). Значение `run` — код выхода.

```js
import { run } from './hello.mjs';
const code = await run({ write: (fd, text) => { /* например, показать на странице */ } });
```

- Без `write` Node.js пишет в стандартный вывод и стандартный поток ошибок, а браузер — в консоль, построчно.
- В браузере отдавайте `hello.wasm` по HTTP из того же места, что и `hello.mjs` (из `file://` его загрузить нельзя).
- `sleep` ждёт с помощью `Atomics.wait`. Браузер разрешает это только внутри Worker на странице с изоляцией cross-origin, поэтому программу, использующую `sleep`, запускайте в Worker.
- Местное время (`decode-universal-time` без `zone` и т. п.) вычисляется по часовому поясу, который сообщает `Date` из JavaScript.
- Помимо того, что нельзя использовать в разделе 3.6, операции с файлами и каталогами, переменные окружения, `(command-line-args)`, домашний каталог и `dribble` дают **ошибку компиляции**. Стандартный ввод читается как пустой.

### 3.8 Компиляция для микроконтроллера (Cortex-M)

С `--target thumbv7em-none-eabihf` команда `typl -c` создаёт исполняемый файл (ELF) для платы Cortex-M4F или M7 без операционной системы. Без `-o` он получает имя исходного файла с заменой `.typl` на `.elf`.

```sh
$ typl -c hello.typl --target thumbv7em-none-eabihf          # создаёт hello.elf
$ qemu-system-arm -M mps2-an386 -nographic \
    -semihosting-config enable=on,target=native -kernel hello.elf   # запустить на Cortex-M4 в QEMU
```

- `typl`, установленный через `install.sh`, можно использовать сразу. Для установки через `cargo install` выполните `rustup target add thumbv7em-none-eabihf`, затем установите с `--features embedded` (`--features wasm,embedded` для обоих). С отладочной сборкой `typl` в репозитории выполните `scripts/build-embedded-runtime.sh`. Для компоновки используется компоновщик из toolchain rustup.
- Память платы задаётся через `--linker-script FILE`. Файл пишется как `memory.x` из `cortex-m-rt`: адреса и размеры FLASH и RAM. Строка вида `_typelisp_stack_size = 32K;` задаёт, сколько RAM занимает стек (по умолчанию 64KiB); остальная RAM — куча. Без этой опции используется раскладка `mps2-an386` из QEMU.

  ```
  MEMORY
  {
    FLASH : ORIGIN = 0x08000000, LENGTH = 512K
    RAM : ORIGIN = 0x20000000, LENGTH = 128K
  }
  _typelisp_stack_size = 16K;
  ```

- `--board-functions` выбирает, кто предоставляет вывод, ввод, завершение и часы (функции платы).
  - `semihosting` (по умолчанию): через semihosting, для запуска в QEMU (`-semihosting-config enable=on`) или под отладчиком.
  - `c`: плата предоставляет их как функции C. Передайте через `--link FILE` объектный файл или статическую библиотеку с определениями функций ниже (`--link` можно повторять; библиотека производителя, вызываемая через `defffi`, передаётся так же).

  ```c
  void     typelisp_host_write(int32_t fd, const uint8_t *p, size_t len); // fd 1 — стандартный вывод, 2 — стандартный вывод ошибок
  size_t   typelisp_host_read(int32_t fd, uint8_t *p, size_t len);        // fd 0; число прочитанных байт, 0 в конце
  void     typelisp_host_exit(int32_t code);                              // не возвращается
  uint64_t typelisp_host_now_us(void);                                    // микросекунды часов, которые никогда не идут назад
  int64_t  typelisp_host_unix_us(void);                                   // микросекунды с 1970-01-01
  void     typelisp_host_sleep_us(uint64_t us);                           // ждёт us микросекунд
  ```

- Регистры платы (периферия, отображённая в память) читаются через `volatile-read-u8`, `volatile-read-u16` и `volatile-read-u32` и записываются через `volatile-write-u8`, `volatile-write-u16` и `volatile-write-u32`. Адрес передаётся как `int`, а прочитанное значение имеет тип своей ширины (`u8` и т. д.). Каждая форма читает или пишет ровно один раз, там, где она написана; компилятор не выбрасывает и не переставляет её. Все они доступны только внутри `unsafe`. Отрицательный адрес или адрес, не кратный ширине, — ошибка времени выполнения до чтения или записи.

  ```lisp
  ;; UART 0 платы mps2-an386 в QEMU: данные 0x40004000, состояние 0x40004004, управление 0x40004008
  (defun put-byte ((c u32)) ()
    (unsafe
      (loop (when (= (logand (volatile-read-u32 #x40004004) 1) 0) (break)))   ; ждать, пока идёт передача
      (volatile-write-u32 #x40004000 c)))

  (defun main () ()
    (unsafe (volatile-write-u32 #x40004008 1))                               ; включить передачу
    (put-byte 104) (put-byte 105) (put-byte 10))                             ; "hi" и перевод строки
  ```

- Функцию, вызываемую при приходе прерывания, пишут как `defun` с атрибутом `#[interrupt(N)]` (прерывание периферии `N`) или вроде `#[exception(SysTick)]`. Прерывание включается через `(enable-interrupt N)`. Обработчик выполняется сразу; только если оно пришло посреди работы среды выполнения, он выполняется после её окончания. Обработчик не может ждать (`sleep` — ошибка компиляции). Подробности — в разделе 3.17 [справочника по синтаксису](../reference/syntax.md).

  ```lisp
  (use std::board::enable-interrupt)

  #[interrupt(5)]
  (defun on-five () ()
    (println "interrupt 5"))

  (defun main () ()
    (enable-interrupt 5)
    (unsafe (volatile-write-u32 #xE000E200 (as u32 32))))   ; самим вызвать прерывание 5 (регистр ожидающих прерываний NVIC)
  ```

- Среда выполнения запускает программу (таблица векторов и подготовка RAM) и выделяет память. HardFault или необработанное прерывание завершает программу с кодом выхода panic (1).
- `throw`/`catch`/`panic`, большие числа, дроби и числа с плавающей точкой, а также задачи, каналы и `sleep` работают так же, как в исполняемом файле. Задачи выполняются по очереди на единственном ядре. Функции C (`defffi`) можно использовать.
- Программа, использующая то, чего нет на плате, даёт **ошибку компиляции**: помимо того, что нельзя использовать в разделе 3.7, это `eval` и `macroexpand`. Местное время неизвестно (как в разделе 3.6).
- Арена cons начинается с 1024 ячеек и растёт по мере надобности. `--heap-cells`, `--max-memory`, `--no-cons`, `-O<N>` и `--release` работают как обычно.

## 4. Дампы

Определения текущего сеанса можно сохранить в один файл и в следующий раз начать с него.

```sh
$ typl
typl> (defun sq ((n i32)) i32 (* n n))
typl> (compile sq)
true
typl> (dump "session.typld")
true
typl> :quit
$ typl --image session.typld
typl> (sq 9)
81
```

Это работает и при запуске файла, как `typl --image session.typld prog.typl`.

- Сохраняются **определения**. Выражения, вычисленные в сеансе, не сохраняются.
- Функции, скомпилированные через `compile`, сохраняются в скомпилированном виде.
- Глобальные переменные восстанавливаются **повторным выполнением их инициализаторов**, а не со значениями, которые
  они имели в момент записи дампа.
- Дамп нельзя загрузить `typl` другой версии, чем та, что его записала (это ошибка).

Если вы запускаете файл и делаете из него `(dump ...)`, определения этого файла находятся в модуле, названном по
имени файла. Функция, определённая в `dp.typl`, называется `dp::sq`, и для вызова из другого файла нужен `pub`
([Модули и разбиение на файлы](modules.md)).

## 5. О скомпилированных файлах модулей

Формата наподобие `.fasl` из Common Lisp для записи скомпилированного результата каждого модуля в файл нет.
`compile-file` строит исполняемый файл прямо из исходников. Промежуточных файлов не остаётся.
