# Задачи и каналы

Словарь задач (лёгких потоков). `task` и `thread`, которые их запускают, и `select`, который ждёт нескольких
событий, — специальные формы, они описаны в [Справочнике по синтаксису](../syntax.md#12-конкурентность-задачи). Эта
глава охватывает остальное: типы, методы и функции.

Задачи **кооперативны**: задача переключается только в тех местах, которые вы пишете. Задачи выполняются одновременно
на `TYPELISP_THREADS` потоках ОС (в `typl` на другие потоки уходят только скомпилированные задачи). Где они
переключаются и чем это отличается от Go, описано в
[Справочнике по синтаксису 12.5](../syntax.md#125-где-переключаются-задачи) и
[12.7](../syntax.md#127-отличия-от-go).

## 1. `Task<T>` — дескрипторы задач

| Имя | Использование | Тип | Смысл |
|---|---|---|---|
| `wait` | `(wait t)` | `(Task<T>)→T` | Ждёт завершения и возвращает значение |

```lisp
(let ((t1 (task (work 7))))
  (wait t1))
```

- **`wait` можно вызывать сколько угодно раз** (значение кешируется). В отличие от `JoinHandle::join` в Rust, он не
  поглощает дескриптор, так что ждать можно из нескольких мест.
- **Задача выполняется, даже если никогда не делать `wait`.** Отказ от дескриптора её не останавливает.
- Это обычное значение, поэтому его можно положить в `Vector<Task<()>>`.
- **Когда главная задача завершается, завершается процесс** (как в Go). Остальные работающие задачи обрываются, и
  очистка `unwind-protect` не выполняется, потому что это завершение процесса, а не раскрутка стека.

## 2. `Chan<T>` — каналы

| Имя | Использование | Тип | Смысл |
|---|---|---|---|
| `Chan::new` | `(the Chan<int> (Chan::new 0))` | `(int)→Chan<T>` | Канал ёмкости `n`. `0` — рандеву (без буфера) |
| `send` | `(send ch v)` | `(Chan<T>,T)→()` | Ждёт, пока появится место, затем передаёт значение |
| `recv` | `(recv ch)` | `(Chan<T>)→Option<T>` | Ждёт, пока придёт значение. `none`, когда канал закрыт и пуст |
| `close` | `(close ch)` | `(Chan<T>)→()` | Закрывает его |
| `len` | `(len ch)` | `(Chan<T>)→int` | Сколько значений сейчас в буфере |
| `cap` | `(cap ch)` | `(Chan<T>)→int` | Ёмкость |

**Аргумент типа задаётся через `the`** (так же, как `(the Vector<i32> (Vector::new))`). **Ёмкость нужно писать
всегда**: два случая, которые в Go пишутся `make(chan int)` и `make(chan int, 16)`, пишутся `(Chan::new 0)` и
`(Chan::new 16)`.

```lisp
(defun produce ((ch Chan<int>) (n int)) ()
  (dotimes (i n) (send ch (* i 2)))
  (close ch))

(let ((ch (the Chan<int> (Chan::new 2))))
  (task (produce ch 5))
  (doiter (v ch) (println "~a" v)))       ; for v := range ch из Go
```

- **`Chan<T>` сам является своим итератором** (реализует `Iter`). `recv` возвращает `Option<T>`, тот же тип, что и
  `Iter::next`, поэтому `doiter` и `map`/`filter`/`foldl` работают с ним как есть.
- **`send` в закрытый канал вызывает panic**, и **повторный `close` тоже** (оба — как в Go). Это ошибки в программе, а
  не восстановимые неудачи, поэтому это не `Result`.
- **Закрытие канала, на котором задача ждёт возможности сделать `send`, вызывает panic в этой задаче** (правило Go).
- `recv` на закрытом канале возвращает то, что осталось в буфере, а когда он опустеет, продолжает возвращать `none`.
- `close` разрешается по типу получателя, так что это не то же самое, что `close` трейта `Stream`. `Chan<T>` не
  реализует `Stream`.
- **Отрицательная ёмкость вызывает panic** (она не округляется молча до 0).

## 3. `yield` / `sleep` — уступить очередь

| Имя | Использование | Тип | Смысл |
|---|---|---|---|
| `yield` | `(yield)` | `()→()` | Отдаёт остаток своей очереди (`runtime.Gosched` из Go) |
| `sleep` | `(sleep 0.5)` | `(f64)→()` | Останавливает **только эту задачу**. Остальные продолжают работать |

`sleep` останавливает задачу, а не поток. Только когда ни одна задача не может выполняться, он уходит в `sleep` ОС до
ближайшего срока. `(sleep 0.0)` — это «уступить на 0 секунд» из CL.

Как и в CL, `sleep` принимает **секунды**. Целые не преобразуются в числа с плавающей точкой автоматически, поэтому
`(sleep 1)` из CL здесь пишется `(sleep 1.0)`. Отрицательное значение или NaN вызывает panic.

## 4. `WaitGroup` — ожидание N завершений

| Имя | Использование | Тип | Смысл |
|---|---|---|---|
| `WaitGroup::make` | `(the WaitGroup (WaitGroup::make))` | `()→WaitGroup` | Группа без незавершённых дел |
| `add` | `(add wg 1)` | `(WaitGroup,int)→()` | Увеличивает счётчик. Делайте это до начала работы |
| `done` | `(done wg)` | `(WaitGroup)→()` | Одно дело завершено. При 0 освобождаются все ожидающие |
| `wait` | `(wait wg)` | `(WaitGroup)→()` | Ждёт, пока счётчик не дойдёт до 0. Из любого числа задач |

`(wait wg)` и `(wait task)` разрешаются по типу получателя, поэтому сосуществуют под одним именем. Если счётчик
опускается ниже 0, происходит panic (`done` вызван слишком часто или `add` с отрицательным числом). Как в Go, группу,
вернувшуюся к 0, можно использовать снова, начав с `add`. Никакое обновление не теряется, даже если задачи выполняются
на разных потоках ОС.

**При наличии `Task<T>` она нужна реже, чем в Go**: часто достаточно `(doiter (t tasks) (wait t))`. Это средство для
динамически растущей работы или для случая, когда не хочется хранить дескрипторы.

```lisp
;; fan-in: запустить по задаче на каждый вход и объединить их (в этом языке нет nil-каналов)
(defvar (left i32) 0)
(defun drain ((in Chan<i32>) (out Chan<i32>)) ()
  (doiter (v in) (send out v))
  (setf left (- left 1))
  (if (eq left 0) (close out) ()))
```

## 5. `after` — канал, выдающий значение через заданное время

| Имя | Использование | Тип | Смысл |
|---|---|---|---|
| `after` | `(recv (after 0.5))` | `(f64)→Chan<()>` | Канал, выдающий одно значение через `sec` секунд |

`time.After` из Go. Его можно писать как есть в ветви тайм-аута `select`
([Справочник по синтаксису 12.3](../syntax.md#123-select--ожидание-нескольких-операций-с-каналами-сразу)). Его
ёмкость 1, поэтому отправляющая задача может завершиться, даже если никто не получит значение.

## 6. `Mutex<T>` — взаимное исключение для общих данных

| Имя | Использование | Тип | Смысл |
|---|---|---|---|
| `Mutex::make` | `(the Mutex<i32> (Mutex::make 0))` | `(T)→Mutex<T>` | Незаблокированный мьютекс, содержащий `v` |
| `lock` | `(lock m)` | `(Mutex<T>)→()` | Берёт блокировку (ждёт) |
| `unlock` | `(unlock m)` | `(Mutex<T>)→()` | Освобождает её. Panic, если она не взята |
| `with-lock` | `(with-lock (x m) body...)` | Макрос | Блокирует, связывает содержимое с `x`, выполняет `body` и **всегда** освобождает |

```lisp
(let ((counter (the Mutex<i32> (Mutex::make 0))))
  (with-lock (n counter) (setf n (+ n 1)))
  (with-lock (n counter) n))                     ; => 1
```

- **`x` — не копия значения, а «место»** (`symbol-macrolet`). `(setf x 42)` изменяет содержимое мьютекса.
- `with-lock` освобождает через `unwind-protect`, поэтому блокировка освобождается, как бы ни было покинуто тело:
  нормальное завершение, `throw`, `panic` или `break`/`return`/`return-from`.
- **Повторный вход приводит к взаимоблокировке** (а не к panic). Планировщик сообщает, что «ничто не может
  продвинуться», для задачи, застрявшей на собственной блокировке.
- **`m::v` обращается к содержимому вне блокировки**, что неопределено в том смысле, что другая задача может как раз
  его изменять. Это та же позиция, что у `sync.Mutex` в Go: в языке без проверки владения и заимствования статическую
  гарантию вроде `MutexGuard` построить нельзя.

## 7. `Thread<T>` — отдельные потоки ОС

Дескриптор, возвращаемый `(thread (f args...))`
([Справочник по синтаксису 12.2](../syntax.md#122-thread--запуск-задачи-в-отдельном-потоке-ос)). Аналог `Task<T>`.

| Имя | Использование | Тип | Смысл |
|---|---|---|---|
| `join` | `(join th)` | `(Thread<T>)→T` | Ждёт завершения и возвращает значение (останавливается вызывающая **задача**. Можно вызывать сколько угодно раз; значение кешируется) |
| `Thread::spawn` | `(Thread::spawn (lambda () int 42))` | `((fn () T))→Thread<T>` | Функциональная версия `(thread (f))` (`std::thread::spawn` из Rust) |
| `Thread::current-id` | `(Thread::current-id)` | `()→int` | Номер выполняющегося потока ОС. Уникален в пределах процесса, без иного смысла, кроме «тот же ли это поток» |
| `Thread::available-parallelism` | `(Thread::available-parallelism)` | `()→int` | Число потоков, которые машина может выполнять одновременно (значение `TYPELISP_THREADS` по умолчанию). Panic, если ОС не отвечает |

```lisp
(defffi (c-usleep "usleep") (u32) i32)
(defun sleepy ((us int)) int
  (progn (unsafe (c-usleep (as u32 us))) us))    ; блокирующая функция C
(let ((th (thread (sleepy 500000))))
  ...                                            ; тем временем другие задачи продолжают работать
  (join th))                                     ; => 500000
```

- Вызов блокирующей функции C (`defffi`) останавливает только этот поток.
- `task` внутри `thread` выполняется как обычная задача на других потоках.
- Можно использовать и в `typl`. При интерпретации `(thread (f ...))` компилирует `f` на месте и затем выполняет её в
  отдельном потоке.
- `Thread::spawn` принимает функциональное значение, поэтому на месте не компилирует. Вызов с верхнего уровня,
  который интерпретирует `typl`, вызывает panic
  ([Справочник по синтаксису 12.2](../syntax.md#122-thread--запуск-задачи-в-отдельном-потоке-ос)). Из
  скомпилированных функций им пользоваться можно.

## 8. Чего нет

- **`Atomic`**. Хватает `Mutex`.
- **Локальных для задачи переменных** (в Go их тоже нет).
- **nil-каналов**. Причина и альтернатива — в [Справочнике по синтаксису 12.7](../syntax.md#127-отличия-от-go).
