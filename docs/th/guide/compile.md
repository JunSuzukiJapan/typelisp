# การคอมไพล์

หากไม่ทำอะไรเพิ่ม โปรแกรม typelisp จะรันในอินเทอร์พรีเตอร์ นอกจากนี้ยังมีวิธีคอมไพล์เป็นโค้ดเนทีฟ
สองวิธี และวิธีบันทึกสภาพแวดล้อมอีกหนึ่งวิธี รายละเอียดของข้อกำหนดอยู่ใน
[เอกสารอ้างอิงไวยากรณ์ บทที่ 10](../reference/syntax.md#10-การคอมไพล์)

| วิธี | ทำอย่างไร | ผลลัพธ์ |
|---|---|---|
| การคอมไพล์แบบ JIT | `(compile name)` | ฟังก์ชันในเซสชันที่กำลังรันถูกแทนที่ด้วยโค้ดเนทีฟ |
| การคอมไพล์แบบ AOT | `typl -c src.typl` หรือ `(compile-file "src.typl" "out")` | ไฟล์ปฏิบัติการที่ทำงานได้ด้วยตัวเอง |
| Dump | `(dump "file.typld")` | บันทึกการนิยาม; `typl --image` เริ่มใหม่จากสภาพแวดล้อมเดิม |

## 1. การเตรียมการ

การคอมไพล์ใช้ LLVM 22 หากคุณบิลด์ `typl` ตาม [README.md](../../../README.md) ก็ไม่ต้อง
เตรียมอะไรเพิ่ม

ไฟล์ปฏิบัติการที่สร้างด้วยการคอมไพล์แบบ AOT ถูกลิงก์กับไลบรารีสถิต `libtypelisp_front.a` `typl`
ที่บิลด์แบบ release (รวมถึงที่ติดตั้งด้วย `cargo install`) มีไลบรารีนี้อยู่ภายในตัว จึงไม่ต้อง
เตรียมอะไร ครั้งแรกที่คอมไพล์ มันจะเขียนไลบรารีออกไปที่
`~/.typelisp/lib/<build ID>/` (หรือ `$TYPELISP_HOME/lib/<build ID>/` หากตั้งตัวแปรสภาพแวดล้อม
`TYPELISP_HOME` ไว้) และใช้สำเนานั้นต่อไป `typl --remove-lib` จะลบสำเนานั้น (ถ้าใส่ `--others`
จะลบสำเนาที่เขียนโดย `typl` รุ่นอื่น ถ้าใส่ `--all` จะลบทั้งหมด) `typl` ที่บิลด์แบบ debug
ใช้ไลบรารีใน `target/debug/` ของรีโพซิทอรีที่บิลด์มา หากต้องการใช้ไลบรารีที่วางไว้ที่อื่น
ให้ระบุโฟลเดอร์ของมันด้วย `--lib-dir` ตอนเริ่ม `typl` (หัวข้อ 3.2)
บน macOS การลิงก์ใช้ Xcode Command Line Tools

## 2. การคอมไพล์แบบ JIT

วิธีนี้เปลี่ยนฟังก์ชันที่นิยามไว้แล้วให้เป็นโค้ดเนทีฟทันที

```lisp
(defun fib ((n int)) int
  (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2)))))

(compile fib)
(fib 30)           ; from here on, calls run the compiled code
```

- `name` ไม่ถูกประเมินค่า ให้เขียนชื่อฟังก์ชันตามที่เป็น (ไม่ใช่สตริง) สำหรับเมทอด ให้เขียนพร้อม
  ชื่อชนิด เช่น `(compile point::norm)`
- ฟังก์ชันที่มันเรียกจะถูกคอมไพล์ไปด้วย
- **ฟังก์ชัน generic คอมไพล์ไม่ได้** เพราะมีการสร้างสำเนาสำหรับแต่ละชนิดในแต่ละจุดที่ใช้
  ให้คอมไพล์ฟังก์ชันที่เรียกมันด้วยชนิดที่เจาะจงแทน
- `trace`, `step`, `disassemble`, `compile`, `compile-file` และ `dump` เป็นการดำเนินการของ
  อินเทอร์พรีเตอร์ ดังนั้นฟังก์ชันที่เรียกสิ่งเหล่านี้จึงคอมไพล์ไม่ได้ การพยายามคอมไพล์จะเกิด
  ข้อผิดพลาดที่ระบุเหตุผล

หากต้องการดูผลการคอมไพล์ ให้ใช้ `disassemble`

```lisp
(disassemble fib)          ; the host machine code
(disassemble fib true)     ; LLVM IR
```

## 3. การสร้างไฟล์ปฏิบัติการด้วยการคอมไพล์แบบ AOT

### 3.1 การเขียนโปรแกรม

เป็นจุดเริ่มต้น ให้นิยาม **ฟังก์ชัน `main` ที่ไม่รับอาร์กิวเมนต์**

```lisp
(use std::env::command-line-args)
;; hello.typl
(defun fib ((n int)) int
  (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2)))))

(defun main () ()
  (println "args: ~a" (command-line-args))
  (println "fib(25) = ~a" (fib 25)))

(main)
```

`(main)` ที่ท้ายไฟล์มีไว้เพื่อให้ `main` ถูกเรียกเมื่อคุณรัน
`typl hello.typl` `compile-file` ข้าม `(main)` ตัวสุดท้ายนี้ ดังนั้นไฟล์เดียวกัน
ใช้ได้ทั้งในอินเทอร์พรีเตอร์และกับการคอมไพล์แบบ AOT

### 3.2 การคอมไพล์

จากบรรทัดคำสั่ง ให้ใช้ `typl -c` (`typl --compile` ก็เหมือนกัน)

```sh
$ typl -c hello.typl            # makes hello
$ typl -c hello.typl -o fib     # names the executable fib
$ ./hello a b
args: #(./hello a b)
fib(25) = 75025
```

หากไม่ใส่ `-o` ไฟล์ปฏิบัติการจะตั้งชื่อตามไฟล์ซอร์สโดยตัด `.typl` ออก และวางไว้ในโฟลเดอร์
เดียวกับไฟล์ซอร์ส หากชื่อไฟล์ซอร์สไม่ลงท้ายด้วย `.typl` จำเป็นต้องใส่ `-o` เมื่อใช้ `-c`
(`--compile`) จะระบุ `--image` และ `--feature` ไม่ได้

เมื่อใส่ `--release` ให้ `typl` จะเป็น **บิลด์ release** ซึ่งลบ `eprint`/`eprintln` (เอาต์พุตข้อผิดพลาดมาตรฐานสำหรับตรวจสอบปัญหา; [การพิมพ์](../reference/functions/printing.md)) ออกพร้อมอาร์กิวเมนต์ สิ่งที่ถูกลบยังคงผ่านการตรวจสอบชนิด ดังนั้นถ้ามีข้อผิดพลาดชนิดตรงนั้น การคอมไพล์จะล้มเหลว `--release` เป็นตัวเลือกของ `typl` ทั้งหมด ไม่ได้มีผลแค่กับ `-c` แต่มีผลเหมือนกันเมื่อรันไฟล์ ใน REPL และกับ `typl test` `compile-file` ที่เรียกภายใน `typl` ที่ใส่ `--release` ก็จะเป็นบิลด์ release ด้วย และโค้ดที่ `eval` ภายในไฟล์ปฏิบัติการที่สร้างแบบนั้นก็จะถูกลบ `eprint`/`eprintln` ออกเช่นกัน

```sh
$ typl --release -c hello.typl
$ typl -c hello.typl --release     # เขียนหลัง -c ก็เหมือนกัน
```

`-O0` `-O1` `-O2` และ `-O3` กำหนด**ระดับการปรับให้เหมาะสม** ค่าเริ่มต้นคือ `-O0` ซึ่งไม่ปรับให้เหมาะสม ตั้งแต่ `-O1` ขึ้นไป คอมไพเลอร์จะทำการปรับให้เหมาะสมแบบง่ายก่อน เช่น แทนตัวแปรที่ผูกกับลิเทอรัลเพียงอย่างเดียวด้วยค่าของมัน หรือคำนวณเลขคณิตจำนวนเต็มบนค่าคงที่ไว้ล่วงหน้า แล้วปล่อยส่วนที่เหลือให้การปรับให้เหมาะสมของ LLVM ในระดับชื่อเดียวกัน ไม่ว่าระดับใด ผลการคำนวณก็เหมือนกัน เช่นเดียวกับ `--release` นี่เป็นตัวเลือกของ `typl` ทั้งหมด: นอกจากไฟล์ปฏิบัติการที่ `-c` สร้างแล้ว ยังมีผลกับโค้ดที่ถูกคอมไพล์ระหว่างการรันไฟล์ ใน REPL และใน `typl test` รวมถึง `compile-file` ที่เรียกในที่นั้นด้วย โค้ดที่อินเทอร์พรีเตอร์รันจะไม่ถูกปรับให้เหมาะสม

```sh
$ typl -O2 -c hello.typl
$ typl -c hello.typl -O2     # เขียนหลัง -c ก็เหมือนกัน
```

คุณทำสิ่งเดียวกันได้โดยเรียก `compile-file` จาก REPL หรือจากโปรแกรม

```sh
$ typl
typl> (compile-file "hello.typl" "hello")
typl> :quit
$ ./hello a b
args: #(./hello a b)
fib(25) = 75025
```

หากต้องบิลด์ซ้ำ ๆ คุณสามารถใส่บรรทัดเดียวนี้ในไฟล์แล้วรันด้วย `typl build.typl`

```lisp
;; build.typl
(compile-file "hello.typl" "hello")
```

ชื่อไฟล์ถูกแก้ไขจาก **ไดเรกทอรีปัจจุบันที่เริ่ม `typl`** ไม่ใช่จากตำแหน่งของ `build.typl`

หากต้องการลิงก์ `libtypelisp_front.a` ที่วางไว้ที่อื่นนอกจากที่ `typl` ค้นหา ให้ระบุโฟลเดอร์ของมันด้วย
`--lib-dir` ใช้ได้ทั้งกับ `typl -c` และ `compile-file`

```sh
$ typl --lib-dir ~/lib/typelisp -c hello.typl
$ typl --lib-dir ~/lib/typelisp build.typl
```

หากโฟลเดอร์ที่ระบุไม่มี `libtypelisp_front.a` `typl` จะหยุดพร้อมข้อผิดพลาด ไฟล์นี้ใช้ได้เฉพาะ
กับ `typl` ที่บิลด์มาพร้อมกันเท่านั้น หลังจากบิลด์ `typl` ใหม่ ให้คัดลอกอีกครั้ง

### 3.3 สิ่งที่ไฟล์ที่คอมไพล์แบบ AOT มีได้

- ระดับบนสุดของไฟล์จุดเริ่มต้นมีได้เฉพาะการนิยาม (`defun` `defvar`
  `defparameter` `defconstant` `defmacro` `defsignature` `defstruct` `defenum` `deftype` `deftrait`
  `impl` `defffi`, `(unsafe (def-c-struct ...))`) และ `use` `module` นิพจน์ระดับบนสุด
  เช่น `(println ...)` ไม่อนุญาต ยกเว้น `(main)` ตัวสุดท้าย ให้ใส่งานไว้ใน `main`
- หากไม่มี `main` ที่ไม่รับอาร์กิวเมนต์ การคอมไพล์จะล้มเหลวพร้อมข้อผิดพลาด
- ไฟล์ของโมดูลที่ถูก `use` ก็ถูกคอมไพล์และรวมเป็นไฟล์ปฏิบัติการเดียว
- ไลบรารีที่ระบุด้วย `:library` ใน `defffi` ถูกลิงก์โดยอัตโนมัติ ([FFI สำหรับ C](ffi.md))
- ฟังก์ชันของไลบรารีมาตรฐานทุกตัวใช้กับการคอมไพล์แบบ AOT ได้ `eval` ก็ใช้ได้เช่นกัน แต่
  ตัวตรวจสอบชนิดและอินเทอร์พรีเตอร์จะเข้าไปอยู่ในไฟล์ปฏิบัติการ ทำให้ไฟล์ใหญ่ขึ้นและเริ่มทำงานช้าลง
  โปรแกรมที่ไม่เรียก `eval` จะไม่รวมสิ่งเหล่านี้

### 3.4 พฤติกรรมของไฟล์ปฏิบัติการ

- `(command-line-args)` คืนค่า `Vector<string>` รูปแบบเดียวกัน ไม่ว่าจะรันเป็น
  `typl hello.typl a b` หรือ `./hello a b` สมาชิกตัวแรกคือชื่อโปรแกรม
- กำหนด exit code ด้วย `(exit n)` หาก `main` คืนค่าตามปกติ จะเป็น 0
- เมื่อเกิด `panic` โปรแกรมจะพิมพ์ข้อความและจบด้วยรหัสที่ไม่ใช่ศูนย์

### 3.5 ทรัพยากรที่ไฟล์ปฏิบัติการใช้

`typl -c` มีตัวเลือกที่กำหนดว่าไฟล์ปฏิบัติการใช้ทรัพยากรใดได้บ้างขณะทำงาน

```sh
$ typl --heap-cells 100000 -c hello.typl    # ตรึง arena ของ cons ไว้ที่ 100000 เซลล์
$ typl -c hello.typl --max-memory 64M       # จองหน่วยความจำได้ไม่เกิน 64 MiB
$ typl -c hello.typl --no-cons              # ไม่ใช้เซลล์ cons
```

- `--heap-cells N` ตรึงความจุของ arena ของเซลล์ cons ไว้ที่ `N` เซลล์ arena จะไม่โตเกินนั้น ถ้าการเก็บขยะคืนเซลล์ไม่ได้เลย โปรแกรมจะหยุดด้วยข้อผิดพลาดขณะทำงาน ถ้าไม่ระบุ arena จะเริ่มที่ 65536 เซลล์และโตขึ้นตามต้องการ
- `--max-memory SIZE` จำกัดหน่วยความจำทั้งหมดที่ไฟล์ปฏิบัติการจอง นับทุกอย่าง ได้แก่ arena ของ cons สตริง ค่าอย่างเวกเตอร์และตารางแฮช และหน่วยความจำที่รันไทม์ใช้เอง `SIZE` เป็นจำนวนไบต์ และต่อท้ายด้วย `K` `M` หรือ `G` (1024, 1024² และ 1024³ เท่า) ได้ การจองที่จะเกินขีดจำกัดจะถูกรายงาน และโปรแกรมจบด้วยรหัสออก 1 การจบแบบนี้จับด้วย `catch` ไม่ได้ ถ้าไม่ระบุจะไม่มีขีดจำกัด
- `--no-cons` สร้างไฟล์ปฏิบัติการที่ไม่ใช้เซลล์ cons เลย ไม่มี arena ของ cons โปรแกรมที่ทำสิ่งที่ต้องใช้เซลล์ cons จึงเป็น**ข้อผิดพลาดตอนคอมไพล์** ซึ่งแสดงการดำเนินการนั้นและลำดับฟังก์ชันจาก `main` ที่ไปถึง ต้องใช้เซลล์ cons เมื่อสร้างลิสต์ `Sexpr` (รวมถึงลิสต์ที่ quote และลิสต์ที่สร้างด้วย quasiquote) หรืออาร์กิวเมนต์ `&rest` และเมื่อใช้ `read` `eval` `macroexpand` การดำเนินการกับตัวเลข สตริง เวกเตอร์ ตารางแฮช struct แชนเนล และอื่น ๆ รวมถึง `print`/`println`/`format` ไม่ใช้เลย ระบุร่วมกับ `--heap-cells` ไม่ได้ และเขียนหลัง `-c`

`--max-memory` เขียนหลัง `-c` ส่วน `--heap-cells` เขียนก่อนหรือหลัง `-c` ก็ได้ และจะเป็นความจุของ arena ของ cons ของไฟล์ปฏิบัติการ arena ของ cons ถูกนับรวมในขีดจำกัดหน่วยความจำ ถ้าขีดจำกัดเล็กเกินกว่าจะใส่ arena ได้ โปรแกรมจะหยุดก่อนเริ่ม

### 3.6 คอมไพล์เป็น WebAssembly

เมื่อใส่ `--target wasm32-wasip1` คำสั่ง `typl -c` จะสร้างโมดูล WebAssembly (คำสั่ง WASI preview 1) แทนไฟล์ปฏิบัติการ ถ้าไม่ใส่ `-o` ชื่อจะเป็นชื่อซอร์สที่เปลี่ยน `.typl` เป็น `.wasm`

```sh
$ typl -c hello.typl --target wasm32-wasip1      # ได้ hello.wasm
$ wasmtime hello.wasm a b                        # รันด้วยสภาพแวดล้อมที่รองรับ WASI
args: #(hello.wasm a b)
fib(25) = 75025
```

- `typl` ที่ติดตั้งด้วย `install.sh` ใช้ได้ทันที ส่วนที่ติดตั้งด้วย `cargo install` ต้องเตรียมการก่อน (ซึ่งใช้กับหัวข้อ 3.7 ด้วย) ก่อนอื่นรัน `rustup target add wasm32-wasip1 wasm32-unknown-unknown` ด้วย rustup จากนั้นติดตั้งโดยใส่ `--features wasm` (`cargo install --locked --path . --features wasm`)
  `typl` ที่ติดตั้งโดยไม่ใส่จะไม่มีรันไทม์ WebAssembly และ `--target` จะเป็นข้อผิดพลาด ถ้าใช้ `typl` แบบ debug build ในรีโพสิทอรี ให้รัน `scripts/build-wasm-runtime.sh` ในรีโพสิทอรีแทน
- การลิงก์ใช้ลิงเกอร์ของ toolchain ของ rustup (`rust-lld`) จึงต้องมี rustup ตอนคอมไพล์ด้วย
- โมดูลทำงานเหมือนไฟล์ปฏิบัติการ: เอาต์พุตมาตรฐาน ข้อผิดพลาดมาตรฐาน และรหัสออก, `(command-line-args)`,
  การอ่านเขียนไฟล์, `throw`/`catch`/`panic`, งาน แชนเนล และ `sleep` รวมถึง `eval` ใช้ได้
  งานจะรันทีละงานบนเธรดเดียว อ่านเขียนไฟล์ได้เฉพาะในไดเรกทอรีที่สภาพแวดล้อมเปิดให้โมดูลเห็น
  (ใน wasmtime ระบุด้วย `--dir`)
- โปรแกรมที่ใช้สิ่งที่ WebAssembly ไม่มีจะเป็น**ข้อผิดพลาดตอนคอมไพล์** ข้อความแสดงสิ่งที่ใช้และ
  ลำดับฟังก์ชันจาก `main` ที่ไปถึงสิ่งนั้น สิ่งที่ใช้ไม่ได้คือ: ซ็อกเก็ต (TCP, UDP, Unix domain,
  TLS, การแปลงชื่อ), เธรดของระบบปฏิบัติการ (`Thread`), ฟังก์ชัน C (`defffi`), `get-internal-run-time`, `machine-instance`, `software-version`, `file-author`,
  และ `ed`
- WASI ไม่มีวิธีรู้เขตเวลา จึงไม่รู้เวลาท้องถิ่น `decode-universal-time` และ `encode-universal-time` ที่ละ `zone` รวมถึง `get-decoded-time` จะ panic ตอนรัน ถ้าให้ `zone` ก็ใช้ได้
- `--heap-cells`, `--max-memory`, `--no-cons`, `-O<N>` และ `--release` ใช้ได้เหมือนกับไฟล์ปฏิบัติการ

### 3.7 รันในเบราว์เซอร์หรือ Node.js

เมื่อใส่ `--target wasm32-unknown-unknown` คำสั่ง `typl -c` จะสร้างโมดูล WebAssembly สำหรับโหลดและรันจาก JavaScript ข้างโมดูล (`hello.wasm`) ในโฟลเดอร์เดียวกันจะมี JavaScript ที่โหลดและรันโมดูลนั้น (`hello.mjs`) การเตรียมการเหมือนหัวข้อ 3.6

```sh
$ typl -c hello.typl --target wasm32-unknown-unknown   # ได้ hello.wasm และ hello.mjs
$ node hello.mjs                                       # รันด้วย Node.js
args: #()
fib(25) = 75025
```

จาก JavaScript อื่น ให้เรียก `run` ของ `hello.mjs` ฟังก์ชัน `write` จะได้รับเอาต์พุตเป็นข้อความ (`fd` เป็น 1 สำหรับเอาต์พุตมาตรฐาน และ 2 สำหรับข้อผิดพลาดมาตรฐาน) ค่าของ `run` คือรหัสออก

```js
import { run } from './hello.mjs';
const code = await run({ write: (fd, text) => { /* เช่น แสดงบนหน้าเว็บ */ } });
```

- ถ้าไม่ส่ง `write` Node.js จะเขียนไปที่เอาต์พุตมาตรฐานและข้อผิดพลาดมาตรฐาน ส่วนเบราว์เซอร์จะเขียนลงคอนโซลทีละบรรทัด
- ในเบราว์เซอร์ ให้เสิร์ฟ `hello.wasm` ผ่าน HTTP จากที่เดียวกับ `hello.mjs` (โหลดจาก `file://` ไม่ได้)
- `sleep` รอด้วย `Atomics.wait` ซึ่งเบราว์เซอร์อนุญาตเฉพาะภายใน Worker ของหน้าที่แยก cross-origin เท่านั้น จึงควรรันโปรแกรมที่ใช้ `sleep` ใน Worker
- เวลาท้องถิ่น (`decode-universal-time` ที่ละ `zone` เป็นต้น) คำนวณจากเขตเวลาที่ `Date` ของ JavaScript รายงาน
- นอกจากสิ่งที่ใช้ไม่ได้ในหัวข้อ 3.6 แล้ว การจัดการไฟล์และไดเรกทอรี ตัวแปรสภาพแวดล้อม `(command-line-args)` ไดเรกทอรีหลัก และ `dribble` เป็น**ข้อผิดพลาดตอนคอมไพล์** อินพุตมาตรฐานถูกอ่านเป็นว่าง

### 3.8 คอมไพล์สำหรับไมโครคอนโทรลเลอร์ (Cortex-M)

เมื่อใส่ `--target thumbv7em-none-eabihf` คำสั่ง `typl -c` จะสร้างไฟล์ปฏิบัติการ (ELF) สำหรับบอร์ด Cortex-M4F หรือ M7 ที่ไม่มีระบบปฏิบัติการ ถ้าไม่ใส่ `-o` ชื่อจะเป็นชื่อซอร์สที่เปลี่ยน `.typl` เป็น `.elf`

```sh
$ typl -c hello.typl --target thumbv7em-none-eabihf          # สร้าง hello.elf
$ qemu-system-arm -M mps2-an386 -nographic \
    -semihosting-config enable=on,target=native -kernel hello.elf   # รันบน Cortex-M4 ของ QEMU
```

- `typl` ที่ติดตั้งด้วย `install.sh` ใช้ได้ทันที ถ้าติดตั้งด้วย `cargo install` ให้รัน `rustup target add thumbv7em-none-eabihf` แล้วติดตั้งพร้อม `--features embedded` (ทั้งสองอย่างใช้ `--features wasm,embedded`) ถ้าใช้ `typl` ที่เป็นบิลด์ดีบักในรีโพสิทอรี ให้รัน `scripts/build-embedded-runtime.sh` การลิงก์ใช้ลิงเกอร์ของ toolchain ของ rustup
- ระบุหน่วยความจำของบอร์ดด้วย `--linker-script FILE` เขียนแบบเดียวกับ `memory.x` ของ `cortex-m-rt` คือที่อยู่และขนาดของ FLASH และ RAM บรรทัดอย่าง `_typelisp_stack_size = 32K;` กำหนดว่าสแตกใช้ RAM เท่าใด (ถ้าไม่เขียนคือ 64KiB) ส่วนที่เหลือของ RAM คือฮีป ถ้าไม่ใส่ตัวเลือกนี้จะใช้การจัดวางของ `mps2-an386` ใน QEMU

  ```
  MEMORY
  {
    FLASH : ORIGIN = 0x08000000, LENGTH = 512K
    RAM : ORIGIN = 0x20000000, LENGTH = 128K
  }
  _typelisp_stack_size = 16K;
  ```

- `--board-functions` เลือกว่าใครให้เอาต์พุต อินพุต การจบโปรแกรม และนาฬิกา (ฟังก์ชันของบอร์ด)
  - `semihosting` (ค่าเริ่มต้น): ให้ผ่าน semihosting สำหรับรันใน QEMU (`-semihosting-config enable=on`) หรือดีบักเกอร์
  - `c`: บอร์ดให้เป็นฟังก์ชัน C ส่งออบเจ็กต์หรือไลบรารีแบบสแตติกที่นิยามฟังก์ชันด้านล่างด้วย `--link FILE` (`--link` ใส่ซ้ำได้ ไลบรารีของผู้ผลิตที่ `defffi` เรียกก็ส่งแบบเดียวกัน)

  ```c
  void     typelisp_host_write(int32_t fd, const uint8_t *p, size_t len); // fd 1 คือเอาต์พุตมาตรฐาน 2 คือข้อผิดพลาดมาตรฐาน
  size_t   typelisp_host_read(int32_t fd, uint8_t *p, size_t len);        // fd 0 จำนวนไบต์ที่อ่าน 0 เมื่อจบ
  void     typelisp_host_exit(int32_t code);                              // ไม่กลับมา
  uint64_t typelisp_host_now_us(void);                                    // ไมโครวินาทีของนาฬิกาที่ไม่ย้อนกลับ
  int64_t  typelisp_host_unix_us(void);                                   // ไมโครวินาทีตั้งแต่ 1970-01-01
  void     typelisp_host_sleep_us(uint64_t us);                           // รอ us ไมโครวินาที
  ```

- รันไทม์เริ่มโปรแกรม (ตารางเวกเตอร์และการเตรียม RAM) และจัดสรรหน่วยความจำ เมื่อเกิด HardFault หรืออินเทอร์รัปต์ที่ไม่มีตัวจัดการ โปรแกรมจะจบด้วยรหัสออกเดียวกับ panic (1)
- `throw`/`catch`/`panic` จำนวนเต็มขนาดใหญ่ เศษส่วน และทศนิยม รวมถึงงาน แชนเนล และ `sleep` ทำงานเหมือนในไฟล์ปฏิบัติการ งานรันสลับกันบนคอร์เดียว ใช้ฟังก์ชัน C (`defffi`) ได้
- โปรแกรมที่ใช้สิ่งที่บอร์ดไม่มีเป็น**ข้อผิดพลาดตอนคอมไพล์** นอกจากสิ่งที่ใช้ไม่ได้ในหัวข้อ 3.7 แล้วยังมี `eval` และ `macroexpand` เวลาท้องถิ่นไม่ทราบ (เหมือนหัวข้อ 3.6)
- อารีนาของ cons เริ่มที่ 1024 เซลล์และขยายเมื่อไม่พอ `--heap-cells`, `--max-memory`, `--no-cons`, `-O<N>` และ `--release` ใช้ได้ตามเดิม

## 4. Dump

คุณบันทึกการนิยามของเซสชันปัจจุบันลงในไฟล์เดียวและเริ่มจากไฟล์นั้นในครั้งถัดไปได้

```sh
$ typl
typl> (defun sq ((n i32)) i32 (* n n))
typl> (compile sq)
true
typl> (dump "session.typld")
true
typl> :quit
$ typl --image session.typld
typl> (sq 9)
81
```

ใช้ได้กับการรันไฟล์เช่นกัน เช่น `typl --image session.typld prog.typl`

- สิ่งที่ถูกบันทึกคือ **การนิยาม** นิพจน์ที่ประเมินค่าในเซสชันไม่ถูกบันทึก
- ฟังก์ชันที่คุณ `compile` ไว้จะถูกบันทึกในรูปที่คอมไพล์แล้ว
- ตัวแปรโกลบอลถูกกู้คืนโดย **รันตัวกำหนดค่าเริ่มต้นของมันอีกครั้ง** ไม่ใช่ด้วยค่าที่มันมี
  ตอนเขียน dump
- dump ไม่สามารถโหลดด้วย `typl` คนละรุ่นกับรุ่นที่เขียนมัน (เป็นข้อผิดพลาด)

หากคุณรันไฟล์และ `(dump ...)` จากไฟล์นั้น การนิยามของไฟล์นั้นจะอยู่ในโมดูลที่ตั้งชื่อตาม
ไฟล์ ฟังก์ชันที่นิยามใน `dp.typl` มีชื่อ `dp::sq` และการเรียกจากไฟล์อื่นต้องใช้
`pub` ([โมดูลและการจัดวางไฟล์](modules.md))

## 5. เกี่ยวกับไฟล์โมดูลที่คอมไพล์แล้ว

ไม่มีรูปแบบอย่าง `.fasl` ของ Common Lisp สำหรับเขียนผลการคอมไพล์ของแต่ละโมดูลออกเป็น
ไฟล์ `compile-file` สร้างไฟล์ปฏิบัติการโดยตรงจากซอร์ส ไม่มีไฟล์ระหว่างทางหลงเหลือ
