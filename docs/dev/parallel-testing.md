# 並列テスト実行

テストスイートを並列に流せるようにした作業の記録。直列実行の
`scripts/test-serial.sh` は、決定論的な再実行のために残してある。

## 背景

このリポジトリのテストは長く直列でしか流せなかった。LLVM を使うテストを
並列に走らせると稀に SIGSEGV し、その原因は「プロセス間でもスレッド間でも
共有 Context が衝突する」ものとされていた。

別リポジトリでの最小再現（共有 Context＋並列で SIGSEGV、直列または独立
Context で通過）と typelisp 側の調査で、次のことが分かった。

- 別プロセス同士はアドレス空間が別で、LLVM の Context を共有しない。よって
  「プロセス間の衝突」は誤診で、真因は 1 本のテスト実行ファイルの中の
  スレッド同士だった。
- typelisp は共有 Context を `COMPILE_LOCK`（`src/compile/mod.rs`）で守って
  いたが、typelisp 自身で書かれたコンパイラ（自己ホスト。コードベース内の
  呼称は「島」。以下、自前コンパイラ）が駆動する IR 構築の区間はビルトイン
  呼び出しごとの細粒度ロックしかなく、スレッド間で IR 構築が混ざっていた。
- 全体を 1 ガードで包めなかった理由は `Mutex` の非再入性で、自前コンパイラの
  ビルトインが内側で同じロックを取るため、外側で取ると詰んだ。

## 方針

`COMPILE_LOCK` を再入可能にし、コンパイル全体を 1 ガードで直列化する。
保持スレッドからの再取得は no-op としてネストし、外側のガードだけが他
スレッドを排除する。内側の取得を握る既存の呼び出し側は変えずに済む。

## 変更

実装は `src/compile` の中に収まる。

- `mod.rs`：`CompileGuard` が所有ガードとネストを区別する。再入取得は
  `MutexGuard` を持たず、drop してもスレッドローカルの保持印を消さない。
- 全体ガード化：`driver.rs` の `compile_scc` と `disassemble_function`、
  `aot.rs` の `compile_file`、`bootstrap.rs` の自前コンパイラ生成、
  `prelude_bootstrap.rs` の prelude 生成、`dump.rs` のセッション生成。
  いずれもモジュール生成から検証・JIT／オブジェクト出力・破棄までを
  1 ガードで包み、内側の取得はネストする。
- `llvm_builtins.rs`：ロックの説明を更新し、ハンドル登録の teardown を
  直接の取得に単純化した（再入で安全になったため）。
- 回帰テスト：再入の単体テスト（`mod.rs` の tests）と、8 スレッドで別
  セッションから JIT コンパイルする `tests/compile_parallel_test.rs`。

ついでに直した既存の問題。

- `disassemble_function` がモジュールをロック解放後に drop していた。
  `~Module` は共有 Context の表を触るため、ガード内で破棄する形に直した。
- `tests/compiled_unwind_test.rs` の 3 テストがプロセス全体の
  `CLEANUP_RUNS` に厳密な差分を assert しており、並列で競合した。
  専用の Mutex で直列化した（`sched_threads_test.rs` の前例に倣う）。

## `scripts/test-parallel.sh`

`test-serial.sh` と同じ対象（`--lib` と `tests/*.rs` の各ターゲット）を
`xargs -P` で流す。使い方は直列版と同じで、`-j N`（`TEST_JOBS`、既定 6）
が同時実行するバイナリ数の上限、`--` 以降は各 `cargo test` へ転送する
（中身に空白を含めないこと）。

設計の要点。

- 親は対象の一覧を `xargs` に渡すだけで、各ターゲットは `--worker` 付きの
  自己再帰で実行する。関数 export も引数の再引用も要らない。
- 判定は標準出力のパースではなく `.rc` ファイルで行う。各ワーカーは終了
  コードを `target/test-parallel-logs/<target>.rc` に書き、親はそれを集計
  する。`.rc` の無いターゲットは結果無しとして失敗に数える。
- ターゲットごとに 3600 秒（`TEST_TIMEOUT`）のタイムアウトと個別ログが
  付く。失敗とタイムアウトのターゲットは、最後にログの末尾 200 行を標準出力へ
  出す（CI ではジョブが終わるとログのファイルが消えるため）。AOT テスト用の staticlib ビルドと `timeout` の名前解決は直列版と
  同じ。`bash` 3.2（macOS 付属）で動く書き方にしている。
- `--shard` は `test-each.sh` と同じ分割規則で、リリースは 4 分割で流す
 （`release.yml`）。ディスクの小さい環境用の `test-each.sh` は残してある。

## 検証

`test-parallel.sh` で全 162 ターゲットを実行し、sandbox の OS 制限で赤に
なる 4 件（TCP/TLS の bind、所有者名の解決）以外は緑を確認した。赤の 4 件
は制限の無い実行で緑になることを別途確認した。生成物（自前コンパイラ・prelude の
ビットコード）はバイト一致のテストが通っており、再構成で変わっていない。

## 注意

- 同一スコープで `let _guard` を二重に束縛すると、内側の束縛ができた時点で
  外側が drop される。外側が所有ガードだった場合、ロックは外れているのに
  手元にはネスト扱いの no-op ガードだけが残る。全体ガードの下では二重取得
  を書かず、書くとしても別スコープにする。
- `COMPILE_LOCK` を握ったまま panic すると汚染し、以降の `.unwrap()` 取得
  が連鎖的に落ちる。並列実行で多数が `PoisonError` になったら最初の
  panic を見る（`handoff.md` の落とし穴にもある通り）。

## 残件

なし。シリアルの全走は sandbox の OS 制限で赤の 4 件以外は緑を確認し、
既定の実行は並列（`test-parallel.sh`、リリースは `--shard` 分割）に切り替えた。
