# 64bit 幅の整数型を言語から消す計画

作成: 2026-08-31。状態: **未着手**（調査のみ）。
TODO.md の「未修正のバグ」5 件のうち最後の 1 件（#2 `i64` の切り詰め）の実施計画。

## 0. なぜ

実行時の値はタグ付き 1 語で、下位 3bit がタグ——即値の整数に残るのは 61bit しかない。
`i64` という**タグに干渉する幅の型**を言語が持っている限り、上位 3bit を落とす経路が
どこかに残り続ける。多くの Lisp が整数を 1 種類にしてタグ用の bit を確保したのと同じ理由で、
**64bit 幅の型を作らない**のが正しい形——これがユーザ判断（2026-08-31）。

消すのは幅が 64bit のものだけ: **`i64` / `u64` / `isize` / `usize`**。
`u32`（最大 4294967295）は 61bit の即値に収まるので残す。

## 1. 決定事項（2026-08-31、ユーザ判断）

1. `i32` より大きい数は **`bignum`** を使う。
2. `Sexpr` の `Int` ペイロードは **`i32`**。`i32` の範囲を超えるリテラルは `bignum` に読む。
3. `time` / `date` 系の組み込みは **専用の構造体**を返す（現在 `i64` を返している）。
4. **引数の型と名前を一致させる**。`i32` を受け取る関数の名前に `i64` が入っているのは禁止
   （島の `const-i64` が該当）。
5. **移行措置は要らない**。言語ユーザーはまだ居ないので単純に削除する。
6. **演算は型の幅と符号のとおりに行う**（§3.7）。型名は「`i32` = 32bit を符号付きとして
   扱う」「`u32` = 32bit を符号なしとして扱う」以上の意味を持たない。今はインタプリタも
   コンパイラも 64bit で計算しているので、`i32` の変数が 2^31 を超える値を静かに持てる。
7. **`f32` は本物の binary32 にする**（§3.8）。幅が違うことが `f32` と `f64` の
   存在理由なので、同じ表現・同じ精度で済ませてよいはずがない。
8. **残る型は全部、型名どおりのビット数にする**（2026-08-31、ユーザ判断）。
   削除するのは 64bit 幅の 4 つ（`i64`/`u64`/`isize`/`usize`）だけ。残る
   `i8`/`i16`/`i32`/`u8`/`u16`/`u32`/`f32`/`f64` は**例外なく**名乗ったビット数で
   振る舞う——「狭い幅はデータを名指すためのもので、計算する型ではない」という
   [functions.md](../functions.md) §1b の方針は、これで全面的に撤回になる。

**なぜ `f64` は消さなくてよいか（`i64` との違い）**: `f64` の値は**ヒープの箱**
（`BoxedObj::Float(f64)`）で、タグが付くのは箱の id のほう。だから 64bit の
ビットパターンは 1 bit も失われない。コンパイル済みコードのローカルでも
`Repr::Float` は**タグの付かない生の語**（`f64::to_bits` をそのまま `i64` に）なので同じ。
61bit の即値に触れるのはリテラルを core IR で運ぶときだけで、そこは既に
32bit ずつの半分に割ってある（§3.1）。`i64` は逆に**即値そのもの**なので、
3bit のタグに直接ぶつかる——これが片方だけ消える理由。

### 1.1 `isize`/`usize` も消す（2026-08-31、確認済み）

名前にビット数が入っていないので残してよさそうに見えるが、3 つ問題がある。

1. **名乗っているのは「ポインタ幅」で、このターゲットでは 64bit。** つまり `i64` と
   まったく同じタグ干渉の罠を、**名前が警告してくれない形で**残すことになる。
   `i64` はまだ名前が危険を予告するぶんマシ。
2. **この言語にユーザーが握れるポインタが無い。** 値はターゲットに関わらず 3bit タグ付きの
   語で、ヒープの id は `BoxId`/`StrId` ＝ **`u32`**。添字も長さも `i32`
   （`length` → `i32`、`ref` → `(string, i32)`）。`usize` が名指すべき
   「オブジェクトを添字できる幅」は、この言語では 32bit であって 64bit ではない。
3. **実装にポインタ幅を見ている箇所が 1 つも無い。** `isize`/`usize` は
   `INT_TYPE_NAMES` に名前が並んでいるだけで、Rust から名前を借りただけの存在。
   使っている typelisp コードも無い（prelude のカタログ行と `numeric_widths_test` のみ）。

残すとしたら定義は「`i32`/`u32` の別名」にしかならないが、それは**同じ概念を 2 通りに
綴る**ことで、2026-08-04 に一度事故を起こした形（[type_key.rs](../../crates/typelisp-front/src/type_key.rs) の冒頭が戒めている）。

## 3. 設計上の分かれ道（各項に推奨あり）

削除に伴って「`i64` が無いと書けないもの」が 6 つある。単なる置換では済まないのはここだけ。

### 3.1 core IR の 32bit 半分（`(int HI LO)` / `(float HI LO)`）

今は `bits >> 32` と `bits & 0xFFFF_FFFF` を `Value::Int` で運んでいる。下半分は
最大 4294967295 で、**`i32` には収まらない**（`sexpr-int` が `i32` を返すようになるため）。

**推奨**: 両半分を**符号付き `i32` のビットパターン**として運ぶ（`as i32` / `as u32 as i32`）。
島の再構成は上位の埋めを消すために定数 32 だけで書ける:

```lisp
(build-or (build-shl (const-word hi) (const-word 32))
          (build-lshr (build-shl (const-word lo) (const-word 32)) (const-word 32)))
```

`0xFFFF_FFFF` というマスク定数自体が 32bit を超えるので、`build-and` ではなく
**シフト 2 回**で下 32bit を残す。ここは実装の細部だが、外すと float リテラルが静かに壊れる。

### 3.2 島の `const-i64`（88 箇所）

`i32` を受け取り **LLVM の 64bit 定数**を作る関数。生成されるコードの語幅は
ソース言語の型とは無関係に 64bit なので、関数自体は残る。決定事項 4 により改名が要る。

**推奨**: **`const-word`**。「生成コードの 1 語」を作る、という意味に名前を合わせる。
呼び出し側は全て小さい値（タグマスク・添字・0/1/-1）なので、`i32` 引数で足りる
——64bit 幅の定数が要る 2 箇所（`compile-int` / `compile-float`）は §3.1 のとおり
既に半分ずつ組み立てている。

### 3.3 `most-positive-fixnum` / `most-negative-fixnum`

今は `i64` の上下限（`9223372036854775807`）。

**推奨**: **`i32` の上下限**（`2147483647` / `-2147483648`）。固定幅整数型が `i32` だけに
なるのだから、「fixnum の端」はそこ。今の値はそもそも実行時の即値（61bit）とも
一致しておらず、消すことで嘘が 1 つ減る。

### 3.4 `sxhash` と FNV-32（`*fnv-mask*` = 4294967295）

`Hash` トレイトの `sxhash` は `i64` を返し、FNV-32 の丸めに 32bit のマスクを使っている。
マスクの値が `i32` に入らない。

**推奨**: `sxhash` の戻り型を **`i32`** にし、各ステップのマスクを `*sxhash-mask*`
（1073741823 = 2^30-1）に統一する（最終マスクと同じ値なので定数が 1 つ減る）。
`sxhash` の契約は「等しい値は等しくハッシュする」だけなので、分布が変わっても仕様は満たす。

今の FNV-32 が動いているのは「整数演算が内部では 64bit のまま」という緩さのおかげでも
ある。§3.7 でその緩さ自体を潰すので、マスクの付け替えは**必須**であって好みではない。

### 3.5 `BitVector`

`Vector<i64>` に 32bit ずつ詰めている（「タグの端に近寄らないため」と注記がある）。
語が `i32` になると、最後の語のマスク `(- (ash 1 used) 1)` が `used = 32` で溢れる。

**推奨**: **1 語 31bit** に詰め替える。`(ash 1 31)` を書かずに済み、符号 bit にも触らない。
語数の計算（`(/ (+ n 31) 32)` → `(/ (+ n 30) 31)`）と添字（`(/ i 32)` / `(mod i 32)`）が
連動して変わる。`*bitvector-word-mask*` は消える。

### 3.6 時刻（決定事項 3）

`get-universal-time` は 1900 年起点の秒で、2026 年は約 39.8 億——**`i32` に入らない**。
`get-internal-real-time` はマイクロ秒なので約 35 分で溢れる。どちらも構造体にする。

**推奨**:

```lisp
(pub defstruct universal-time (pub day i32) (pub second i32))   ; 1900-01-01 からの日数と、その日の中の秒
(pub defstruct internal-time  (pub second i32) (pub microsecond i32))
```

- `universal-time` を「日 + 日内秒」に割るのは、`decode-universal-time` が最初に
  やっている計算そのものだから——構造体にした時点で除算が消える。`encode-universal-time`
  も `days-from-civil` の結果をそのまま入れるだけになる。比較は 2 段の辞書順。
- `file-modified-date` / `file-write-date` も `Result<universal-time, FileError>` に。
- `internal-time-units-per-second` は `microsecond` フィールドの単位を言う定数として
  `i32` で残す（1000000）。`time` マクロの引き算は 2 フィールドの減算になる。

### 3.7 演算は型の幅と符号のとおりに行う（決定事項 6）

**型名は幅と符号そのもの**——`i32` は「32bit を符号付きとして扱う」、`u32` は
「32bit を符号なしとして扱う」以上の意味を持たない（2026-08-31、ユーザ判断）。
今はどちらの実行系もそう扱っていない。

- インタプリタ: `eval_int_builtin` が `Value::Int`（`i64`）同士で `a + b` を計算する。
  整数型が 1 本の関数を共有していて、幅も符号もどこにも入っていない。
- 島: `build-add`/`build-sub`/`build-mul` を 64bit の語に発行する。除算は
  `rt_i64_div`/`rt_i64_mod`、`logcount`/`integer-length` は `rt_i64_*` で 64 が基準。

だから今は `(the i32 2000000000)` 同士を足すと 4000000000 になり、`u32` が正しく
見えるのも「64bit で計算しているから」でしかない。`i64` を消してもこの緩さは残るので、
同じ作業で潰す。

**正規化の規則は 1 つで足りる。** 幅 `w`、符号あり／なしに対して:

```
signed   w:  (ashr (shl x (64-w)) (64-w))
unsigned w:  (lshr (shl x (64-w)) (64-w))
```

`w = 32` でも `0xFFFF_FFFF` のような 32bit 超の定数が要らない（シフト量は常に小さい）ので、
§3.1/§3.2 の「大きい定数を書かない」制約とも噛み合う。インタプリタ側は同じ規則を
Rust の `as i32` / `as u32` で書ける。

**必要な変更**:

- **インタプリタ**: `eval_int_builtin` に受け手の**幅と符号**を渡す。ディスパッチ地点
  （`Interp::eval_builtin_method`）は既に型名を持っている（`is_int_receiver(type_name)`）
  ので、`INT_TYPE_NAMES` から `(幅, 符号)` を引く表を 1 つ足せばよい。
  `+`/`-`/`*`/ビット演算は計算後に正規化、`/`/`mod`/比較/シフトは符号で分岐する。
- **島**: `+`/`-`/`*`/ビット演算は**下位 `w` bit が 64bit 演算の結果と一致する**ので、
  結果に上の正規化を掛けるだけでよい。`/`/`mod`/比較/右シフトは、両オペランドが
  正規形なら**符号によって命令が変わる**（`sdiv`/`udiv`、`srem`/`urem`、
  `icmp slt`/`icmp ult`、`ashr`/`lshr`）。左シフトは結果の正規化が要り、シフト量の
  クランプ境界が 64 → `w` になる。`compile-assoc` は受け手の型名を文字列で持っている
  ので、分岐に必要な情報はその場にある。
- `rt_i64_div`/`rt_i64_mod`/`rt_i64_logcount`/`rt_i64_integer_length` は幅と符号の
  ぶんだけ要る。名前は受け取る型に合わせる（決定事項 4）。オーバーフロー条件は
  符号付きの `MIN / -1` だけで、符号なしには無い。`integer-length` の基準も幅ごと。

**`u32` は残る。** 32bit 符号なしとして扱えばよく、`bignum` に追い出す理由は無い。
`i8`/`i16`/`u8`/`u16` も同じ規則の `w` 違いなので、**同じ 1 つの仕組みで一緒に正確になる**
——今日はどれも幅の注釈でしかないが、この作業のあとは名前のとおりに振る舞う。
消えるのは 64bit 幅の 4 つ（`i64`/`u64`/`isize`/`usize`）だけで、残るのは
`i8`/`i16`/`i32`/`u8`/`u16`/`u32` の 6 つ。

### 3.8 `f32` は本物の binary32 にする（監査結果 + 決定事項 7）

「静的な型は幅を名乗るのに、実行時はその幅で扱わない」は整数だけの話ではない。
**これは見落としではなく、明文化された方針**だった——[functions.md](../functions.md) §1b:

> **幅は静的な区別だけで、実行時表現は共通**——整数はどの型でも `i64`、浮動小数点は
> どちらも `f64` なので、`u8` の算術は 8 ビットで巻き戻らず、`f32` の算術は f32 精度に
> 丸めない。（…）狭い幅が要るのはデータを*名指す*ためで、計算する型としてではない。

決定事項 6 はこの方針の**整数側を撤回**するもの。同じ方針の残りは 1 つ:

**`f32` は `f64` のラベルでしかない。**

- `Value::Float` は `f64` 1 種類（`Repr::Float` の doc も「`f64`」と書いてある）。
- `eval_float_builtin` は `f64` で計算する。`f32` 用の分岐は無い。
- 島も同じ: `float-receiver-type?` が `f32`/`f64` を 1 つに畳み、`build-fadd` ほかは
  すべて `double`。`f32` 固有の命令は 1 つも無い。
- `as`/`try-as` の `f64`↔`f32` は**純粋な付け替え**（`Checker::check_as` の相対枝）。
  丸めないので `try-as` は常に `some`。`called_width` も両方 `f64` に潰す。

**決定（2026-08-31、ユーザ判断）: `f32` は本物の binary32 にする。**
幅が違うことが `f32` と `f64` の存在理由そのものなのだから、同じであってよいはずがない。
`f32` を消す選択肢は無い——`i64` を消す理由（タグへの干渉）は `f32` には当てはまらない
（`f32` は*狭い*ので表現上の危険が無い）。

規則は §3.7 と同じ形——「演算のあと型の幅に落とす」の浮動小数点版が「**binary32 に丸める**」:

```
f32 の正規化:  Rust なら `x as f32 as f64` / LLVM なら `fptrunc double→float` → `fpext float→double`
```

格納は `f64` のビットのままでよい。どの binary32 の値も binary64 で正確に表せるので、
整数を 64bit の語に符号拡張して置くのと**まったく同じ形**になる（表現は広く、演算は名乗った幅）。

**必要な変更**:

- `eval_float_builtin` に受け手の幅を渡し、`f32` なら各演算のあと `as f32 as f64` で丸める。
  `float_unary`（`sqrt`/`floor`/…）と `expt` も同じ。
- 島: `float-receiver-type?` が `f32`/`f64` を 1 つに畳んでいるのをやめ、`f32` の演算は
  `fptrunc`/`fpext` で挟む。比較は丸めた値どうしで行う。
- `as`/`try-as` の `f64`↔`f32` を**付け替えから本物の変換へ**。`f64`→`f32` は丸め
  （`try-as` は値が binary32 で表せるときだけ `some`）、`f32`→`f64` は常に正確。
  `called_width` の「両方 `f64`」も消える。
- 浮動小数点リテラル: `(the f32 0.1)` は binary32 に丸めた値になる。core IR の
  `(float HI LO)` は f64 のビットのままでよい（丸めた結果を入れる）。

**波及**（§3.7 と共通）:

- [functions.md](../functions.md) §1b の「幅は静的な区別だけで、実行時表現は共通」の段落は
  **丸ごと書き換え**。
- 「CL の派生カタログ（`abs`/`signum`/`gcd`/`lcm`/`isqrt`/`expt` と述語）は
  `i32`/`i64`/`f64`/`bignum`/`ratio` のまま」という線引きも、その理由
  （「狭い幅は計算する型ではない」）が消えるので引き直しになる。
- `as`/`try-as` の同族間が付け替えでなくなるので、`as_conversion_test` の
  「常に `some`」系のテストは**意味が変わる**（削除ではなく書き換え）。

## 4. その他の機械的な置換

- ストリームの不透明ハンドル（`registry.rs` の `let h = Type::I64`、prelude の
  `file-stream` ほか 5 つの `defstruct`）→ `i32`。
- `ByteInput`/`ByteOutput` の `Item` と `stream-read-byte`/`stream-write-byte` → `i32`
  （バイトは 0..255）。
- `read-from-string` の `start` と返り位置（`cons-cell<Option<Sexpr>, i64>`）→ `i32`。
- `*print-right-margin*` ほか `*print-*` の整数変数 → `i32`。
- `direction-input`/`-output`/`-append` → `i32`。
- prelude の `i64` メソッドブロック（`abs`/`signum`/`rem`/`gcd`/`lcm`/述語/`logeqv` 系/
  `floor-div` 系/`isqrt`/`expt`/`Eq`/`Ord`/`Add`..`Rem`/`Bits`/`Number`/`Hash`）→ 削除。
- `u64`/`isize`/`usize` も同じ扱いで削除（`Eq`/`Ord`/`Hash` の 1 行ずつ）。
- 読み取り: `reader.rs` の `i64::from_str_radix` / `parse::<i64>` / `i64::try_from` 4 箇所を
  `i32` に。

## 5. 成果物と版

- ダンプと FASL に型名が載るので**版を上げる**。
- 島の SOURCE を触る（§3.1/§3.2）ので**再生成は 2 回**（自己ホストの不動点）。
  prelude のビットコードも再生成。
- `NATIVE_LOWERED_PRIMITIVES` / `INT_TYPE_NAMES` は 10 → 6 になる。
  この 2 つと registry・インタプリタ・bridge・島の分岐が**同じ順序で同じ名前**を
  数えている前提は変わらないので、4 箇所を同時に減らす。

## 6. リスク

- **`format` の整数ディスパッチ**が `i32`/`i64` の両方を試す形になっている
  （`Checker::format_call_owners`、`~/name/` の「整数だけは値から区別できない」）。
  `i64` が消えれば**この曖昧さ自体が無くなる**——先に消してから、その分岐を削る。
- §3.7 は**この計画の中で一番広く触る**（整数演算の経路すべて）。`i64` の削除と
  同じコミットに入れないと、「`i32` と名乗るのに 64bit で計算される」状態が残る。
- テストの 819 箇所は大半が機械的だが、`as_conversion_test` のように
  「`i32` と `i64` を跨ぐ」ことそのものを試すテストは**削除**になる
  （`Checker::check_as` の幅の付け替えと `retype_option` も同時に消える）。
