# 名前解決の一本化 — 実装計画

作成: 2026-10-11

## 1. 決まったこと（2026-10-11、ユーザー決定）

- `defun` で定義した関数も、`impl` に書いたメソッドも、名前の解決は 1 箇所で行い、
  どこからでも同じ方法で解決する。
- 関数と変数の名前空間は分けない。1 つの名前に結び付く値は、関数か変数かに関係なく 1 つだけ。
  CL の `symbol-function` と `symbol-value` のように 2 つの値を持つことはない。
- メソッドは第 1 引数の型だけから探す。第 2 引数の型からは探さない。
- `push` は第 1 引数が列、第 2 引数が足す要素（`(push v x)`）。CL の順序（`(push x v)`）で
  書いている呼び出しは引数を入れ替える。
- `format` の `~/name/` は、これが済んでから、同じ解決の上に作り直す（§5）。
- マクロも関数・変数と同じ名前空間に入る（2026-10-12、ユーザー決定）。同じモジュールで
  マクロと関数（または変数）に同じ名前は使えない。別のモジュールなら近い方が勝つ。

経緯: `~/name/` に組み込み型の値を渡すために関数も呼べるようにしようとしたとき、
「`~/name/` 専用の表」や「関数を呼ぶメソッドを型に足す」案が出た。どちらも解決の仕組みを
もう 1 つ作るもので、後者は無関係な呼び出しの意味まで変えた。解決が場所ごとに別々なのが元の問題。

## 2. 今の解決（2026-10-11 時点）

| 場所 | 順序 |
|---|---|
| 呼び出し `(f a ...)`（`check_list`） | ローカル → マクロ → 構成子 → `use` した静的メソッド → 第 1 引数の型のメソッド → 第 2 引数の型のメソッド → 関数 → グローバル変数 |
| 値 `f`（`check` の `Symbol`） | ローカル → グローバル変数 → 関数 → メソッド（期待型の第 1 引数の型） |
| パスの呼び出し `(a::b ...)`（`check_path_call`） | マクロ → 関数 → 型の変種 → 型の静的メソッド |
| パスの値 `a::b`（`check` の `Path`） | フィールド → グローバル変数 → 関数 |
| `compile` / `trace` / `untrace` / `disassemble`（`resolve_callable`） | 素の名前は関数かマクロ、パスはメソッド → 関数 |
| `documentation` / `ed` / `source-file`（`resolve_definition`） | 変数 → 関数 → 型 → 型の別名 → トレイト → マクロ |
| `use`（`check_use`） | 関数 → 型 → … |
| `~/name/`（`note_format_calls`、実行時は `Interp::format_call`） | 引数の型のメソッドだけ |
| 実行時（`Interp::resolve_fn_ref`、`ModuleScope::resolve_fn`） | チェッカーの結果があるのに、書かれた名前を `home` から探し直す |
| 実行時（`Interp::resolve_fn_def` / `method_key`） | `"type::method"` の文字列を分解して探し直す |

食い違い:

- 呼び出しではメソッドが関数より先、値では関数がメソッドより先。
- 呼び出しでは関数がグローバル変数より先、値ではグローバル変数が関数より先。
- 同じモジュールに同じ名前の関数とグローバル変数を定義できる（チェッカーの `fns` と `vars`、
  実行時の `fns` と `globals` が別の表）。
- 実行時の探し直しはチェッカーと別の実装で、チェックの後に近いモジュールへ同名の関数が
  定義されると、チェッカーが型を確かめたのと別の関数を呼びうる。

## 3. 一本化した規則

チェッカーに解決の入口を 1 つ置き（`Checker::resolve_name`）、上の表の全員がそれを呼ぶ。
実行時は解決しない。チェッカーが解決した結果（`Ref::resolved`、メソッドの型と名前）だけを使う。

### 3.1 素の名前 `n`、受け手の型 `R`（無いこともある）

1. ローカル（`let`・引数・`labels`・`symbol-macrolet`・`macrolet`）
2. モジュールの名前 `n` がマクロなら、そのマクロ
3. 構成子（`use` した列挙型の変種）、`use` した静的メソッド
4. `R` があれば、`R` のメソッド `n`
5. モジュールの名前 `n` が値（関数かグローバル変数）なら、その値

モジュールの名前 `n` は、関数・グローバル変数・マクロのどれか 1 つ。今のモジュール、`use` の
別名、祖先（根まで）の順に探し、最初に見つかったものに決まる（`Checker::resolve_module_entry`）。
`use` の別名がそのどれも指していない（型を指している）ときは、祖先へ探し続ける。
2 と 5 は同じ探索の結果を、マクロなら 2 で、値なら 5 で使う。マクロを 2 で決めるのは、マクロの
引数は式ではなく、4 のために第 1 引数の型を調べられないから。

受け手の型 `R`:

- 呼び出し `(n a ...)` では第 1 引数の型
- 値 `n` では期待型 `(fn (T ...) ...)` の第 1 引数の型（期待型が無ければ無し）
- `~/n/` では引数の型
- `compile` / `trace` / `untrace` / `disassemble` / `documentation` では無し

結果が値として使えないもの（マクロ）を値の位置で得たら、その旨のエラーにする。
呼び出しの位置でグローバル変数を得たら、その値（関数）を適用する。値の位置で関数を得たら関数値にする。

### 3.2 パス `a::...::n`

1. モジュールの名前（マクロ、関数、グローバル変数のどれか 1 つ）
2. 型の変種、型の静的メソッド

値の位置の `x::f`（`x` が値に結び付いた名前）は名前の解決ではなくフィールドの読み出しなので、
今までどおり先に試す。

### 3.3 定義の衝突

同じモジュールで、関数・グローバル変数・マクロのうち 2 つに同じ名前は使えない。どの順に定義しても
エラーにする（`check_value_clash`。型とトレイトの `check_type_trait_clash` と同じ扱い）。同じ種類の
再定義は今までどおり `RedefPolicy` に従う。

### 3.4 メソッドの名前の綴り（2026-10-11、ユーザー決定）

モジュールの中の名前と型の中の名前は別の名前にする。モジュール `a` の関数 `b` は `a::b`、
型 `a` のメソッド `b` は `a''b`。

それまではどちらも `a::b`（シンボルは `tl_a::b`）だった。両方を呼ぶ関数を `compile` すると、
コンパイルドライバがメソッドを関数と取り違えてパニックした。区切りに `'` を使うのは、
リーダーの区切り文字なのでソースに書いた名前には入らないから（`#` は名前に入るので `##` では
根の関数 `a##b` と衝突する）。

メソッドの名前を文字列にするのは `types::method_link_name` だけで、逆向きは
`types::split_method_link_name` だけ。これを使うのは、LLVM のシンボル（`tl_a''b`）、インタプリタに
登録する名前（`trace` の鍵と表示）、実行時のメッセージ、ダンプが docstring と総称メソッドの
テンプレートを置く鍵。島の `compile-assoc-user` だけは同じ文字列を自分で組み立てる。チェッカーの
型エラーは、ソースに書く形どおり `a::b` と書く。

## 4. 実装の順序

各 Phase の終わりに全テストを通す。

### Phase 1: 関数と変数の名前空間を 1 つに

- 定義の衝突をエラーにする（§3.3）。prelude・テスト・examples に衝突があれば直す。
- モジュールの値の検索を 1 つの関数にし（関数かグローバル変数かを返す）、呼び出しと値の両方が使う。

### Phase 2: 解決の入口を 1 つに

- `Checker::resolve_name`（§3.1、§3.2）を作り、呼び出し・値・パス・`compile` 系・
  `documentation` 系・`use` をそれに載せる。
- 第 2 引数の型でメソッドを探す規則（`try_instance_method_swapped`）を消す。
  `(push x v)` の順で書いている呼び出しを入れ替える。

### Phase 3: 実行時の探し直しをやめる

- 中間表現の `call`・`fnref`・`global`・`set-global` から `(WRITTEN...)` と `(HOME...)` を、
  `assoc`・`methodref` と `compile-fn` 系の対象から `(HOME...)` を消す。実行時はチェッカーが
  解決したパスで直接引く（`ModuleScope::get_fn` / `get_global` / `get_method`）。
- `ModuleScope::resolve_fn` / `resolve_global` / `resolve_method` と、それだけが読んでいた
  定義の `pub` の印（`FnDef::public`、`GlobalDef::public`、定義のノードの PUB 欄）を消す。
  `Ref` は解決済みのパスだけになるので `Path` に置き換える。
- コンパイルドライバの関数とメソッドの名前を、文字列ではなく型付きの値（関数のパスか、
  型のパスとメソッド名の組）で持つ。`CompileTarget`・`CallEdge`・`CompiledItem` は同じ形なので
  1 つにする。`Interp::resolve_fn_def` / `method_key` の文字列の分解は消す。
- メソッドの名前（LLVM のシンボルとコンパイラ内部の名前）は `型''メソッド` と綴る（§3.4）。

### Phase 3b: マクロを同じ名前空間に

- 定義の衝突にマクロを加える（§3.3）。
- マクロの検索を、関数・変数と同じ 1 回の探索にする（§3.1、§3.2）。

### Phase 4: `~/name/` を作り直す（§5）

## 5. `~/name/`（Phase 4 の前に決める）

`~/name/` は、その場所で `(name 引数 colon at)` と書いたのと同じ解決をする（§3.1、`R` は引数の型）。
引数の型がチェック時に分かる場合はそこで解決が済む。`~{` の中の要素のように型が実行時にしか
分からない場合の扱いは、Phase 3 までが済んでから決める。
