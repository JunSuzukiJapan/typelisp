# 名前・モジュール・定義の識別 — 設計（2026-10-17 改訂）

## 1. 原則（ユーザー決定）

- パス `foo::bar::zot` の意味は「`foo` 名前空間の子の `bar` 名前空間の子の `zot`」だけである。
  これ以外の解釈に沿った設計は採らない。
- パスを含んだ名前（セグメントを `::` でつないだ文字列）を、登録・比較・検索のキーにしない。
  文字列を `::` で切ってパスに戻すこともしない。
- 名前はシンボル（ポインタ）で、比べるのはポインタだけ。特殊形の頭、関数名の解決、
  ローカル変数、core IR の変数も含む。
- モジュールの中で書いた名前はそのモジュールのシンボル。外のシンボルになるのは明示的に
  取り込んだときだけ。`(module m (defun map ...))` の `map` は `m` の `map`。
- 公開（`pub`）していない定義は、ほかのモジュールから見えない。祖先も同じ。
- 標準ライブラリはルートの子モジュール `std`。中は Rust 風の子モジュールに分ける（5 節）。
  取り込みなしで使えるのは `std::prelude` が公開するものだけ。
- `std::prelude` の名前と同じ名前を定義するには、先に `(shadow NAME)` が要る。無ければエラー
  （`(defstruct Error ...)` もこれでエラーになる）。
- `use` は、取り込む側のモジュールの表に「そのモジュールのシンボル → 取り込む定義」を登録する。
  シンボル表は書き換えない。
- 語彙表は、予約語（SYSTEM）・`std`・`%core` の 3 つに分ける（実装済み）。
- REPL のトップレベルはモジュール `user`。
- 定義は「シンボル＋名前空間」で識別する。定義に別の番号は振らない。
- 名前空間はリーダーが作る。`(module foo` を読んだところで `foo` の名前空間に入る。パスは
  読むときに 1 段ずつたどって 1 つのシンボルにする。
- 型は名前空間ではない。型が持つのは、その型に属するメソッドなどの表。`Point::new` は
  「型 `Point` の表の `new`」と読む（`foo::bar::zot` を読んでいる最中に `bar` が型だとわかる）。
- `p::x` のように先頭が値（ローカル変数・大域変数）のときは、`x` は `p` の型の表で引く。
  `p` の束縛と型が決まるのは解析のときなので、リーダーは `(%value-member p x)` と読み、
  解析が解決する（3.9）。
- 役割を分ける（2026-10-18、ユーザー決定）: 型情報の保持と型の検査は別のもの。チェッカーは
  型の検査だけをする。マクロの展開・束縛の登録・名前の解決・型の推論は解析の層が行い、
  型情報は型情報の層が持つ（3.9）。
- `macrolet` と `symbol-macrolet` は、`(module m` と同じく定義に来た時点で登録し、本体に効かせる。
- 型と同じ名前の変数の後ろに `::` は書けない（2026-10-18、ユーザー決定 (a)）。シンボルは大文字と
  小文字を区別しないので、型 `P` と変数 `p` は同じシンボルで、`p::y` は型 `P` の表の `y` と読む。
- 名前の意味はセッションごと（2026-10-18、ユーザー決定 (i)）。シンボルそのものと、その名前の木
  （節と綴りからポインタ）はプロセスに 1 つ。どの節がモジュールか、型の表、`use` の取り込みは
  セッション（ヒープ）ごとの表 `SessionNames` が持つ（3.3）。
- メソッドの名前もシンボルで、CL の総称関数と同じ扱い。ほかのモジュールの名前にメソッドを
  足すとき、それを呼ぶときは名前を取り込む。`std::prelude` は prelude のメソッドの名前も公開する。
- 表示: 今のモジュールの定義と取り込んだ定義は名前だけ、今のモジュールの子孫の定義は今の
  モジュールからの相対パス、それ以外はルートからのパス。祖先の定義もルートから。エラー文の中で
  定義を名指しするパスは短くしない。

## 2. 今の実装のどこが原則に反しているか

文字列のパスを識別に使っているところは、すべて作り直しの対象である。

| 箇所 | 今 | 問題 |
|---|---|---|
| チェッカーのレジストリ `Namespace` | 子モジュールも定義も `String` キー。シンボル表の木とは別の、2 本目の木 | 木が 2 本あり、名前は文字列で引く |
| 定義の識別 `Path(Vec<String>)` | セグメントの文字列の列。`Display` で `::` につないだものが識別 | 定義が文字列で識別される |
| ヒープの型表 `type_keys` | `"std::option<char>"` のような文字列を登録して番号を振る | パスを含む名前を登録している |
| `ConcreteNames` の型キー、特殊化名、リンク名 | 文字列を組み立て、`base_type` / `type_arg_list` / `split_fn_type` で切り戻す | 文字列を切ってパスと型引数に戻している |
| 手書きの型キー | `BUILTIN_TYPE_KEYS`、`RESULT_KEYS`、`READER_MACRO_OPTION_KEY` など | 同上。パスが変わるたびに書き換え |
| 印字の表 | 変種名・フィールド名・`print-object`・`~/name/` の表が型キーの文字列キー。実行ファイルは `rt_print_*` に文字列で登録 | 同上 |
| `NameView`（段階 2a で追加） | 型キーの文字列を `::` で切って短くする | 文字列を切ってパスに戻している |
| `throw_tags` | キーが「所属パス::綴り」 | パスを含む名前をキーにしている |
| シンボル表の子モジュール | `children: HashMap<Box<str>, NsId>` | 子の名前がシンボルでない |
| `split("::")` で `Path` を作る箇所 | dump.rs、interp.rs、checker.rs ほか 10 か所以上 | 文字列からパスを作っている |

## 3. 新しい設計

### 3.1 モジュールの木は 1 本

シンボル表の節（`NsId`）がモジュールそのものになる。チェッカーのレジストリの `Namespace` は
廃止し、その表を `NsId` ごとに持つ。

- 節が持つもの: 親の `NsId`、自分の名前（親のモジュールのシンボル `SymRef`）、
  子モジュール `SymRef → NsId`、シンボル表 `名前 → SymRef`（読むときに使う）、定義の表（3.2）。
- 子モジュールのキーもシンボル。`(module bar ...)` の `bar` は、それを書いたモジュールのシンボル。

### 3.2 定義は「シンボル＋名前空間」で識別する

定義の名前のシンボルは、必ず定義したモジュールのシンボルである（外のシンボルでは定義できない）。
シンボルは所属の節（`home`）を持つので、「どのモジュールの何か」はシンボルだけで決まる。
1 つのシンボルが複数のものを指すのは名前空間が違うときだけなので、定義の識別は
`(SymRef, 名前空間)` で足りる。

- 名前空間は 3 つ: 値（関数・大域変数・マクロ）、型（型・トレイト・C 構造体・型の別名）、
  モジュール。
- モジュールの節の表: 値 `SymRef → 定義`、型 `SymRef → 定義`、子モジュール `SymRef → NsId`。
  自分の定義では、キーのシンボルと定義の名前のシンボルは同じ。
- `use` は今のモジュールの表に「自分のシンボル → 取り込む定義（の名前のシンボル）」を足す。
- 型は名前空間ではない。型が持つのは「その型に属するメソッドなど（構成子・フィールドの
  アクセサ・静的メソッド・メソッド）の表」で、キーはそれらの名前のシンボル。
- メソッドの名前は CL の総称関数と同じ扱い: `impl` を書いたモジュールで読んだシンボル
  （取り込んでいればそれ）。別々のモジュールが取り込みなしで書いた同名のメソッドは別物。
  ほかのモジュールの名前にメソッドを足すとき、それを呼ぶときは、その名前を取り込む。
  トレイトのメソッドの名前は、トレイトを定義したモジュールのシンボル。
- 名前を書けない定義（コンストラクタの内部名、単型化した定義、チェッカーが作る補助）は、
  そのモジュールに所属するがどの表からも読めないシンボル（gensym と同じもの）を名前に持つ。
- `Path(Vec<String>)` は定義の識別に使わない。チェッカーの中で定義を指すものはすべて
  `(SymRef, 名前空間)`。パスが要るのは表示とプロセスの外へ書き出すときだけで、シンボルの
  `home` から親をたどって作る。

節の木は `typelisp-mem` に置く（シンボルと同じ層。ヒープと印字が使うため）。

### 3.3 名前の解決

- 読むとき（リーダー）: モジュール `m` で名前 `n` を読むと、
  1. `m` の表にあればそれ、2. 予約語ならそれ、3. `std::prelude` が公開していればその定義の
  シンボル、4. どれでもなければ `m` に作る。名前のハッシュは 1 回。
- `(module foo` まで読んだところで `foo` の名前空間を作って入り、閉じ括弧までのシンボルは
  そこに登録する。モジュールの本体を読み終える前でも、中の子モジュールは木にある。
- `(defstruct point` / `(defenum` / `(deftrait` を読んだところで、`point` が型であることと、
  その型の表を作る。名前空間は作らない。フォームを読み終えたところで、構成子・フィールドの
  アクセサ・トレイトのメソッドの名前を表に登録する。`(impl point` は表を開き、`impl` を読み終えた
  ところで中で定義した名前を登録する。マクロが展開して作った定義は、解析が同じ登録をする。
- `(use ...)` もリーダーが処理する（2026-10-18、ユーザー決定）。`use` のパスを 1 つ読み終えるたびに、
  セッションにあるモジュールか型ならその場で取り込みを登録し、そうでなければ読むときの評価の
  仕組み（`ReadEval::bring_in`）が依存するファイルを読み込んでから登録する。モジュールの本体の
  中でも、`use` の後ろに書いたものはそのまま読める。
- 先行登録と `use` の処理をするのは、トップレベルのフォームとモジュールの本体のフォームだけ。
  クォートの中の `(defstruct ...)` や `(use ...)` はデータで、何も登録しない。
- `(module PATH` の PATH は、各セグメントをその前のモジュールの子として作りながら読む。`use` の
  パスは、まだ読み込まれていないモジュールを名指せるので、各セグメントを今のモジュールで読む。
- 名前の意味の表 `SessionNames` はヒープ（`HeapShared`）が持つ。リーダーが書き込むのは
  読んだ時点で分かること（モジュール、型の名前とメンバー、取り込み）。チェッカーはフォームを
  検査する前後に、レジストリの定義（検査で生まれたメンバー、組み込みの型を含む）を写す
  （`Registry::publish_names`）。dump を読み込んだときも写す。検査より前に読むドライバ（prelude を
  読み込まないテスト）は、読む前に `Checker::publish_names` を呼ぶ。
- 1 フォームずつ読む。全部を先に読んでから検査すると、前のフォームの検査で生まれる名前
  （構造体のセッター `set-x` など）が、後ろのフォームを読む時点で表に無い。
- パス `foo::bar::zot` は 1 段ずつたどって読む。`foo` が名前空間ならその中で `bar` を読み、
  `bar` が名前空間ならその中で `zot` を読む。`bar` が型なら、`zot` は `bar` の表で引く。
  結果は 1 つのシンボル。先頭は、今のモジュールの子にあればそれ、無ければルートの子。
  `::foo` はルートから。たどれなければ読むときのエラー。
- 素の名前の解決（解析）: 局所の束縛、次に今のモジュールの表をシンボルで引く。祖先はたどらない。
  見つかるのは、今のモジュールの定義と、取り込んだ定義だけ。
- メソッド呼び出し: 第 1 引数の型の表を、書いた名前のシンボルで引く。
- パスで書いた名前: リーダーが 1 つのシンボルにしているので、解析はそのシンボルの
  所属モジュール（型の表のものならその型の表）を 1 回引く。`pub` でなければ見つからない扱い。
- マクロの展開が持ち込んだシンボルは、展開した側のモジュールのシンボルのまま。

### 3.4 型

- `Type::Named(SymRef, Vec<Type>)`、`Type::Dyn(SymRef, ...)`、`Type::CStruct(SymRef)`。
  シンボルは型の名前空間の定義の名前。
- 基本型（`int` `char` `string` など）も `std::primitive` の定義で、名前のシンボルは語彙表の
  固定のもの。`Type::Int` などの変種は残し、その定義はそのシンボルで引く。

### 3.5 実行時の型の識別（型キーの置き換え）

ヒープの型表は文字列を登録しない。型の形をそのまま登録して番号（`TypeId`）を振る。

```
TypeShape = Named(SymRef, [TypeId])
          | Fn([TypeId], rest: Option<TypeId>, ret: TypeId)
          | Dyn(SymRef, [TypeId])
          | Ptr(TypeId)
          | Unit | Never
```

- 同じ形には同じ番号（形の上でハッシュする）。箱は `TypeId` を持ち、比べるのは番号。
- 型引数を取り出すのは形を読むだけ。文字列を切らない。
- 印字の表（変種名・フィールド名・`print-object`・`~/name/`）のキーは型の名前のシンボルか
  `TypeId`。
- 単型化した定義は、`(元の定義のシンボル, [TypeId])` の表から引く、その定義のための
  名前を書けないシンボルで識別する。
- `throw_tags` のキーはシンボル（`SymRef`）。

### 3.6 プロセスの外へ出すとき

- ダンプ・fasl: 定義は「所属モジュールの節を根から順に、各セグメントのシンボル名」と
  「定義の名前」で書く（名前の列であって、つないだ 1 本の文字列ではない）。読むときは
  木を 1 段ずつたどってシンボルに戻す。型は `TypeShape` を再帰で書く。
- 実行ファイル: 起動時に、使う節・シンボル・型の形を順に作る表を埋め込み、ポインタと番号は
  そのとき決まる。コンパイル済みコードは型の番号を起動時に埋まる大域の表から読む。JIT は同じ
  プロセスなので番号をそのまま定数にする。印字の登録（`rt_print_*`）も番号で行う。
- LLVM のシンボル名（リンク名）はリンカに渡すためだけに定義のシンボルから作り、読み戻さない・
  表のキーにしない。

### 3.7 表示

`NameView` は定義のシンボル（型なら `TypeShape` の中のシンボル）の `home` から節を親へ
たどって表示を作る。今のモジュールの `NsId` と比べ、取り込みは今のモジュールの表を見る。文字列は最後に組み立てる
だけで、切らない。

### 3.8 ローカル変数と IR

- 局所の束縛（型情報の層のスコープ）のキーは `SymRef`。
- core IR の `(var SYM)` は利用者のシンボルを運び、インタプリタと島は `eq` で比べる。
- 島の IR タグの振り分けはタグのシンボルとの `eq`。
- 定義を指す IR（`call` の呼び先など）は定義のシンボルを運ぶ。

### 3.9 処理の流れと役割（2026-10-18、ユーザー決定の (A)）

トップレベルのフォーム 1 つごとに、次の順で処理する。

1. 読む（リーダー）: 文字をデータにする。文字をどのシンボルにするかを変えるもの
   （`(module foo`、`use`、型の表）は、読んでいる途中に登録する（3.3）。
2. 解析: データをたどり、マクロを展開し、束縛を登録し、名前を解決し、各式の型を決める。
   結果は、各節が参照先と型を持つ解析済みの木。
3. 検査（チェッカー）: 解析済みの木で、決まった型どうしが合っているかを検査する。
4. 下ろす: 検査を通った木から core IR を作る。
5. 評価: 今と同じ。

型情報の層は 2〜4 から問い合わせを受ける。持つのは、大域の定義とその型（今のレジストリ）、
型の表（メソッド・フィールド・構成子）、局所の束縛とその型のスコープ（今の `Env`）。
解析が書き込み、検査と下ろしは読むだけ。

境目の規則: すでにシンボルになったものの意味を決めるもの（ローカル変数、`macrolet`、
`symbol-macrolet`、マクロの展開）は解析で処理する。マクロの展開結果は文字にならないので、
書いたフォームも展開結果も同じ解析を通る。登録の処理は 1 か所にしかない。

解析がすること:

- マクロの展開。`macrolet`・`symbol-macrolet` の登録と、その本体への適用。
- 束縛の登録（`let` `let*` `lambda` `labels` `defun` の引数、`match` のパターン、ループの変数）。
  型を書いた束縛はその型で、書いていない束縛は初期値の推論した型で登録する。
- 名前の解決: 変数・関数・マクロ・型・メソッド、`(%value-member p x)`（`p` の型の表の `x`）。
- 各式の型を決める: リテラル、呼び出しの戻り値、ジェネリックの型引数（期待する型と引数から）、
  `match` の腕どうしで型引数を埋め合う推論、ループと `block` の出口の型、単型化の要求。
- 型が衝突しても止まらない。型変数は最初に決まった型を採り、後の食い違いは検査が見つける。
- 解析が止まるエラーは、先へ進めないものだけ: 名前が解決できない、マクロの展開に失敗した、
  型を決められない。

検査がすること:

- 決まった型どうしが合うか: 引数と仮引数、戻り値と宣言、代入とその場所、`if` と `match` の
  腕どうし、期待する型。
- トレイトの境界（`:where`）を満たすか、`impl` がトレイトのメソッドをそろえているか。
- `match` の網羅性。
- 可視性（`pub`）、`unsafe` の許可、キーワードを束縛していないか、トップレベル専用の
  フォームの位置、`setf` の場所。

検査は解析がフォーム全体を終えてから行うので、後から決まる型変数も決まった後で見る。

解析済みの木（2026-10-18、ユーザー決定）: 解析の結果は、出現ごとに参照先と型を持つ木に置く。
トップレベルのフォーム 1 つの間だけある Rust の構造で、実行するのは今と同じ core IR。要る理由:

- 検査は節ごとに解析の結果（呼び先の定義と仮引数の型、変数の束縛と型、リテラルの型）を使う。
  検査をフォーム全体の解析の後にするので、結果を残しておく場所が要る。後にするのは、
  `(let ((v (vector-new))) (print-all v) (vector-push v 1))` の `T` のように、型変数が後ろで
  決まるため。
- 下ろす段階も同じ結果（束縛、呼び先、どの `impl` か、単型化のどの実体か、repr のための型）を
  使う。求め直すと同じ問いに答える場所が 2 つになる。
- 読んだデータの cons セルはキーにできない。マクロは同じセルを 2 か所に置ける
  （`` `(progn (let ((p (make-a))) ,e) (let ((p (make-b))) ,e)) ``）ので、結果は出現ごとに持つ。

## 4. 性能

- 読むとき: ハッシュ 1 回、表の参照は多くて 2 回。
- 解決: ポインタをキーにした表を 1 回（パスはセグメントの数だけ）。
- 型の比較: 番号。型の登録: 形のハッシュ 1 回。
- 印字の表・特殊化の表: 番号のキー。

## 6. 段階

各段階で全テストを通してからコミットする。

済み:

- 語彙表の 3 分割、`std`・`%core` の追加、IR のタグを番号で扱う、島を `%core` へ（`ff8354c`）。
- prelude と組み込み関数を `std` へ、REPL を `user` に（`3624635`）。この段階で入れた、
  文字列のパスに頼る部分（`std::` 付きの型キーの文字列、`NameView` の文字列分解、段階 2 の間
  だけ `std` を探す段）は、下の段階で置き換えて消す。

これから:

1. 読み方（3.3）。済み。シンボル表の子モジュールのキーをシンボルにし、型の表をシンボル表に置く。
   リーダーが `(module foo` で名前空間に入り、型の表を登録し、パスを 1 段ずつたどって
   1 つのシンボルにする。`p::x` は `(%value-member p x)` と読む。同じフォームの中の型の名前の
   先行登録、読むときの `use`。チェッカーはそのシンボルから今の `Path` を作って受け取る
   （段階 3 までの橋渡し）。
2. 役割の分離（3.9）。型情報の層（大域の表と局所のスコープ）をチェッカーから出し、
   解析（展開・登録・解決・推論）、検査、下ろしを分ける。`(%value-member p x)` は解析が解決する。
3. モジュールの木を 1 本にする。レジストリの表を節ごとの `SymRef` キーの表にし、`Path` による
   定義の識別を `(SymRef, 名前空間)` に置き換える。型変数を `Path` から分ける。
4. 名前の解決をポインタにする（3.3）。メソッド呼び出しも書いた名前のシンボルで引く。
   祖先をたどる解決、読むときの `std` の段、文字列による解決を消す。`std::prelude` の公開表、`shadow`、`shadow` なしの prelude の名前の定義をエラーに
   する（`(defstruct Error ...)` のテストを足す）。
5. 実行時の型の識別を `TypeShape` の登録にする（3.5）。型キーの文字列、`ConcreteNames` の
   切り戻し、手書きのキー、印字の表の文字列キー、`rt_print_*` の文字列登録を消す。
   `NameView` を定義のシンボルから作る形に書き直す。島と成果物を再生成する。
6. `std` を子モジュールに分け、組み込み型を移す（5 節）。`std::prelude` を作り、テスト・例に
   `use` を足す。
7. 局所の束縛と IR の変数を `SymRef` に、定義を指す IR を定義のシンボルに（島の再生成は 2 回）。
8. ダンプ・fasl を 3.6 の形に。
9. 利用者向け文書（日本語の原本、翻訳）。
