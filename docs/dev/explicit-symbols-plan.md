# 名前・モジュール・定義の識別 — 設計（2026-10-17 改訂）

## 1. 原則（ユーザー決定）

- パス `foo::bar::zot` の意味は「`foo` 名前空間の子の `bar` 名前空間の子の `zot`」だけである。
  これ以外の解釈に沿った設計は採らない。
- パスを含んだ名前（セグメントを `::` でつないだ文字列）を、登録・比較・検索のキーにしない。
  文字列を `::` で切ってパスに戻すこともしない。
- 名前はシンボル（ポインタ）で、比べるのはポインタだけ。特殊形の頭、関数名の解決、
  ローカル変数、core IR の変数も含む。
- モジュールの中で書いた名前はそのモジュールのシンボル。外のシンボルになるのは明示的に
  取り込んだときだけ。`(module m (defun map ...))` の `map` は `m` の `map`。
- 公開（`pub`）していない定義は、ほかのモジュールから見えない。祖先も同じ。
- 標準ライブラリはルートの子モジュール `std`。中は Rust 風の子モジュールに分ける（5 節）。
  取り込みなしで使えるのは `std::prelude` が公開するものだけ。
- `std::prelude` の名前と同じ名前を定義するには、先に `(shadow NAME)` が要る。無ければエラー
  （`(defstruct Error ...)` もこれでエラーになる）。
- `use` は、取り込む側のモジュールの表に「そのモジュールのシンボル → 取り込む定義」を登録する。
  シンボル表は書き換えない。
- 語彙表は、予約語（SYSTEM）・`std`・`%core` の 3 つに分ける（実装済み）。
- REPL のトップレベルはモジュール `user`。
- 定義は「シンボル＋名前空間」で識別する。定義に別の番号は振らない。
- 名前空間はリーダーが作る。`(module foo` を読んだところで `foo` の名前空間に入る。パスは
  読むときに 1 段ずつたどって 1 つのシンボルにする。
- 型は名前空間ではない。型が持つのは、その型に属するメソッドなどの表。`Point::new` は
  「型 `Point` の表の `new`」と読む（`foo::bar::zot` を読んでいる最中に `bar` が型だとわかる）。
- `p::x` のように先頭が値（ローカル変数・大域変数）のときは、`x` は `p` の型の表で引く。
  `p` の束縛と型が決まるのは解析のときなので、リーダーは `(%value-member p x)` と読み、
  解析が解決する（3.9）。
- 役割を分ける（2026-10-18、ユーザー決定）: 型情報の保持と型の検査は別のもの。チェッカーは
  型の検査だけをする。マクロの展開・束縛の登録・名前の解決・型の推論は解析の層が行い、
  型情報は型情報の層が持つ（3.9）。
- `macrolet` と `symbol-macrolet` は、`(module m` と同じく定義に来た時点で登録し、本体に効かせる。
- 型と同じ名前の変数の後ろに `::` は書けない（2026-10-18、ユーザー決定 (a)）。シンボルは大文字と
  小文字を区別しないので、型 `P` と変数 `p` は同じシンボルで、`p::y` は型 `P` の表の `y` と読む。
- 名前の意味はセッションごと（2026-10-18、ユーザー決定 (i)）。シンボルそのものと、その名前の木
  （節と綴りからポインタ）はプロセスに 1 つ。どの節がモジュールか、型の表、`use` の取り込みは
  セッション（ヒープ）ごとの表 `SessionNames` が持つ（3.3）。
- メソッドの名前もシンボルで、CL の総称関数と同じ扱い。ほかのモジュールの名前にメソッドを
  足すとき、それを呼ぶときは名前を取り込む。`std::prelude` は prelude のメソッドの名前も公開する。
- 表示: 今のモジュールの定義と取り込んだ定義は名前だけ、今のモジュールの子孫の定義は今の
  モジュールからの相対パス、それ以外はルートからのパス。祖先の定義もルートから。エラー文の中で
  定義を名指しするパスは短くしない。

## 2. 今の実装のどこが原則に反しているか

文字列のパスを識別に使っているところは、すべて作り直しの対象である。

| 箇所 | 今 | 問題 |
|---|---|---|
| チェッカーのレジストリ `Namespace` | 子モジュールも定義も `String` キー。シンボル表の木とは別の、2 本目の木 | 木が 2 本あり、名前は文字列で引く |
| 定義の識別 `Path(Vec<String>)` | セグメントの文字列の列。`Display` で `::` につないだものが識別 | 定義が文字列で識別される |
| ヒープの型表 `type_keys` | `"std::option<char>"` のような文字列を登録して番号を振る | パスを含む名前を登録している |
| `ConcreteNames` の型キー、特殊化名、リンク名 | 文字列を組み立て、`base_type` / `type_arg_list` / `split_fn_type` で切り戻す | 文字列を切ってパスと型引数に戻している |
| 手書きの型キー | `BUILTIN_TYPE_KEYS`、`RESULT_KEYS`、`READER_MACRO_OPTION_KEY` など | 同上。パスが変わるたびに書き換え |
| 印字の表 | 変種名・フィールド名・`print-object`・`~/name/` の表が型キーの文字列キー。実行ファイルは `rt_print_*` に文字列で登録 | 同上 |
| `NameView`（段階 2a で追加） | 型キーの文字列を `::` で切って短くする | 文字列を切ってパスに戻している |
| `throw_tags` | キーが「所属パス::綴り」 | パスを含む名前をキーにしている |
| シンボル表の子モジュール | `children: HashMap<Box<str>, NsId>` | 子の名前がシンボルでない |
| `split("::")` で `Path` を作る箇所 | dump.rs、interp.rs、checker.rs ほか 10 か所以上 | 文字列からパスを作っている |

## 3. 新しい設計

### 3.1 モジュールの木は 1 本

シンボル表の節（`NsId`）がモジュールそのものになる。チェッカーのレジストリの `Namespace` は
廃止し、その表を `NsId` ごとに持つ。

- 節が持つもの: 親の `NsId`、自分の名前（親のモジュールのシンボル `SymRef`）、
  子モジュール `SymRef → NsId`、シンボル表 `名前 → SymRef`（読むときに使う）、定義の表（3.2）。
- 子モジュールのキーもシンボル。`(module bar ...)` の `bar` は、それを書いたモジュールのシンボル。

### 3.2 定義は「シンボル＋名前空間」で識別する

定義の名前のシンボルは、必ず定義したモジュールのシンボルである（外のシンボルでは定義できない）。
シンボルは所属の節（`home`）を持つので、「どのモジュールの何か」はシンボルだけで決まる。
1 つのシンボルが複数のものを指すのは名前空間が違うときだけなので、定義の識別は
`(SymRef, 名前空間)` で足りる。

- 名前空間は 3 つ: 値（関数・大域変数・マクロ）、型（型・トレイト・C 構造体・型の別名）、
  モジュール。
- モジュールの節の表: 値 `SymRef → 定義`、型 `SymRef → 定義`、子モジュール `SymRef → NsId`。
  自分の定義では、キーのシンボルと定義の名前のシンボルは同じ。
- `use` は今のモジュールの表に「自分のシンボル → 取り込む定義（の名前のシンボル）」を足す。
- 型は名前空間ではない。型が持つのは「その型に属するメソッドなど（構成子・フィールドの
  アクセサ・静的メソッド・メソッド）の表」で、キーはそれらの名前のシンボル。
- メソッドの名前は CL の総称関数と同じ扱い: `impl` を書いたモジュールで読んだシンボル
  （取り込んでいればそれ）。別々のモジュールが取り込みなしで書いた同名のメソッドは別物。
  ほかのモジュールの名前にメソッドを足すとき、それを呼ぶときは、その名前を取り込む。
  トレイトのメソッドの名前は、トレイトを定義したモジュールのシンボル。
- 名前を書けない定義（コンストラクタの内部名、単型化した定義、チェッカーが作る補助）は、
  そのモジュールに所属するがどの表からも読めないシンボル（gensym と同じもの）を名前に持つ。
- `Path(Vec<String>)` は定義の識別に使わない。チェッカーの中で定義を指すものはすべて
  `(SymRef, 名前空間)`。パスが要るのは表示とプロセスの外へ書き出すときだけで、シンボルの
  `home` から親をたどって作る。

節の木は `typelisp-mem` に置く（シンボルと同じ層。ヒープと印字が使うため）。

### 3.3 名前の解決

- 読むとき（リーダー）: モジュール `m` で名前 `n` を読むと、
  1. `m` の表にあればそれ、2. 予約語ならそれ、3. `std::prelude` が公開していればその定義の
  シンボル、4. どれでもなければ `m` に作る。名前のハッシュは 1 回。
- `(module foo` まで読んだところで `foo` の名前空間を作って入り、閉じ括弧までのシンボルは
  そこに登録する。モジュールの本体を読み終える前でも、中の子モジュールは木にある。
- `(defstruct point` / `(defenum` / `(deftrait` を読んだところで、`point` が型であることと、
  その型の表を作る。名前空間は作らない。フォームを読み終えたところで、構成子・フィールドの
  アクセサ・トレイトのメソッドの名前を表に登録する。`(impl point` は表を開き、`impl` を読み終えた
  ところで中で定義した名前を登録する。マクロが展開して作った定義は、解析が同じ登録をする。
- `(use ...)` もリーダーが処理する（2026-10-18、ユーザー決定）。`use` のパスを 1 つ読み終えるたびに、
  セッションにあるモジュールか型ならその場で取り込みを登録し、そうでなければ読むときの評価の
  仕組み（`ReadEval::bring_in`）が依存するファイルを読み込んでから登録する。モジュールの本体の
  中でも、`use` の後ろに書いたものはそのまま読める。
- 先行登録と `use` の処理をするのは、トップレベルのフォームとモジュールの本体のフォームだけ。
  クォートの中の `(defstruct ...)` や `(use ...)` はデータで、何も登録しない。
- `(module PATH` の PATH は、各セグメントをその前のモジュールの子として作りながら読む。`use` の
  パスは、まだ読み込まれていないモジュールを名指せるので、各セグメントを今のモジュールで読む。
- 名前の意味の表 `SessionNames` はヒープ（`HeapShared`）が持つ。リーダーが書き込むのは
  読んだ時点で分かること（モジュール、型の名前とメンバー、取り込み）。チェッカーはフォームを
  検査する前後に、レジストリの定義（検査で生まれたメンバー、組み込みの型を含む）を写す
  （`Registry::publish_names`）。dump を読み込んだときも写す。検査より前に読むドライバ（prelude を
  読み込まないテスト）は、読む前に `Checker::publish_names` を呼ぶ。
- 1 フォームずつ読む。全部を先に読んでから検査すると、前のフォームの検査で生まれる名前
  （構造体のセッター `set-x` など）が、後ろのフォームを読む時点で表に無い。
- パス `foo::bar::zot` は 1 段ずつたどって読む。`foo` が名前空間ならその中で `bar` を読み、
  `bar` が名前空間ならその中で `zot` を読む。`bar` が型なら、`zot` は `bar` の表で引く。
  結果は 1 つのシンボル。先頭は、今のモジュールの子にあればそれ、無ければルートの子。
  `::foo` はルートから。たどれなければ読むときのエラー。
- 素の名前の解決（解析）: 局所の束縛、次に今のモジュールの表をシンボルで引く。祖先はたどらない。
  見つかるのは、今のモジュールの定義と、取り込んだ定義だけ。
- メソッド呼び出し: 第 1 引数の型の表を、書いた名前のシンボルで引く。
- パスで書いた名前: リーダーが 1 つのシンボルにしているので、解析はそのシンボルの
  所属モジュール（型の表のものならその型の表）を 1 回引く。`pub` でなければ見つからない扱い。
- マクロの展開が持ち込んだシンボルは、展開した側のモジュールのシンボルのまま。

### 3.4 型

- `Type::Named(SymRef, Vec<Type>)`、`Type::Dyn(SymRef, ...)`、`Type::CStruct(SymRef)`。
  シンボルは型の名前空間の定義の名前。
- 基本型（`int` `char` `string` など）も `std::primitive` の定義で、名前のシンボルは語彙表の
  固定のもの。`Type::Int` などの変種は残し、その定義はそのシンボルで引く。

### 3.5 実行時の型の識別（型キーの置き換え）

型の表は文字列を登録しない。型の形をそのまま登録して番号（`TypeId`）を振る。表はヒープでなく
プロセスに 1 つ（5c で変えた。欄の型の雛形や `rt_print_*` の登録は、ヒープを作る前に番号が
要る）。組み込みの型を最初に登録するので、`TypeId` の定数はどのプロセスでも同じ番号になる。

```
TypeShape = Named(NsId, SymRef, [TypeId])
          | Fn([TypeId], rest: Option<TypeId>, ret: TypeId)
          | Dyn(NsId, SymRef, [TypeId])
          | Ptr(TypeId)
          | CStruct(NsId, SymRef)
          | Unit | Never
          | Param(u32)
```

- `Param(n)` は欄の型の雛形の中の、持ち主の型の n 番目の引数。値の型にはならない。

- 定義は所属モジュール（`NsId`）とそこでの名前のシンボルの組で指す。チェッカーの `Path` と
  同じ 2 つで、シンボルだけでは定義が決まらない（5b で `SymRef` だけの案から変えた）。

- 同じ形には同じ番号（形の上でハッシュする）。箱は `TypeId` を持ち、比べるのは番号。
- 型引数を取り出すのは形を読むだけ。文字列を切らない。
- 印字の表（変種名・フィールド名・`print-object`・`~/name/`）のキーは型の名前のシンボルか
  `TypeId`。
- 単型化した定義は、`(元の定義のシンボル, [TypeId])` の表から引く、その定義のための
  名前を書けないシンボルで識別する。
- `throw_tags` のキーはシンボル（`SymRef`）。

### 3.6 プロセスの外へ出すとき

- ダンプ・fasl: 定義は「所属モジュールの節を根から順に、各セグメントのシンボル名」と
  「定義の名前」で書く（名前の列であって、つないだ 1 本の文字列ではない）。読むときは
  木を 1 段ずつたどってシンボルに戻す。型は `TypeShape` を再帰で書く。
- 実行ファイル: 起動時に、使う節・シンボル・型の形を順に作る表を埋め込み、ポインタと番号は
  そのとき決まる。コンパイル済みコードは型の番号を起動時に埋まる大域の表から読む。JIT は同じ
  プロセスなので番号をそのまま定数にする。印字の登録（`rt_print_*`）も番号で行う。
- LLVM のシンボル名（リンク名）はリンカに渡すためだけに定義のシンボルから作り、読み戻さない・
  表のキーにしない。

### 3.7 表示

`NameView` は定義のシンボル（型なら `TypeShape` の中のシンボル）の `home` から節を親へ
たどって表示を作る。今のモジュールの `NsId` と比べ、取り込みは今のモジュールの表を見る。文字列は最後に組み立てる
だけで、切らない。

### 3.8 ローカル変数と IR

- 局所の束縛（型情報の層のスコープ）のキーは `SymRef`。
- core IR の `(var SYM)` は利用者のシンボルを運び、インタプリタと島は `eq` で比べる。
- 島の IR タグの振り分けはタグのシンボルとの `eq`。
- 定義を指す IR（`call` の呼び先など）は定義のシンボルを運ぶ。

### 3.9 処理の流れと役割（2026-10-18、ユーザー決定の (A)）

トップレベルのフォーム 1 つごとに、次の順で処理する。

1. 読む（リーダー）: 文字をデータにする。文字をどのシンボルにするかを変えるもの
   （`(module foo`、`use`、型の表）は、読んでいる途中に登録する（3.3）。
2. 解析: データをたどり、マクロを展開し、束縛を登録し、名前を解決し、各式の型を決める。
   結果は、各節が参照先と型を持つ解析済みの木。
3. 検査（チェッカー）: 解析済みの木で、決まった型どうしが合っているかを検査する。
4. 下ろす: 検査を通った木から core IR を作る。
5. 評価: 今と同じ。

型情報の層は 2〜4 から問い合わせを受ける。持つのは、大域の定義とその型（今のレジストリ）、
型の表（メソッド・フィールド・構成子）、局所の束縛とその型のスコープ（今の `Env`）。
解析が書き込み、検査と下ろしは読むだけ。

境目の規則: すでにシンボルになったものの意味を決めるもの（ローカル変数、`macrolet`、
`symbol-macrolet`、マクロの展開）は解析で処理する。マクロの展開結果は文字にならないので、
書いたフォームも展開結果も同じ解析を通る。登録の処理は 1 か所にしかない。

解析がすること:

- マクロの展開。`macrolet`・`symbol-macrolet` の登録と、その本体への適用。
- 束縛の登録（`let` `let*` `lambda` `labels` `defun` の引数、`match` のパターン、ループの変数）。
  型を書いた束縛はその型で、書いていない束縛は初期値の推論した型で登録する。
- 名前の解決: 変数・関数・マクロ・型・メソッド、`(%value-member p x)`（`p` の型の表の `x`）。
- 各式の型を決める: リテラル、呼び出しの戻り値、ジェネリックの型引数（期待する型と引数から）、
  `match` の腕どうしで型引数を埋め合う推論、ループと `block` の出口の型、単型化の要求。
- 型が衝突しても止まらない。型変数は最初に決まった型を採り、後の食い違いは検査が見つける。
- 解析が止まるエラーは、先へ進めないものだけ: 名前が解決できない、マクロの展開に失敗した、
  型を決められない。

検査がすること:

- 決まった型どうしが合うか: 引数と仮引数、戻り値と宣言、代入とその場所、`if` と `match` の
  腕どうし、期待する型。
- トレイトの境界（`:where`）を満たすか、`impl` がトレイトのメソッドをそろえているか。
- `match` の網羅性。
- 可視性（`pub`）、`unsafe` の許可、キーワードを束縛していないか、トップレベル専用の
  フォームの位置、`setf` の場所。

検査は解析がフォーム全体を終えてから行うので、後から決まる型変数も決まった後で見る。

解析済みの木（2026-10-18、ユーザー決定）: 解析の結果は、出現ごとに参照先と型を持つ木に置く。
トップレベルのフォーム 1 つの間だけある Rust の構造で、実行するのは今と同じ core IR。要る理由:

- 検査は節ごとに解析の結果（呼び先の定義と仮引数の型、変数の束縛と型、リテラルの型）を使う。
  検査をフォーム全体の解析の後にするので、結果を残しておく場所が要る。後にするのは、
  `(let ((v (vector-new))) (print-all v) (vector-push v 1))` の `T` のように、型変数が後ろで
  決まるため。
- 下ろす段階も同じ結果（束縛、呼び先、どの `impl` か、単型化のどの実体か、repr のための型）を
  使う。求め直すと同じ問いに答える場所が 2 つになる。
- 読んだデータの cons セルはキーにできない。マクロは同じセルを 2 か所に置ける
  （`` `(progn (let ((p (make-a))) ,e) (let ((p (make-b))) ,e)) ``）ので、結果は出現ごとに持つ。

### 3.10 段階 2 の作り（2026-10-18）

今のチェッカー（`check/checker.rs`、約 1 万 9 千行、`check_*` が 132、型エラーを出す箇所が 480）は、
フォームをたどりながら、マクロの展開、束縛の登録、名前の解決、型の推論、検査、core IR の組み立てを
1 回で行い、`Checked { form, ty }`（core IR と型）を返す。これを 3.9 の 4 つに分ける。

モジュールの置き場所:

| モジュール | 役割 | 今どこにあるか |
|---|---|---|
| `check/info.rs` | 型情報の層: レジストリ、局所のスコープ、型の表への問い合わせ | `Registry`、`Env`、`Scope`、`resolve_*` の一部 |
| `check/analyze.rs` ほか | 解析: 展開・登録・解決・推論、解析済みの木を作る | `check_*` の本体 |
| `check/verify.rs` | 検査: 解析済みの木で型の一致などを見る | `check_*` の中の型エラー |
| `check/lower.rs` | 下ろす: 解析済みの木から core IR | `forms.rs` と `check_*` の中の組み立て |

解析済みの木（`Node`）:

- Rust の構造で、トップレベルのフォーム 1 つの間だけある。節は `kind`・`ty`（決まった型）・`loc`
  （元のフォームの位置）を持つ。
- `kind` は、参照先を解決済みの形で持つ。局所の束縛は型情報の層のスコープの番号、大域の定義は
  定義の識別（段階 3 までは `Path`、その後は `(SymRef, 名前空間)`）、メソッドは選んだ `impl`、
  総称関数の呼び出しは単型化の実体、フィールドは型の表のメンバー。
- 種類は今の core IR の形に合わせる（`var` `global` `call` `assoc` `if` `let` `lambda` `match`
  `construct` `field-get` `set` `quote` `loop` `block` ...）。下ろす段階は節 1 つにつき今の
  `forms.rs` の組み立てを 1 つ呼ぶ。
- 引用したデータ（`quote` の中身）は `Value` のまま持つ。ヒープの値を持つ節は根（ルート）に
  載せる（`Checked.form` と同じ規律）。

移し方（各段でテストを通してコミットする）:

- 2a. 型情報の層を切り出す。`Env`・`Scope` と、レジストリへの問い合わせを `check/info.rs` に移し、
  チェッカーはそこを通して引く。振る舞いは変えない。
- 2b. 木を入れる（済み）。式の解析は `Checked { ty, node, loc }`（型・節・書かれた位置）を返し、
  IR は持たない。下ろす段階（`check/lower.rs` の `lower`）が木を子から順にたどって IR を作り、
  定数の畳み込みもそこで行う。下ろすのは IR が要る所（定義の本体、トップレベルの式、`&optional`
  の既定値など）で、トップレベルのフォームの終わりまでに済む。木が指すヒープの値（リテラルの箱、
  クォートしたデータ）は、そのフォームの間だけ専用の根のスタックに載せる（`Checker::hold`）。
  フォームの部分を調べるために開いた `RootScope` が閉じても外れないようにするため。
  型だけを変える箇所は `Checked::retyped` で節を残す。
- 2c. 検査を移す。型の一致を見る箇所を、種類ごとに解析から `verify.rs` へ移す（引数と仮引数、
  戻り値、`if`/`match` の腕、代入、期待する型、トレイトの境界、網羅性、`pub`、`unsafe`、
  キーワードの束縛、トップレベル専用の位置、`setf` の場所）。解析は食い違いで止まらず、
  最初に決まった型を採る。
  食い違いは木の節（`Node::Disagree`）として残し、`verify.rs` が子から順（内側が先、
  兄弟は左から）にたどって報告する。検査を走らせるのは IR を下ろす入口（`Checker::lowered`）と、
  調べた木を捨てる所（トレイトの既定本体、`where` 境界越しの呼び出しの引数、`match` の腕の
  試し検査、失敗を言い換える `aref` と `~/name/`）。期待する型との食い違いと、枝の型の合流
  （`if`・`match`・`select` の腕、`catch`、`block` と `return-from`、`loop` の脱出）は移した。
  引数と仮引数も移した。合わない引数は節に包む。どの引数からも決まらない型引数があるときは、採る型が
  無いので解析はそこで止まる（型 `!` で続けると、その値を使う側が `!` について止まるエラーを出し、
  原因より先に出る）。止まるときは、引数に残った食い違いを先に報告する。
  食い違いの位置は、包まれた値に書かれた位置があればそれを採る（合わない引数を指す）。
  空の本体と期待する型の食い違いも節にする。
  `where` 境界も移した。満たさない呼び出しは特殊化せず、元の名前のまま節に包む。
  `:dyn` への変換の可否も移した。値の型が名前の型でない、トレイトを実装しない、ヒープ表現が無い、
  ニッチの `Option`、関連型が食い違う、`:dyn` からの変換で継承しない・ピンが食い違う、は値を包む。
  オブジェクト安全性、`impl` に無いメソッドや束縛されていない関連型は、トレイトや `impl` の定義の誤りなので
  止まるエラーのまま。
  網羅性も移した。網羅されない `match` は型の付いた `match` のままなので、recover モードでは穴でなく
  そのまま下ろす（腕の束縛を補完が読む）。
  `pub` も移した。`make-instance` が `pub` でないスロットを渡す誤りは節に、`defsignature` と定義の
  照合（`pub`・仮引数・戻り値・`&rest`）は `verify::signature_agrees` に。他のモジュールの非公開の名前は
  解決で見えないので、解析が止まるエラー（名前が解決できない）のまま。
  `unsafe` も移した。`unsafe` の外の C 関数の呼び出しは、許可の誤りを形の誤りより先に出すため引数を
  見ず、戻り値の型の穴を節で包む。`unsafe` の外の生のマシン語の値は型を残して包む（値になる場所ごとに
  `unsafe` が要るので、それぞれ報告する）。
  キーワードの束縛とトップレベル専用の位置は、判定を `verify::bound_name`・`verify::expression_head` に
  移したが、その場で止まるエラーのまま。どちらも書かれた形だけの規則で、後で解析するものは関わらない。
  続けると、登録されなかった定義を後ろが「束縛されていない」と報告し、そちらが先に出る。
  `setf` の場所も移した。定数への代入は代入の節を、構造体を値として持つ C 構造体のフィールドへの丸ごとの
  代入は代入する値を包む。束縛されていない変数、無いフィールド、setter が無い場所、場所でない形は
  解決や形の誤りなので、止まるエラーのまま。
- 2d. 名前を分ける。残った歩き方を解析（`analyze.rs` ほか）とし、マクロの展開、`macrolet`・
  `symbol-macrolet` の登録、`(%value-member p x)` の解決が型情報の層を通ることを確かめる。
  済み。チェッカーのモジュールを `check/analyze.rs` に改名した。`macrolet`・`symbol-macrolet` の
  スコープは `Info` の外から見えず、本体の間だけ積むのと、シンボルマクロを引くのは `Info` のメソッドが行う。
  `check_*` のメソッド名と `Checker` の型名は変えていない。

エラーの順序: 検査がフォーム全体の解析の後になるので、1 つのフォームに誤りが 2 つあるときに
最初に報告されるものが変わることがある。テストが最初のエラー文を見ている箇所は、その都度直す。

## 4. 性能

- 読むとき: ハッシュ 1 回、表の参照は多くて 2 回。

- 型の比較: 番号。型の登録: 形のハッシュ 1 回。

済み:

これから:

1. 読み方（3.3）。済み。シンボル表の子モジュールのキーをシンボルにし、型の表をシンボル表に置く。

2. 役割の分離（3.9、3.10）。型情報の層（大域の表と局所のスコープ）をチェッカーから出し、
   解析（展開・登録・解決・推論）、検査、下ろしを分ける。`(%value-member p x)` は解析が解決する。
   2a〜2d の順に進める（3.10）。
3. モジュールの木を 1 本にする。レジストリの表を節ごとの `SymRef` キーの表にし、`Path` による
   定義の識別を `(SymRef, 名前空間)` に置き換える。型変数を `Path` から分ける。
   次の順に進める。
   - 3a. 型変数を `Type::Var` にし、`Path` から分ける。済み（`780f699`）。
   - 3b. `Path` をモジュールの `NsId` と、名前がそのモジュールで読めるシンボルの組にする。済み（`4a9fc94`）。比べるのは
     ポインタ。モジュールのシンボル表は一度読めた名前の意味を変えないので、同じ節の並びから作った
     `Path` は同じものになる。節の並びは持たず、木から作る（表示とプロセスの外へ書き出すとき）。
     ダンプには節の並びで書き、並べる順も節の並びで決める（ダンプの中身が実行ごとに変わらないように）。
     定義の名前のシンボルの持ち主が定義のモジュールでないもの（固定の語彙の名前の定義）が残るので、
     この段階ではモジュールを `Path` が持つ。
   - 3c. 型の要素の名前（`型::要素`）を `Path` で作らない。作ると型と同じ名前の節が木にできる。
     フォームに書くときは型の `Path` と要素の名前から作る（`forms::member_form`）。
     書かれたままで解決前の名前（型の名前、トレイトの名前）はこの段階では `Path` のまま残す。
     段階 4 でリーダーが読んだシンボルから定義を引くようになると、文字列で解決する処理ごと無くなる。
     済み（`53dbc77`）。
   - 3d. レジストリの `Namespace` の木を、モジュールの `NsId` ごとの、名前のシンボルをキーにした
     表にする。`Registry` は `NsId` から `Namespace` を引く表を持ち、`Namespace` は子を持たない。
     どのモジュールがどのモジュールの中にあるかはシンボル表の木だけが知っていて、子の列挙は
     その木の子のうちセッションが持つものを返す（`Registry::children`）。各表（`Names<T>`）の
     キーは名前がそのモジュールで読めるシンボルで、`Path` が持つシンボルと同じものなので、
     `Path` から定義を引くときは文字列を通らない。書かれた名前で引くときはシンボルを作らずに探す
     （`symbols::find_exact`、`symbols::find_ns`）ので、定義の無い名前を尋ねてもシンボルが残らない。
     ダンプの形は変えない（モジュールの節の並びと名前で書く）。
4. 名前の解決をポインタにする（3.3）。メソッド呼び出しも書いた名前のシンボルで引く。

   する（`(defstruct Error ...)` のテストを足す）。

   - 4a. 素の名前を読むときにセッションを通す（`SessionNames::read`）。今のモジュールが `use` で
     取り込んだ名前、次に標準ライブラリが全モジュールに公開する名前（`SessionNames::export`）、
     どちらでもなければ今のシンボル表の読み方。公開するのは `std` の定義と、ルートに置いた組み込みの
     定義（`Registry::with_builtins` がルートに作ったもの）。組み込みの定義は段階 6 で `std` へ移るので、
     名前の `std` のシンボルで公開する。こうすると、`std` とルートの両方が定義する名前（`Sexpr` の

   - 4b. `shadow` と、公開されている名前を `shadow` なしで定義したときのエラー。`(shadow NAME...)` は

     定義形（`defun`・`defvar`・`defmacro`・`defstruct` など）の入口で、名前のシンボルが公開されたもの
     なら `std` の外ではエラー（`Checker::refuse_offered_name`）。局所の束縛は対象外。済み（`5ce33e1`）。
   - 4c. 解析が素の名前をシンボルで引く。今のモジュールの表、取り込み、公開の表の順。公開の表は
     公開したシンボルからその名前の定義（`std` のものとルートのもの）を引く。祖先をたどる解決と
     `std` の段を消す。パスは読んだシンボルで引く。3 つに分ける。
     - 4c-1. 素の名前の値（関数・変数・マクロ・構成子）をシンボルで引く（`Info::find_named`）。今の
       モジュールの表、取り込み、シンボルの持ち主のモジュール（マクロが運んだシンボル）、公開された
       ルートの定義、`std` の表の順で、祖先はたどらない。補完も同じ範囲を出す。解析が合成する、

       1 つずつ読む。済み。
     - 4c-2. 型・トレイト・別名・C 構造体の名前をシンボルで引く。型の式は書いたモジュールで読み
       （`parse_type` が名前空間を受け取る）、素の名前は「今のモジュールとシンボル」、`::` のパスは
       リーダーと同じ手順でたどった先のモジュールと最後のシンボルになる（`written_path`）。引くのは
       `Info::find_written` で、書いた組の定義（別のモジュールなら `pub` が要る）、なければ今の
       モジュールの名前として 4c-1 の規則で引く。型変数は今のモジュールの素の名前で型の定義が無いもの。
       トレイトも `pub` が無ければ外から使えないので `pub deftrait` を書けるようにした。子モジュールから
       ルートの定義を使うには `::` か `use` が要る。綴りが標準ライブラリの公開する名前と同じ IR の
       タグ（`scope`、`vector`、`cons` など）は `std` の語彙に移し、`%core` でもタグと定義が同じ
       シンボルになるようにした（番人は `no_core_vocabulary_member_is_spelled_as_an_offered_name`）。
       済み。
     - 4c-3. パスを読んだシンボルで引き、文字列でたどる `find_module`、祖先の連鎖、`std` の段を消す。
       解析はパスを、読んだシンボルのまま 1 段ずつたどる（`SessionNames::reached`、リーダーと同じ
       手順。先頭は今のモジュール、シンボルの持ち主のモジュール、ルート、`std` の順）。行き先は
       「たどった先のモジュールの最後のシンボル」か「型とそのメンバー」（`PathTarget`）。型の定義の
       モジュールはセッションが覚える（`SessionNames::type_home`）。段を進むときは、モジュール自身の
       子と型が `use` の取り込みより先。`use` のパスはリーダーが読まずに残すので（読み込む前の
       モジュールを名指せる）、解決するときにリーダーと同じ手順で読む。同じディレクトリのファイルを
       素の名前で名指す `use` は残した。解析が書いて検査し直すフォーム（`make-instance` の構成子、
       `loop` の `option::some` など）と `~/a::b/` の頭は、シンボルからパスを作る（`forms::name_form`、
       `forms::member_form`）。ダンプのパスは各段のシンボルの持ち主を持つ（形式 24）。`pub` でない
       定義は、そのモジュールからだけ見える（祖先と子孫も別のモジュール）。ただし段階 6 までは、
       標準ライブラリのモジュールどうしと、ルートの組み込みの非公開の定義は互いに見える
       （`Info::in_scope`）。標準ライブラリの固有メソッド 287 個と `cons-cell` のフィールドに `pub` を
       付けた（これまでは祖先の規則で全モジュールから見えていた）。IR の中のパス（`path_form`、
       `path_from_id`）と、解析が今のモジュールを綴りで持つ部分（`Info::ns`、`enter_module`、
       `mod_aliases`）は 4d で消す。
       解析が合成する型のメンバーの呼び出し（`型::メンバー`）は、パスでなく
       `(%type-member 型 メンバー)` と書く（`forms::member_form`）。パスだと、型と同じ名前の
       モジュールがあるとそちらに取られる。同じディレクトリのファイルを名指す `use` は、
       2 段以上のパス（`(use canvas::canvas)`）にも効く。`use` の取り込みはセッションの表にも
       載せる（`Registry::publish_imports`）。ダンプから戻したセッション（AOT 実行ファイルの中の
       `eval`）が取り込みを持つようにするため。ルートからのパス（`::main::f`）を `use` したとき、
       ファイルの読み込みは先頭の空の段を飛ばしてソースルートだけから探す
       （`Loader::ensure_loaded`）。空の段を綴りに入れると、読み込み中のファイルを別の名前の
       モジュールとしてもう一度読み込んでいた。`Heap::names` のロックは同じスレッドが二度
       取ると止まったままになるので、ガード（`NamesGuard`）がその場で panic させる。済み。
   - 4d. 文字列で解決する処理の残りを消す。解析は今のモジュールを `NsId` で持つ（`Info::ns`）。
     モジュールに入るときは今のモジュールから子を 1 段ずつたどり、出るときは入る前のモジュールに
     戻す（`in-module` には閉じる形が無いので、戻り先を積む `Info::ns_base`）。特殊化の
     テンプレート、トレイトの既定の本体、ブランケット実装、`#[test]` の関数、`use` したモジュール
     （`mod_aliases`）も、モジュールを `NsId` で持つ。ダンプには `Path` と同じく節の並びで書く
     （`types::ns_as_segments`）。IR の中の定義の名前は、リーダーが `::a::b::name` を読んだのと
     同じ、ルートからのパスで書く（`core::path_form`）。先頭がルートの空の名前のシンボル、続いて
     木のキーのシンボル、最後に名前のシンボル。ルートの定義も `::name` で、裸のシンボルにしない。
     裸の名前は読むモジュールのシンボルになるので、印字した IR をどのモジュールで読み直しても同じ
     定義を指す。読むのは `core::path_value` だけで、先頭がルートでないものは定義の名前として
     受け取らない。手書きの IR のテストも `::f`、`::m::f` と書き、`%core` でそのまま読む。
     組み込み関数の値が持つ受け手の型のパスも同じ形で、`core::path_form` で書き `core::path_value` で読む。シンボルの意味が変わったので、
     ダンプの形式は 25。型キーの文字列から `Path` を作り直す処理（`type_key`、評価器の表）は
     段階 5 と 7 で消す。
5. 実行時の型の識別を `TypeShape` の登録にする（3.5）。型キーの文字列、`ConcreteNames` の
   切り戻し、手書きのキー、印字の表の文字列キー、`rt_print_*` の文字列登録を消す。
   `NameView` を定義のシンボルから作る形に書き直す。島と成果物を再生成する。
   型キーの文字列は今、4 つの経路を通っている。IR（`construct`・`pat-ctor`・`dyn-new` の
   キーと、組み込み関数の `ret_key`）、コンパイル済みコード（`rt_data_new`・`rt_struct_new`・
   `rt_hashtable_new` などが先頭の引数で文字列を受け取り、その場で intern する）、ランタイムの
   組み込み（`"vector<string>"` などの手書きのキー）、印字の表。切る処理（`split_type`、
   `type_arg_list`、`split_fn_type` など）は合わせて 60 か所ほど。
   表を先に形にすると、IR とコンパイル済みコードが運んでくる文字列を形に戻す処理（文字列を切る
   読み取り器）が要る。それを作らないために、運ぶ側を先に変える。
   - 5a. IR とコンパイル済みコードが型を形で運ぶ。キーの文字列の欄を、型を書いたフォーム
     （`(type-named ::gen (type-named ::i32))` のように、定義の名前は 4d と同じルートからの
     パス）にする。コンパイル済みコードはそのフォームを定数として `rt_*` に渡す。フォームから
     表の識別を引く処理は `typelisp-mem` の 1 か所に置き、評価器もランタイムもそれを呼ぶ。
     表はこの段階ではまだ文字列で引く。
     フォームの語彙は `type-named`・`type-fn`・`type-dyn`・`type-ptr`・`type-cstruct`・
     `type-param`（欄の型の雛形の中の、持ち主の型の N 番目の引数）・`type-var`（ジェネリックな
     定義の本体の中の型引数。本体は下ろすが実行しない）・`type-unit`・`type-never` で、
     `%core` にある。書くのは `core::type_form`、読むのは `typelisp_mem::type_key_of_form`。
     IR の欄は済み（ダンプの形式は 26）。`DynNew` と `BoxOption` はキーを持たなくなった（値の型
     そのものだった）。コンパイル済みコードは、ブリッジが `quoted_form` でフォームを実行時に組み
     直す節にして `rt_*` に渡し、ランタイムは `type_key_of_form` で読む（ABI 0.3.16）。
     ブリッジの中で表を引く `:dyn` の vtable の表だけが、まだキーの文字列で引く。
   - 5b. 表を形にする。`TypeShape` と `Heap::intern_type`（形 → `TypeId`）を置き、
     `TypeKeyId` を `TypeId` にする。5a の 1 か所はフォーム → 形になる。型から作る側
     （チェッカーの `Type`、ランタイムの手書きのキー、固定の型）も形を作る。型の名前の文字列は
     形から組み立てる表示だけにする。
     済み。形は `typelisp_mem::TypeShape`、表は形でだけ引く（文字列から番号を引く手段は無い）。
     型の名前は登録のときに形から 1 度組み立てる表示で、綴りは前のキーと同じ。チェッカーの型は
     `type_key::type_id`、ランタイムの手書きの型は Rust の定数で木を書く `TypeSpec`
     （`Heap::intern_spec`）で形にする。評価器・スケジューラ・組み込み関数の値は型を `TypeId` で
     運ぶ。ダンプの形式は変わらず、ABI は 0.3.17。まだ文字列で引くのは、欄の型の雛形
     （`field_key_template`）、`:dyn` の vtable の表、`dyn-new` の `type_key_field`。
   - 5c. 文字列を切る処理を形を読む処理にする。印字の表のキーと `rt_print_*` の登録を番号か
     シンボルにする。
     済み。型の表をプロセスに 1 つにした（3.5）。欄の型の雛形は `Param` を含む形の `TypeId`
     （`type_key::field_template`）で、値の型引数で埋めるのは `typelisp_mem::instantiate`。
     印字の表（変種名・欄の雛形・欄の名前）は定義（`NsId` と `SymRef` の組）で引き、
     `:dyn` の vtable の表と `dyn-new` は `TypeId` で引く。実行ファイルは使う型の形を語の列
     （`typelisp_mem::type_words`）で埋め込み、起動時に `rt_types_define` が番号の表にして、
     `rt_print_*` の登録はその表の番号で行う（3.6 の起動時の表を 5d から前倒しした）。
     ABI は 0.3.18。文字列のキーで残るのは、FFI の型（`defffi` の宣言とコールバックの署名、
     `rt_ffi_callback_register`。5d）と `print-object` の表（`value_key_for_method`。5e）。
   - 5d. コンパイル済みコードがフォームでなく番号を使う。JIT は番号を定数にし、AOT は起動時に
     形の表から番号を埋める大域の表を読む（3.6。表を作る `rt_types_define` は 5c で入った）。
     FFI の型も番号にする。島を 2 回作り直す。
     前半は済み。ブリッジは型を `(type-ref N)`（N はこのプロセスの型の番号）で出し、島はそれを
     モジュールの型の表から読む命令（`load-type`）にする。表を埋めるのは `compile::type_table` で、
     このプロセスに載せるモジュール（JIT）では番号を並べた定数の表に、外へ出すモジュール（島・
     prelude・fasl・実行ファイル）では型の形の語の列と、それを `rt_types_define` で表にする
     初期化関数（`typelisp_types_init.<モジュール名>`）にする。初期化関数は `jit_engine` と
     実行ファイルの `main` の先頭が呼ぶ。ビットコードはすべて `type_table::write_bitcode` で
     書き出す。計画の「JIT は番号を定数に」からのずれ: 命令に番号を直接書かず、定数の表を読む。
     prelude と島のビットコードは JIT にも AOT にも載るので、どちらでも同じ書き方にするため。
     最適化をかけない JIT（-O0）では表を読む命令が残る。`TypeId` の語はタグ付きの整数
     （`TypeId::word`）。ABI は 0.3.19。
     後半（FFI）も済み。`defffi` の IR は C の型を型のフォームで持ち、`FfiDecl` の型は
     `TypeId`。コールバックは関数の定義（`NsId` と `SymRef`）と関数型の `TypeId` の組で識別し、
     呼び出し側は `(quote PATH)` と `(type-value TYPE)` を渡す。`type-value` は組み込みに型を
     値として渡す IR の節で、評価器は型の番号を、ブリッジは `(type-ref N)` を返す。実行ファイルは
     定義を `type_words::definition_words` の語の列で埋め込み、`rt_ffi_callback_register` で
     登録する。C メモリ層（`c_mem`）は型を `TypeId` で持ち、`c-alloc` は配置を
     `SIZE ALIGN OFFSET TYPE ...` の引数で受け取る。パスから定義を引く処理は
     `symbols::definition_of_path` の 1 か所。ダンプの形式は 27、ABI は 0.3.20。
   - 5e. 単型化した定義を `(元の定義のシンボル, [TypeId])` の表で識別し、`ConcreteNames` の
     切り戻しを消す。`NameView` を定義のシンボルから作る。
     前半は済み。単型化した定義は表（`typelisp_mem::specialization`）で、元の定義（関数なら
     所属モジュールと名前のシンボル、メソッドなら型の定義とメソッド名のシンボル）と型引数の
     `TypeId` の列から引く。名前はどの表にも載らないシンボル（`symbols::unlisted`）で、綴り
     （`unwrap <int>`）は表示とリンク名のためだけにある。チェッカーはメソッド名を IR まで
     （`Node::Assoc`・`MethodRef`・vtable の表・`defmethod`・`CompileTarget::Method`）シンボルの
     まま運ぶ。ダンプは単型化のシンボルを元の定義と型引数の形（`owned_form::OwnedSym`・
     `OwnedType`）で書き、読むときに表から同じシンボルを引く（`Path` の serde も同じ形）。
     `print-object` の振り分けは値の型の形から表を引き、実行ファイルの登録と印字側の表
     （`rt_print_object_method`）は `TypeId` で引く。インタプリタの `FnDef` は自分の定義
     （`CompileTarget`）を持ち、`~/name/` とフレームの警告は名前を切らずに、定義から作った名前と
     照合する。コンパイル済みコードは引用したシンボルを綴りから作り直すので、単型化した関数を
     C のコールバックに渡すときは、それを呼ぶ定義を別に作る。ダンプの形式は 28、ABI は 0.3.21。
     チェッカーの中のメソッドの表（`AdtDef::assoc`・`insts`・テンプレート）はまだメソッド名の
     文字列で引く（段階 7）。名前を切る処理で残るのはダンプのキー（`dump::parse_path`・
     `parse_method_key`。段階 8）。
     後半も済み。`NameView` は今のモジュールの `NsId` と、取り込んだ定義（`NsId` と `SymRef`）から
     取り込み名への表を持つ。定義の表示は節の木で決め（今のモジュールか、取り込んだか、その下か）、
     型の表示は型の形をたどる（`NameView::type_name`。型の表の表示と同じ `type_shape::display` に
     定義の書き方を渡す）。文字列は最後に組むだけで、切らない。実行ファイルはモジュールを
     `type_words::ns_words`、取り込んだ定義を `definition_words` の語の列で
     `rt_print_name_module` / `rt_print_name_import` に渡す。ABI は 0.3.22。
6. `std` を子モジュールに分け、組み込み型を移す（5 節）。`std::prelude` を作り、テスト・例に
   `use` を足す。振る舞いを変えない順に次の 5 つに分ける。
   - 6a. 再公開 `(pub use PATH)`。取り込んだ定義を、そのモジュールを通るパスからも引けるようにする
     （`m::name` が `m` の再公開を指す）。モジュールの表に再公開の印を持ち、ダンプにも書く。
     済み。印は `Namespace::reexports`（取り込みの名前の集合）で、`Info::find_written` が
     ほかのモジュールへのパスでたどる。モジュールの再公開はエラー。ダンプの形式は 29、ABI は 0.3.23。
   - 6b. ルートにある組み込みの型と構成子を `std` へ移す（子モジュールへの振り分けは 6d）。
     6a の後で順番を入れ替えた。ルートの組み込み型（`vector` `string` など）と `std` の同名の関数は
     別のモジュールの定義で、1 つの名前を 2 つのモジュールへつなぐ表（`Registry::offered_root`）が
     要った。取り込みの表は 1 つの名前に 1 つのパスなので、`std::prelude` の再公開では表せない。
     同じモジュールに移せば、型と関数は 1 つのシンボルで引ける。
     済み。`offered_root` を消し、`Registry::with_builtins` は最初から `std` に作る。組み込み型かの
     判定は `Path::is_std`（`std` 直下か）。型のキー（表示とリンク名）は `std::int` になる。スカラ型
     （`Type::I32` など）のキーも同じく `std::i32` で、名前そのもの（`int->u8` の変換名、整数の幅）は
     `Type::scalar_name` から読む。利用者に見せる型は、キーでなく `Type` の表示か `NameView` で書く。島が
     組み込みのメソッドを自分で下ろすための `assoc` の型名は、`std` の型なら局所名、それ以外は空
     （`core_bridge::builtin_receiver`。ルートの型は名前だけで書かれるので、組み込みの名前を
     `shadow` して定義すると取り違える）。ABI は 0.3.24。
   - 6c. `std::prelude` を作り、素の名前の最後の引き先（リーダーの 3 番目、解析の
     `Info::find_named` の最後）を `std::prelude` の再公開にする。この段階では今どこからでも
     見えるもの（`std` の定義）を全部再公開し、振る舞いは変えない。
     済み。`std::prelude` は `std` の子モジュール（`types::prelude_ns`）で、`Registry::reexport_std_in_prelude`
     が `std` の定義を 1 つずつ `(pub use std::name)` と同じ別名と再公開の印にする。`with_builtins` の最後と、
     フォームを 1 つ検査するたびに呼ぶ（`std` を読む途中で `%internal` のフォームも読むため）。リーダーが
     取り込みなしで読む名前（`publish_names`）、`find_named` の最後、補完、型の表示名は、この再公開から
     読む。別名表のキーは `std::prelude` 自身のシンボルなので、`find_named` の最後で見つかるのは語彙の
     名前（どのモジュールでも同じシンボル）だけで、ほかの名前はリーダーが定義のシンボルを渡すため
     シンボルの所属で見つかる。ダンプには `std::prelude` の表も入る。
   - 6d. prelude のソースと組み込みの型・関数を `std` の子モジュール（`std::primitive` ほか）に分ける。
     途中。組み込みも prelude のソースも `std` の子モジュールに置けるようにした。`std::prelude` が再公開する
     のは `std` の定義と `registry::PRELUDE_MODULES` に挙げた子モジュールの定義（6e で 5 節の範囲に狭める）。
     同じ名前を 2 つのモジュールで定義すると `reexport_std_in_prelude` が止まる（`std::lazy` のように
     `use` して使うモジュールは挙げない）。コンパイル済みコードが呼ぶ組み込みの置き場所は
     `externs::builtin_homes`（レジストリの `builtin` 関数と、シグネチャを持たない下ろし先の
     `registry::lowered_builtins`）。最初に乱数を `std::random` へ移した。ABI は 0.3.25。
     次に時刻を `std::time` へ移した。ランタイムが組み立てる型の定数表（`TypeSpec`、`BUILTIN_TYPES`）は
     モジュールを `StdModule`（`std` の下の段の並び。1 段ずつたどる）で書く。子モジュールのマクロの雛形が
     後で定義される `std` の名前を使うときは `std::` を付けて書く（付けないと子モジュールのシンボルになる）。
     ABI は 0.3.26。
     次に `room` `dribble` `heap-info` を `std::repl` へ移した。`std::prelude` の名前を定義するときに
     `shadow` を求めないのは `std` とその子モジュール（`types::in_std`）。ABI は 0.3.27。
     次に環境の関数を `std::env` へ、時刻帯の下請けを `std::time` へ移した。ABI は 0.3.28。
     次にソケットの型と関数を `std::net` へ移した。組み込みのエラー型（`NetError` `FileError` など）は
     まだ `std` にあり、まとめて移す。
     次に `Task` `Thread` と `sleep` `yield` を `std::thread` へ、`Chan` と `WaitGroup` `Mutex` `Context`
     などを `std::sync` へ移した。`std` は `std::prelude` が再公開する子モジュールの名前を取り込む
     （各名前の `(use PATH)` と同じ）。`std` の外で `Chan::new` と書くと、先頭の `Chan` は
     自分のモジュール・ルート・`std` の順に探され、`std` の取り込みとして見つかる。
     `Path::is_std` は `std` とその子モジュールの定義を指す（`types::in_std`）。型とトレイトの名前が
     `std` の木で重ならないことは `reexport_std_in_prelude` が確かめる。組み込みの型や関数かどうかは
     `Path::std(..)` との比較ではなく `types::path_is_builtin`（型）と `Path::std_builtin_name`（関数）で
     問う。ABI は 0.3.29。
     次にシンボルの関数（`gensym` `intern` `symbol->string` `string->symbol` `keywordp`）を `std::symbol` へ、
     `exit` を `std::process` へ移した。ABI は 0.3.30。
     次に `Hash` と `sxhash-string` `*sxhash-mask*` を `std::hash` へ移した（ABI は変わらない）。
     次に `Error` と `SimpleError` `WrappedError` `wrap-error` `describe-error` `assert` `assert-eq` `warn`
     を `std::error` へ移した。チェッカーや `typl test` が組み立てる式で標準ライブラリの名前を指すときは、
     `std` で新しくシンボルを作らず、`std` で読んだシンボル（`SessionNames::read(NsId::STD, ..)`）を使う。
     マクロの展開などで持ち込まれたシンボルは、属するモジュールでの意味（定義か、そこでの取り込み）で
     解決する（`Info::find_named`）。組み込みのエラー型（`ParseIntError` など）は、それぞれの分野と一緒に移す。
     次に `Eq` `Ord` `equal` `equalp` を `std::cmp` へ、算術のトレイトを `std::ops` へ移した（トレイトの定義だけを
     移し、各型への impl は `std` に残す）。文書にない名前を探す `root_names_documented_test` は、`std` とその
     子モジュール（`std::%internal` を除く）を数える。ABI は 0.3.31。
     次に `read` とリーダーマクロ・`read-sexpr` などを `std::reader` へ、`eval` `macroexpand` を `std::eval` へ
     移した。評価器が読む `*read-eval*` も `std::reader` で名指しする。ABI は 0.3.32。
     次に `pi` `parse-int` `parse-float`、バイト指定子の関数（`byte` `ldb` `dpb` など）、`boole` とその定数、
     数値の限界の定数を `std::num` へ移した。型ごとのメソッド（`abs` `gcd` など）は型の impl に残す。ABI は 0.3.33。
     次に繰り返しと束縛のマクロ（`while` `until` `while-let` `dotimes` `dolist` `do` `if-let` `->`
     `destructuring-bind` `prog1` `setq` `psetf` `psetq` `dlet` など）を `std::control` へ、`digit-weight`
     `digit->char` `name->char` を `std::char` へ、`left-trim` `right-trim` `trim` を `std::string` へ移した
     （ABI は変わらない）。
     次に `Iter` と `doiter` `map` `filter` `collect` `foldl` `foldr` を `std::iter` へ、`Iter` の上の CL の列と
     リストの関数（`length` `append` `nth` `find` `sort` `assoc` `first` `rest` `remove` `union` など）を `std::seq`
     へ移した（ABI は変わらない）。各型への `Iter` の impl と、型ごとの反復子（`vector-iter` など）は型と一緒に移す。
   - 6e. `std::prelude` の再公開を 5 節の範囲に狭め、テスト・例・文書に `use` を足し、
     `Info::in_scope` の広い規則を狭める。`std::prelude` の名前を定義するときの `shadow` を要求する。
7. 局所の束縛と IR の変数を `SymRef` に、定義を指す IR を定義のシンボルに（島の再生成は 2 回）。
8. ダンプ・fasl を 3.6 の形に。
9. 利用者向け文書（日本語の原本、翻訳）。
