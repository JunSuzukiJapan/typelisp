# 型チェッカーの作り直し — 洗い出しと設計方針（案、2026-11-08）

## 1. 目的

継ぎはぎの修正が重なった型チェッカーを、小さい機能ごとに分かれた、見通しのいい設計に作り直す。
最初の作業量より、その後の追加・修正にかかる時間を短くすることを優先する（ユーザー決定）。

## 2. 今のチェッカーの境界

作り直しの間、外との境界は変えない。境界を固定すれば、評価器・コンパイラ・島・LSP には手を入れずに済む。

| 方向 | 中身 |
|---|---|
| 入力 | リーダーが読んだフォーム（`Value`）。最上位フォームを1つずつ受け取る |
| 出力 | core IR（`TopLevelForm = Value`、cons セルの木）。`Interp::exec` と島がこれを読む |
| 公開の入口 | `check_form` / `check_form_at`、`publish_names`、`finish_unit`、モジュールの出入り（`enter_module` など）、REPL とダンプ用の `signature` / `capture_delta` / `apply_delta`、LSP 用の `take_type_uses` / `take_errors` / `expr_type` / `registry` |
| 内部の流れ | フォーム → 解析（`Node` の木、`Checked`）→ 変換（`lower.rs`、`Node` → core IR） |

`Node` と `lower.rs` はチェッカーの内側にある。作り直しの対象に含めるかは 6 節で決める。

core IR のほかに、登録表と型もチェッカーの外から読まれている（2026-11-08 に確認）。

| 読む側 | 読むもの |
|---|---|
| ダンプ（`dump.rs`） | `Registry` 全体（`AdtDef`・`FnSig`・`TraitDef` など、serde で書き出す） |
| LSP（`src/bin/lsp.rs`） | `registry()` の `def_locs` と `docs`、補完の候補 |
| コンパイラ（`abi_signature.rs`・`llvm_builtins.rs`・`externs.rs`） | `Registry::with_builtins()`、組み込みの `AdtDef`・`FnSig` |
| 評価器（`interp.rs`） | 組み込みの型定義（`builtin_sum_defs`、`task_of` など） |
| 実行時の型の識別（`type_key.rs`） | `Type`（型変数は位置 `TypeShape::Param(i)` に直して扱う） |

`Type::Var` を直接書いている場所は、チェッカーの外では `type_key.rs`・`types.rs`（表示）・`interp.rs:766` の 3 ファイルだけである。

## 3. チェッカーが受け持つ機能

規模は `check/` 全体で約 3 万行。そのうち `analyze.rs` 1 ファイルが約 1.8 万行で、メソッドが約 430 個ある。

### 3.1 最上位フォーム

`defstruct` `defenum` `deftrait` `deftype` `impl`（`impl<T>` を含む）`use` `pub` `unsafe`（`def-c-struct`）。

### 3.2 式の特殊形

`if` `let` `let*` `progn` `unsafe` `c-alloc` `c-ref` `c-deref` `setf` `incf` `decf` `rotatef` `shiftf`
`loop` `block` `return-from` `catch` `throw` `unwind-protect` `break` `return` `list` `format`
`print` `println` `eprint` `eprintln` `pprint` 系 `pprint-logical-block` `lambda` `labels` `macrolet`

`compile` `documentation` `ed` `trace` `untrace` `step` `disassemble` `source-file` `quote` `quasiquote` `:dyn`。

### 3.3 横断する仕組み

- 名前解決（モジュールの木、`use`、パス、メソッドの受け手）
- 型の構文解析と正規化（別名の展開、未定義の型名を断る）
- 登録表（`Registry`：関数・型・トレイト・impl・別名・ドキュメント・定義位置）
- ジェネリック（単型化の要求・テンプレート・特殊化名）
- トレイト（境界の検査、関連型、ブランケット impl、デフォルト本体、`:dyn` の表）
- マクロ展開（`defmacro`、`macrolet`、コアマクロ）
- 表現の分類（`Repr`、Option のニッチ、`Sexpr` への包み方）
- LSP 向けの記録（型の使用位置、ローカル参照、式の型、エラー回復）
- REPL・ダンプ向けの差分
- `#[test]` の収集、FFI コールバックの持ち上げ、`format` の書式エンジン、`loop` の DSL

## 4. 見つかった設計上の問題

### 4.1 型変数を名前で扱っている

`AdtDef.params` は名前の列で、フィールドやメソッドのシグネチャは `Type::Var("T")` の形で保存される。
ほかの定義は、受け手や対象に書かれた名前を宣言側の名前に書き直してから登録される
（`check_defmethod_in_form` の `owner_rename`、`check_impl_form` の `rename`）。

呼び出し側では、型の側のパラメータとメソッド自身のパラメータを、名前をキーにした 1 つの置換表に入れている。
名前がぶつからないようにするための検査が、誤って正しいコードを断っている。

```lisp
(defstruct Pair<T, U> (first T) (second U))
(impl Pair<A,B> (defmethod mk<T> (self (x T)) T x))
;; error: the method's own type parameter `T` has the name of a type parameter of `Pair`
```

実行時の型の識別（`type_key.rs`）は、すでに位置（`TypeShape::Param(i)`）で扱っている。
名前に頼っているのはチェッカーだけである。

### 4.2 書いただけで型変数が宣言されたことになる

`written_type_vars` が、`impl` の対象や `defmethod` の受け手に書かれた未知の名前を、すべて型変数として宣言扱いにする。
`(impl<T> ...)` の頭に書いた宣言は、ブランケット impl のとき以外は使われていない。
型変数は宣言した場所でだけ生まれる、に直す（ユーザー決定）。

```lisp
(impl<T,U> Pair<T,U> ...)
(defmethod pair-first<T,U> ((p Pair<T,U>)) T (first p))
```

### 4.3 ジェネリックな本体を 2 回、別の規則でチェックしている

ジェネリックな本体は、まず型変数を抽象のままチェックし、インスタンス化のたびに元のフォームを具体型でチェックし直す。
2 回のチェックは規則が食い違う。

- 抽象のチェックは Rust と同じく境界を要求する（`(+ x 1)` は「`T` に `+` が無い」でエラー）。
- 具体型でのチェックは、境界が無くても具体型で通れば通る。
- 抽象のチェックがエラーを出しても、テンプレートは登録に残る。そのため REPL では、エラーになった定義がそのまま呼べる（4.4）。
- 抽象のチェックだけが断る書き方があった。ジェネリックな本体の中の `(format false "~a" x)` がそれで、`x : T` を `Sexpr` に包めないとして断っていた（2026-11-08 に、型変数のときは包み方を具体型のチェックへ回すよう修正済み）。

### 4.4 チェックに失敗した定義が登録に残る

`check_defun` などは、自己再帰のためにシグネチャとテンプレートを本体のチェックより先に登録する。
本体のチェックが失敗しても登録を取り消さない。ファイル実行は最初のエラーで止まるので表に出ないが、REPL と LSP では、エラーになった定義が残って呼べてしまう。

```lisp
(defun inc<T> ((x T)) T (+ x 1))   ; error: no method `+` for type variable `T`
(inc 41)                           ; => 42
```

今のチェッカーでは直さず、新しいチェッカーで 5.3 の仕組みにより直す（ユーザー決定）。

### 4.5 ファイルと状態が大きすぎる

- `analyze.rs` 1 ファイルに、最上位フォーム・式・パターン・ジェネリック・トレイトがすべて入っている。
- `Checker` は 35 個、`Info` は 7 個の状態を持つ。その多くが `Cell` / `RefCell` で、チェックの途中で書き換わる
  （ループの段、ブロックの段、`unsafe` の深さ、推論の試し打ち `infer_probe` と穴の数 `probe_holes`、特殊化の待ち行列、型変数の束縛 `type_var_bindings` など）。
- 最上位フォームの振り分け表が、`pub` 付きと無しで 2 つある（`check_one_form` 内と `check_pub`）。

### 4.6 `Self` と関連型をソースの字面で置き換えている

`impl` の項目は、チェックの前に、読んだフォームの中のシンボル `Self` と関連型の名前を、対象の型の書かれた形に置き換えて作り直される（`subst_value`、`subst_method_item`）。
型の置き換えを、型ではなく構文の上でしている。トレイトのシグネチャも `Type::Var("Self")` と関連型の名前で保存され、名前で突き合わされる。

## 5. 設計方針（案）

### 5.1 小さい機能ごとにモジュールを分ける

1 つのモジュールは 1 つの機能だけを受け持ち、ほかのモジュールとは決まった型（`Type`、`Checked`、登録表の読み書き API）だけでやりとりする。
分け方の案を示す。

| モジュール | 受け持ち |
|---|---|
| `types` | `Type` の定義、構文解析、正規化、置換、単一化 |
| `scope` | 型変数の宣言とローカル変数の環境（親フレームを共有する連鎖） |
| `resolve` | 名前解決（モジュールの木、`use`、パス） |
| `registry` | 登録表。書き込みは 1 つの最上位フォームの単位でまとめて確定する |
| `toplevel/*` | 最上位フォーム 1 種類につき 1 ファイル（`defun.rs`、`defstruct.rs`、`impl.rs` …）。振り分け表は 1 つ |
| `expr/*` | 特殊形をまとまりごとに 1 ファイル（制御、束縛、代入、脱出、出力、関数、`match` …） |
| `generic` | インスタンス化と特殊化 |
| `traits` | 境界の検査、関連型、ブランケット impl、`:dyn` の表 |
| `macros` | マクロ展開 |
| `repr` | 表現の分類、`Sexpr` への包み方 |
| `ide` | LSP 向けの記録 |
| `lower` | `Node` → core IR |

### 5.2 型の表し方

- 型の側のパラメータは位置で持つ。登録表のシグネチャには、利用者が書けない位置の印で保存する。
- 型変数は宣言（`defun f<T>`、`defstruct Pair<T,U>`、`impl<T,U>`、`defmethod m<T,U>`、`deftrait` の `(:type ...)`）からだけ生まれる。
- メソッドの型パラメータは、宣言の頭に書いたものだけになる。受け手の型 `Pair<T,U>` は、ほかの引数と同じ「パラメータの型」として扱う。
  型の側のパラメータとメソッド自身のパラメータという 2 種類の区別が無くなり、名前がぶつかる検査も要らなくなる。

### 5.3 登録は成功してから確定する

1 つの最上位フォームの登録は、まとめて仮に書き込み、チェックが成功したときだけ確定する。失敗したら全部捨てる（4.4 の解消）。
自己再帰は、仮の書き込みが同じフォームの中から見えることで支える。

### 5.4 ジェネリックのチェック（ユーザー決定）

本体を 1 回だけ、境界にもとづいてチェックする（Rust と同じ）。インスタンス化は、チェック済みの木の型を置き換えて作る。
表現によって変わる選択（`Sexpr` への包み方など）は、置き換えた後に決まる節点として残す。

これを採ると、今「具体型では通る」だけで境界を書いていないジェネリックな定義は、エラーになる（4.3）。

## 6. 進め方（ユーザー決定）

1. この文書で設計を決める。
2. 新しいチェッカーを今のものの隣に置く。prelude を読み込まないテストから順に、新しいチェッカーでも通るようにしていく。
   環境変数 `TYPELISP_TYPECK` を空でない値にすると、今のチェッカーの `check_form_at` が、すべてのフォームを新しいチェッカー（`crate::typeck`）に渡す。
   新しいチェッカーがまだ扱えない形は `unimplemented!()` で止まる。prelude はダンプから読み込まれ、チェッカーを通らないので、スイッチを立てても REPL は起動する。
   prelude はほぼすべての機能を使うため、prelude を読み込むテストを新しいチェッカーで回せるのは、移植の終盤になる。
3. `Node` と `lower.rs` は、最初は今のものを使い回す。直すべき点が見つかったら、切り替えのあとの次の段階で扱う。
4. 全テストが新しいチェッカーで通ったら切り替え、古いチェッカーを丸ごと消す。
   切り替えた（2026-11-11）。スイッチは無くなり、今のチェッカーの `check_form_at` は常にすべてのフォームを新しいチェッカーに渡す。
   古いチェッカーのチェック本体を消した（2026-11-12）。続いて、組み込みの定義を新しい登録表の形で書き直し、古い登録表（`check::registry`）・写す仕組み（`typeck::bridge`）・`Type::Var` を消した（2026-11-12、7.7・8.3）。
   続いて、ドライバが持つ `check::Checker`（新しいチェッカーへ渡すだけの層）を `typeck::checker::Checker` 1 つにまとめ、`check/analyze.rs` を消した（2026-11-12）。`check` に残るのは、core IR の組み立て（`core`・`forms`・`lower`・`repr`・`freevars`・`fold`）、断るときの文（`verify`）、`loop` の DSL、エディタが読むもの（`locate`・`semantic`）、`CompileTarget` である。

## 7. `types` と `scope` の設計（案）

### 7.1 型パラメータは「どの定義の何番目か」で表す

`Type::Var(String)` をやめ、次の 2 つに置き換える。

```rust
/// 宣言された型パラメータ。どの定義の何番目かで識別する。
pub struct TypeParam {
    pub owner: ParamOwner,
    pub index: u32,
    /// エラーメッセージに出すための、宣言に書かれた名前。比較とハッシュには使わない。
    pub name: SymRef,
}

pub enum ParamOwner {
    /// 関数・型・型の別名・トレイト。定義の Path で識別する。
    Def(Path),
    /// メソッド。型の Path とメンバーのシンボルで識別する。
    Method(Path, SymRef),
}

enum Type {
    ...
    Param(TypeParam),
    /// 呼び出しの推論で使う穴。チェッカーの中だけで使い、登録表と出力には出さない。
    Infer(u32),
}
```

- 定義ごとに持ち主が違うので、別の定義の型パラメータとは名前が同じでもぶつからない。
  `Pair<T,U>` の `T`（`Param{Def(Pair), 0}`）と、メソッド `mk<T>` の `T`（`Param{Method(Pair, mk), 0}`）は別物になる。
- 型の定義のフィールドは、その型の `Param{Def(型), i}` で書く。`p : Pair<A,B>` のフィールドの型は、`i` 番目を `A`・`B` に位置で置き換えて求める。
- 置き換えは「持ち主と番号 → 型」の表で、1 回だけ同時に行う。置き換えた結果をもう一度置き換えることはしない。

### 7.2 呼び出しの推論は穴で行う

ジェネリックな関数やメソッドを呼ぶときは、呼ばれる側のシグネチャの型パラメータを、新しい穴 `Infer(n)` に置き換えてから引数と突き合わせる。
呼ぶ側の型パラメータは、決まった型（中身の分からない定数）として扱う。

自己再帰（`f<T>` の中で `f` を呼ぶ）でも、呼ばれる側は穴に置き換わるので、呼ぶ側の `T` と混ざらない。
ラムダの引数のように、期待する型を先に渡したい場所にも、穴を含んだ型をそのまま渡せる。

穴は 1 つの呼び出しの中で解き終える。解けない穴が残ったら「型パラメータを推論できない」エラーにする。

### 7.3 メソッドと impl の型パラメータ

- `(impl<T,U> Pair<T,U> ...)` の頭の `T,U` は、中の各メソッドの型パラメータの先頭に並ぶ。
  `(defmethod m<V> ...)` なら、`m` の型パラメータは `[T, U, V]`（持ち主は `Method(Pair, m)`）になる。
- 受け手の型 `Pair<T,U>` は、ほかの引数と同じ「パラメータの型」である。メソッドを呼ぶときは、受け手も含めて 7.2 の推論で型パラメータを決める。
- `impl` の外の `(defmethod m<T,U> ((p Pair<T,U>)) ...)` も同じ形になる。

### 7.4 トレイトの `Self` と関連型

トレイトのシグネチャの中では、`Self` を `Param{Def(トレイト), 0}`、`k` 番目の関連型を `Param{Def(トレイト), 1 + k}` として扱う。
`impl` は、ソースの字面を置き換えるのではなく（4.6）、登録済みの型の上で `Self` を対象の型に、関連型を `(:type ...)` で決めた型に、位置で置き換える。

### 7.5 型変数の環境

- 型変数は、宣言（`defun f<T>`、`defstruct Pair<T,U>`、`defenum`、`deftype`、`impl<T,U>`、`defmethod m<T>`、`deftrait` の `Self` と `(:type ...)`）からだけ生まれる。
- 型を構文解析するときは、裸の名前をまず型変数の環境で探し、無ければ型として名前解決する。どちらにも無ければ「未定義の型」エラーにする。書いただけで宣言扱いになる経路（`written_type_vars`）は作らない。
- 環境は、親の枠を参照で共有する連鎖にする。枠を書き換えたり、複製したりしない。
- `:where` の境界は、型変数の名前ではなく `TypeParam` をキーにする。

### 7.6 境界

- `:where` の境界は、型パラメータを宣言した枠の内側の枠（`TypeScope::bound`）に置く。型パラメータが見えるところでは、その境界も見える。
- ジェネリックな本体で、受け手の型が型パラメータ `T` のメソッド呼び出しは、`T` の境界のトレイトとそのスーパートレイトからメソッドを探す。型は、トレイトのシグネチャの `Self` を `T` に、関連型を境界が固定した型に、位置で置き換えたもの。固定していない関連型は、`T` のそのトレイトの関連型を表す射影の型 `Type::Proj`（Rust の `<T as Iter>::Item`）にする。定義の中では、同じトレイトの同じ関連型で `Self` が同じ射影の型とだけ一致し、何も分からない型として扱う。特殊化のとき、lowering が型を書く入口（`Lowering::settle`）で、`Self` が具体型になった射影の型を、その型の `impl` が決めた関連型に置き換える（`bounds::projected`）。
- そのような呼び出しは `TraitCall` ノードにする。特殊化した木を下ろすとき、受け手の型は具体型になっているので、その型の `impl` のメソッドの呼び出しにする。
- 呼び出しの位置では、型引数が境界を満たすかを確かめる。型引数がまだ穴なら、フォームをチェックし終えたところで確かめる。境界が固定した関連型は、`impl` が決めた型（`TraitImpl::assoc`）と単一化する。固定から型引数が決まるので、フォームの終わりの確認は、型引数が決まらないエラーより先に、進まなくなるまで繰り返す。型引数が呼び出し側の型パラメータなら、その境界（かそのサブトレイトの境界）が要る。具体型なら、その型へのトレイトの `impl` が要る。

### 7.7 並べて置く期間の扱い

`Type` は古いチェッカーと新しいチェッカーで共有する。

- `Type` に `Param` と `Infer` を足す。古いチェッカーは `Var` を使い続け、新しいチェッカーは `Var` を使わない。切り替えのときに `Var` を消す。
- 登録表は新しいチェッカー専用のものを別に作る。組み込みの型と関数の定義（今は `registry.rs` に `Var` で書かれている）は、並べて置く期間だけ、古い定義を位置の表し方に直す変換で読み込む。切り替えのときに、組み込みの定義のソースを新しい表し方に書き直し、変換は消す。
- ダンプ・LSP・コンパイラ・評価器が読む登録表は、切り替えのときに新しいものへ移す。

切り替えの後にこの通りにした（2026-11-12）。

- 組み込みの定義は `typeck::builtins` が新しい登録表へ直接書く。型のメソッドのシグネチャは型の型パラメータで書き、定義するときに位置でメソッドの型パラメータへ付け替える（7.3 の形。`defstruct` の取り出しメソッドと同じ）。組み込みのメソッドに、メソッド自身の型パラメータは無い。
- チェッカーの外（コンパイラの `externs.rs`・`abi_signature.rs`・`llvm_builtins.rs`、テスト）は、公開の入口 `typelisp_front::builtins::Builtins` から組み込みの定義を読む。評価器が実行時の型の表に種をまく型（`Option`・`Result`・エラー型・`Vector`・`Task`・`Thread`・`Chan`）は `typeck::builtins::runtime_types` が同じ書き手で書く。
- 書き直す前に、写した結果と書き直した結果を登録表の項目ごとに比べ、一致を確かめた（その比べるテストは写す仕組みと一緒に消した）。ABI の記述（`abi_signature::describe`）も書き直しの前後で一字一句同じだった。
- 古い登録表が起動のたびに確かめていた「標準ライブラリの 2 つのモジュールが同じ名前を定義しない」は、組み込みの定義については `typeck::builtins` のテストが、後から定義するものについては `typeck::define` が確かめる。
- `Type::Var` と、それを書く IR の形 `(type-var "NAME")` を消した（語彙の番号は変えず、`RETIRED_TYPE_VAR` として残す）。型パラメータはいつも `(type-param N)` で書く。

## 8. 登録表と core IR の組み立て（案）

### 8.1 登録表の形

- 定義は `Path`（モジュールとシンボル）をキーにした表に入れる。モジュールごとの入れ子の表にはしない。
  `Path` がすでに「どのモジュールの、どの名前か」を表しているからである。
- 名前空間は 2 つ。値（関数・グローバル変数・マクロ）と、型（型・型の別名・トレイト・C の構造体）。
  1 つのモジュールの 1 つの名前に結び付く値は 1 つだけ、型も 1 つだけ（`docs/dev/name-resolution.md` 1 節、`typelisp-user-error-types` の決定）。
  今の登録表のように、関数・変数・マクロを別々の表に入れて、同じ名前で両方を定義できる形にはしない。
- `use` の取り込みは「どのモジュールで、どの名前が、どの定義を指すか」の表にする。
- 型のメソッドは、型の定義の中ではなく「型の `Path` とメンバーのシンボル」をキーにした表に入れる。
  型の定義を書き換えずにメソッドを足せる（`impl` が型の定義を後から書き換えている今の形をやめる）。
- 表は、新しいチェッカーが必要とする種類だけを、必要になった段階で足す。

### 8.2 成功したときだけ確定する

登録表への書き込みは、すべて取り消し用の記録（書き込む前の値）を残す。
1 つの最上位フォームのチェックが成功したら記録を捨て、失敗したら記録をさかのぼって元に戻す（5.3 の実装）。
自己再帰は、記録を残しながら書き込んだ定義が、同じフォームの中から見えることで支える。

### 8.3 組み込みと prelude

組み込みの定義は、チェッカーを作るときに `typeck::builtins` が登録表へ書く（7.7）。
並べて置いた期間は、今の登録表の中身を写していた（名前の型変数 `Type::Var` を位置の `Type::Param` に直す `typeck::bridge`）。この写しは 2026-11-12 に消した。

prelude のジェネリックな定義の本体（特殊化の元になるチェック済みの木）は、チェッカーが prelude のソースを自分でチェックして持つ（ユーザー決定、2026-11-09）。チェックは prelude のダンプを作るときに1回だけ行う（2026-11-10）。ダンプの単位は、チェッカーの登録表の各表で変わったエントリ（消したものは「無し」として書く）とジェネリックな本体を、`CheckerDelta::registry` にまとめて書く（`typeck::wire::RebuiltUnit`）。木の値はヒープにあるので、木とは別に `OwnedForm` の列として訪れる順に書き、読むときに同じ順で木へ戻す。木の形（`typeck::tree` などの型）を変えると書いたものが読めなくなるので、prelude のダンプを作り直す（`scripts/regen-prelude-bitcode.sh`。読めないときのエラーはそう案内する）。セッションごとに prelude をチェックすると、すべてのテストがその分の時間を払い、全体テストが上限の時間に届いた。登録表の表は、エントリごとに書いた世代（確定した回数）を覚えている。単位を取る前の基準（`RegistrySignature`）は世代の数だけで、差分はその世代より後に書いたエントリ全部になる。単位を読むときは、登録表に取り込み、型・メソッド・`use` を名前の表（`heap.names`）に知らせる。名前の表には、最初のフォームをチェックする前（または `Checker::publish_names` で）登録表の中身をまとめて知らせ、その後はフォームごとに書いた分を知らせる。

prelude のソースは、型変数を宣言する形で書く（`impl<T> Option<T>`）。今のチェッカーもこの形を受け入れる。コアマクロの層と prelude のすべてのフォーム（501 個）は、新しいチェッカーでチェックでき、チェックしたものを評価器で実行できる（2026-11-09）。

### 8.4 core IR の組み立て

core IR の形（`(call ...)`、`(let ...)`、`(defun ...)` など）を組み立てる関数は `check::lower` と `check::core` にある。
組み立てが型の情報として尋ねるのは、次の 3 つだけである。

- 型の種類（構造体か直和型か）：値の表現（`Repr`）を決める。
- 組み込み関数の宣言上の引数と戻り値の型：境界で `int` を生のワードとして渡すかを決める。
- 組み込みメソッドについての同じ問い。

この 3 つ（と値の表現）を必須メソッドにしたトレイト `check::lower::CoreForms` を置き、組み立て関数をその既定メソッドにした。
実装するのは新しいチェッカーの登録表（`typeck::registry::Registry`）だけである。

### 8.5 次の一本

ジェネリックでない関数の定義と呼び出し、ローカル変数、`let`、`if`。

```lisp
(defun pick ((c bool) (a int) (b int)) int (let ((x a)) (if c x b)))
(pick true 1 2)
```

登録表は関数の表と取り消しの記録だけを持つ。名前解決は、ローカル、今のモジュールの関数の順に探す（`use` と祖先は、それらを扱う段階で足す）。

## 9. 進み具合

### 9.1 新しいチェッカーで扱えるもの（2026-11-08）

- リテラル（整数・bignum・ratio・浮動小数・文字列・文字・真偽値・`()`・キーワード）。規則は `typeck::literal` にあり、今のチェッカーもそれを使う。
- ローカル変数、`let`、`progn`、`if`。
- `defun` と呼び出し。ジェネリックな `defun f<T>` を含む。本体は型パラメータを抽象のまま 1 回だけチェックし、呼び出しごとに型パラメータを穴にして解く。
  特殊化は、呼び出したフォームの束（`(module <monomorph specializations> ...)`）の中に、保存したチェック済みの木の型を置き換えて作る。
- 型引数が決まったかどうかは、フォームをチェックし終えたところで 1 回だけ確かめる。後ろの引数や外側の期待する型で決まってよい。
- 組み込み（8.3）と prelude の関数・メソッド・型を呼べる。組み込みのジェネリックな関数とメソッド（`Vector::new` など）は特殊化せず、1 つの入口をすべての型引数で使う。型引数は結果の型が運ぶ。
- `defstruct`（既定値なし）、アクセサ、`make-instance`、フィールドの読み出し `p::x`。
- `defmethod`（`impl` の外）と固有の `impl<T...>`。静的メソッドの呼び出し `(Type::name ...)`、`use` で入った静的メソッド。
- `defenum`、変種の値 `(Name::Variant ...)` と `use` で入った裸の構築子、`module::f` の呼び出し。
- 値のパターン：その型のままの整数・`bool`・`char` のリテラルは語で比べ、ほかの値（文字列、浮動小数、`'sym`、キーワード、`(:= expr)`）は `(equals $match-scrut expr)` の判定で比べる（その型の `Eq` が比べる。`Eq` のない型は断る）。`Sexpr` に対する文字列・箱の数のリテラルは、同一性で比べることになるので断る（今のチェッカーと同じ文）。`bool` は `true` と `false` で網羅する。タプルのパターン `#{p ...}`（`Sexpr` に対してはその長さのタプルへのダウンキャスト）。網羅性では、構造体はその 1 つの形。
- 関連型を固定したスーパートレイト `((Super (Assoc Type)))`。固定はトレイト自身の型パラメータで書ける。トレイトの `impl` は、スーパートレイトの `impl` が固定どおりに関連型を決めていることを確かめる（型パラメータを含むものは、今のチェッカーと同じく確かめない）。
- `task`・`thread`（`typeck::spawn`）。中身は普通の呼び出しとしてチェックし、下ろしたものが呼び出し（`call`・`assoc`・`dyn-call`・`apply`）でなければ断る。値は `Task<T>`・`Thread<T>`。
- `select`（`typeck::select`）。受信の腕は `v` を `Option<T>` に束縛する。チャンネルと送る値は、左から 1 回ずつ評価して `select` を囲む `let` で束縛する。腕の本体の型は `match` と同じく 1 つ。
- `symbol-macrolet`。名前は局所変数と同じ枠に入り、内側の束縛が隠す。名前を書いたところで、その形をその場所でチェックする。`setf` の場所としても形になる。
- `shadow`（読み手が名前をモジュールのものにするので、チェッカーは何もしないフォームを返す）。`make-instance` の型をパスで書くこと。`defmethod` の受け手の型をパスで書くこと。
- `match`：変種・束縛・`_` のパターン。網羅性は入れ子のパターンまで見る（行列による判定）。`Option` をニッチで表すかどうかは lower で決める。
- `Sexpr` の `match`：`Sexpr` の変種の名前（`cons`・`sym`・`int` など）のパターン。`Option<Sexpr>` には、`some` をはがしたものとして `Sexpr` の変種を書き、同じ腕の並びに `none` を書ける。網羅性は `none` と `Sexpr` の変種（退いた `nil` と `bignum` を除く）を合わせたもので見る。`(nil)` と `(bignum ..)` は今のチェッカーと同じ文で断る。
- 型がすでに持つメソッドを、トレイトの `impl` がメソッドを書かずに使うこと。種類（インスタンスメソッドか）、`&optional`・`&key`・`&rest` がないこと、シグネチャがトレイトのものと一致することを確かめる。トレイトに既定の本体があれば、そちらを使う（今のチェッカーと同じ）。
- トレイトオブジェクト `:dyn Trait<pins...>`（`typeck::dyn_trait`）。トレイトオブジェクトが期待されるところで値を箱に入れる（型がトレイトを実装し、ヒープの表現を持ち、`impl` が関連型を固定と同じに決めていること）。型パラメータの値は境界で認め、表は特殊化ごとに作る。サブトレイトのトレイトオブジェクトはスーパートレイトのものになる（表の先頭が同じならそのまま、違えば `dyn-upcast`）。`(as :dyn T x)`。メソッドは表の番号で呼ぶ。表の並び（スーパートレイトのメソッドを書いた順に先に、それからトレイト自身のもの）は今のチェッカーと同じで、`deftrait` が 2 つのスーパートレイトから同じ名前を受け継ぐことや、受け継いだ名前を宣言し直すことを断る。オブジェクト安全性は使うところで確かめる。
- 1 つの具体化のための `impl`（`(impl cons-cell<int,int> ...)`）。メソッドはその具体化のもので、コードは具体化の名前で作る。型引数がまだ決まっていない受け手での呼び出しは、まだ扱わない。
- `use`（`import`・`shadowing-import`・`pub use` を含む）。値・型・トレイト・別名・型の変種と静的メソッド・モジュールを名指しできる。
- `defvar`・`defparameter`・`defconstant`（型の宣言が必須）とグローバル変数の読み出し。`the`。
- `unsafe` と `defffi`（`typeck::defffi`、`pub` を含む）、C のワード `ptr`・`c-long`・`c-ulong`。`defffi` の関数を呼ぶのは `(unsafe ...)` の中だけ（引数を見る前に断る）。C のワードが値になるのは `(unsafe ...)` の中だけで、`unsafe` のフォーム自身の値は例外（関数が答えられるように）。C のワードはほかの型の中に書けず（`defffi` のコールバックの型の引数と結果は例外）、構造体のフィールド・変種・グローバル変数にもできない。文は今のチェッカーのもの。
- 型付きポインタ `(ptr T)` と `def-c-struct`（`typeck::c_memory`）。`(unsafe (def-c-struct ...)...)` を最上位に書く。C 構造体は C の規則で並べ、登録表の型の名前空間に定義（`TypeEntry::CStruct`）を持つ。関数（または最上位のフォーム）のいちばん外側の `unsafe` が中の `c-alloc` を持ち、使われたときだけアリーナを開いて閉じる形にする。`lambda` と `labels` の関数はやり直す。`c-alloc`・`c-ref`・`c-deref`・`p::field` とその `setf` は内部の組み込みの呼び出しで、C から来た型付きポインタ（`defffi` の結果、読み戻したポインタのフィールド）は実行時に確かめる。`unsafe` の値、`task`・`thread` に渡す引数、`throw` が運ぶ値は型付きポインタにできない。C 構造体の名前は値の型として書けない。規則と文は今のチェッカーのもの。`lambda` と `labels` の関数が型付きポインタを取り込むことは断る。関数の引数の枠（`Locals::bind_function`）が境目で、ローカルを引く（`Locals::lookup`）ときに境目を越えたら取り込みになる。取り込みを木から後で集めないので、1回の走査で済む。
- `defffi` のコールバック（`typeck::callback`）。関数の型の引数に書けるのは、最上位の関数の名前、外のローカルを名指さない `lambda`、`labels` の関数の名前（たどり着く兄弟も含めて外のローカルを名指さないもの）。変数は断る。`lambda` は「何も取り込めない」境目で調べ、`labels` の関数は、ブロックを調べ終えたときに、各関数の境目が記録した名前から判断する。`lambda` と `labels` の関数は、木を低くするときに最上位の関数へ持ち上げ、特殊化の後、フォームの前に束へ入れる。持ち上げた関数とコールバックの入口（`CallbackSig`）は `Requests` が集め、入口はフォームが成功したときにセッションに残す（`compile-file` が読む）。ジェネリックな本体の中で持ち上げるものは、まだ扱わない（特殊化ごとに別の関数が要る）。
- `defsignature`（`typeck::defsignature`、`pub` を含む）。関数の前方宣言で、後に来る `defun` は宣言と一致しなければならない（文は今のチェッカーのもの）。型パラメータと `&optional`・`&key` は宣言できない。定義が来ていない宣言は、登録表の `predeclared` に残り、単位を終えるとき（`Checker::finish_unit`）に今のチェッカーのものと合わせて報告する。
- `deftype`（`typeck::deftype`、`pub` を含む）。型の別名で、使うところで本体（型パラメータを使う位置の引数で置き換えたもの）になる。別名が自分を名指すことは、今のチェッカーと同じ文で断る。
- メッセージの型は、今のチェッカーと同じく、フォームのモジュールから見た書き方で書く（フォームの前に今のチェッカーが名前の見え方を公開する。表は今のチェッカーの登録表から作るので、切り替えのときに新しいチェッカーの登録表から作る）。
- `format`・`print`・`println`。宛先がストリームの `format` は、チェックしたストリームを一時変数に束縛し、`(write-string tmp (format false ...))` をチェックしたものにする（値は `()`）。`CharOutput` を実装しない具体的な型の宛先は、今のチェッカーと同じ文で断る。引数は、それぞれの型のまま `Sexpr` のリストにして渡す。どう `Sexpr` にするかは lower で、決まった型から選ぶ（`typeck::sexpr_value`）。制御文字列の指令と引数の型は、フォームをチェックし終えたところで照らし合わせる。
- `defstruct` のオプションとフィールドの既定値（`typeck::defstruct`）。`(defstruct (Name option...) ...)` のオプションは `(:copier name)` と `(:include Parent)` で、ほかの CL のオプションは理由を言って断る（文は今のチェッカーのもの）。既定値 `(name Type default)` は、ソースから名指せない静的メソッド `(default name)` の本体として `defstruct` のときに 1 回だけチェックし（構造体の型パラメータがあり、ローカルは無い）、`make-instance` が与えられなかったスロットでそれを呼ぶ。毎回評価されるのは CL の初期値と同じ。今のチェッカーは既定値をソースのまま持ち、`make-instance` のたびに呼び出しへ埋め込んでチェックしていた。`:include` が持ち込むスロットの既定値は、親の既定値のメソッドを呼ぶ。`:copier` は、同じスロットの値を持つ新しい値を返すインスタンスメソッド。
- `match` の `:when` と `(:or ...)`（`typeck::matching`）。`:when` の条件は腕のパターンが束縛する名前を見てチェックし、その腕は網羅性で何も覆わない。`(:or ...)` はパターンのどこに書いてもよく、今のチェッカーと同じ関数（`expand_or_patterns`）で丸ごとのパターンに展開し、それぞれが同じ名前を同じ型で束縛しなければならない。今のチェッカーは選択肢ごとに腕を作って本体を選択肢の数だけチェックしていた。新しいチェッカーは本体を 1 回チェックし、選択肢を木（`Pat::Or`）に持たせ、lower のときに選択肢ごとの腕にする。
- `Sexpr` からのダウンキャスト（`typeck::pattern`）。`Sexpr`（と `Option<Sexpr>`）に対して、構造体の名前のパターンと、`use` で裸になった変種やパスで書いた変種のパターンは、その型の値を照らす。ジェネリックな型は名指せない。`(the Type pattern)` は、その型の値まるごとを照らす。`Sexpr` の表現を持たない型は断り、ニッチの `Option` は構築子を名指さなければならない。文は今のチェッカーのもの。
- 1 つの具体化のための `impl`（`typeck::trait_impl`、`typeck::impl_block`）。`impl<...>` が何も宣言せず、型がすべての型引数を書くとき（`(impl Show Box<int> ...)`）、その `impl` とメソッドはその具体化のもので、コードはその具体化の名前を持つ。トレイトの `impl` では、書いたメソッドも既定の本体から取るメソッドも、スーパートレイトの確かめも、`trait_impls` への記録も具体化ごと。静的メソッドは、具体化が 1 つならそれ、そうでなければ呼び出しに期待される型で選ぶ。`Type<args>::member` は `compile` と `documentation` で、その具体化のメソッドを名指し、具体化ごとのメソッドのドキュメントはコードの名前で引く。どれを選ぶかが型引数で決まるとき（メソッドを引くとき、`impl` が当てはまるか確かめるとき、`~/name/`）は、決まっていない数のリテラルの穴を先に既定の型にする（`Cx::decide_all`）。今のチェッカーは数のリテラルをすぐに既定の型にしていた。自分の型パラメータを持つ具体化のメソッドは、まだ扱わない（テンプレートを具体化ごとに持つ必要がある）。
- `aref`（`typeck::aref`）。`(aref a i j)` と `(setf (aref a i j) v)` は、配列を先にチェックして一時変数に束縛し、添字を集めた `Vector<int>` で `get`・`set` を呼ぶ形として本体をチェックする。配列でない受け手は、今のチェッカーと同じ文で断る。
- `in-module`・`load`。トップレベルの `in-module` は、入るモジュールを記録し、現在のモジュールを持つドライバ（`Checker`）がそれを受け取る。`module` の本体の `in-module` は、本体の残りをそのモジュールでチェックし、読み手も本体の残りをそのモジュールで読む。式の位置のトップレベルの形は、今のチェッカーと同じエラーにする。
- 定義の名前は、定義するモジュールの同じ綴りのシンボル（`Definer::ownable`）。別のモジュールのマクロが書いた名前も、展開したモジュールの定義になる。
- モジュールの本体ですぐ実行する形（`defmacro`・リーダーマクロの登録）は、それまでに求めた具体化と持ち上げた関数と一緒に束ねて実行する。プロジェクトのドライバが先に展開するトップレベルのマクロ呼び出し（`Checker::try_expand_toplevel_macro`）は、新しいレジストリで展開する。
- `pprint`・`pprint-fill`・`pprint-linear`・`pprint-tabular`・`pprint-logical-block`（`typeck::pprint`）、`eprint`・`eprintln`（`(format *error-output* ...)` としてチェックし、リリースのビルドでは `()` にする）、`source-file`、`step`（`Node::Step`）。
- `ed`（`typeck::tools`）。定義の位置は、ドキュメント文字列と同じ鍵（`Definition`）で `Registry::locs` に記録する（`Definer::record`）。名前から定義を引くのは `documentation` と共有する。
- メソッドを関数の値として使うこと（`Node::MethodRef`）。関数が期待される位置の裸の名前は、期待される関数の第 1 引数の型がその名前のメソッドを持てば、関数より先にそのメソッド。呼び出しの第 1 引数は、呼び出しの名前が関数で、どの型もトレイトもその名前のメソッドを持たないとき（`Registry::is_method_name`）、または値を持たない裸の名前のときは、関数の第 1 引数として引数の型を期待してチェックする。
- `macrolet`（`typeck::macrolet`）。マクロの本体は `defmacro` と同じ `defmacro::macro_form` でチェックし、求めた具体化と一緒に束ねて、本体をチェックする前に評価器に渡す。名前は `Locals` の枠に持ち、近い束縛が隠す。
- トレイトオブジェクトの `match`、`Sexpr` に入れること、`Sexpr` のメソッドを呼ぶこと（`Node::DynValue`）。どれも中の値を `Sexpr` として扱う。`match` は `Sexpr` のダウンキャストのパターンで照合する。トレイトオブジェクトは、自身のトレイトとそのスーパートレイトの境界を満たし、ジェネリックな本体の境界のメソッドはその表を通して呼ぶ。`try-as` でトレイトオブジェクトにすることと、式の位置の `:dyn` は、今のチェッカーと同じ文で断る。
- ジェネリックな関数・`&optional` や `&key` を取る関数を値として使うこと（`typeck::lambda::fn_value`）。型引数は、関数の型が期待される型と単一化されて決まり、lowering で具体化を求める（`Node::FnRef` の `targs`）。`&optional` と `&key` の引数は位置で渡し、既定値があればその型、なければ `Option`。グローバル変数が持つ関数の呼び出しは、関数の値の呼び出し（`Node::Apply`）。
- 組み込みメソッドの具体化（`toplevel::builtin_specialization`）。ジェネリックな型の組み込みのインスタンスメソッドは、トレイトオブジェクトの表やメソッドの値が名指すとき、具体的な型でその組み込みを呼ぶメソッドとして具体化する。
- 外からの問い：`Checker::fn_ret`（AOT の `main` の戻り値型）と `Checker::type_kind`（REPL の値の表現）は、切り替えが入っていれば新しいレジストリに答えさせる。
- ブランケット `impl`（`(impl<T> Trait T (:where ...) ...)`、`trait_impl::check_blanket_impl`）。トレイトに 1 つまで。メソッドは、`T` を `:where` の境界とトレイト自身で縛ったパラメータとして 1 回だけチェックし、書けない名前の合成の持ち主のメソッドとして持つ。境界を満たす型は、自身の `impl` が無ければそのトレイトを実装する（境界の循環はたどっている組で止める）。呼び出し・境界のメソッド・トレイトオブジェクトの表は、そのメソッドを受け手の型で具体化し、コードは受け手の型のメソッドとして作る。
- パスで名指すトレイトの `impl`。スーパートレイトのメソッドを書いたときは、そのスーパートレイトの `impl` に書くよう案内する。
- 定数の畳み込み（`check::fold` を共有する）。lowering で、リテラルを引数にした組み込みのスカラーのメソッドはその値に、条件がリテラルの `if` はその枝にする。
- `int` と `ratio` を混ぜる演算子（CL の contagion）。両方を `rational` に広げ、`rational` の演算子を呼ぶ。
- 境界で縛った型パラメータの演算子は、トレイトのメソッドの名前に読み替える（`/` は `Div` の `div`、`check::analyze::trait_operator_method`）。
- 3 つ以上の列の `append` と `concatenate`（`typeck::sugar`）。`append` は最初の列を先にチェックして一時変数に束縛し、その型で畳み方を選ぶ。
- 境界を満たさない型に、受け手だけを取ってその境界を満たす値を返すメソッドがあれば、エラーでそれを案内する。
- `(documentation name)`（`typeck::documentation`）。
- `#[test]`（`typeck::attribute`）。テストを集めるときは、トップレベルの式をチェックしてから外す。
- 1 つのインスタンス化の `impl` のメソッドが自身の型パラメータを持つこと。テンプレートはインスタンス化のコードの名前で引く。
- 型パラメータと型を混ぜた対象（`impl<T> Pair<T,int>`）は断る。同じメソッド・トレイトを、すべてのインスタンス化と 1 つのインスタンス化の両方に書くことも断る。
- 受け手の型に決まっていない数の穴があり、メソッドがブランケット `impl` のものしかありえないとき、穴を既定の型に決めてから覆うかを見る。
- `(pub use ...)` で再輸出した名前を、パス（`shapes::area`）で書いたときも、定義までたどる（関数・変数・マクロ・型）。
- キーワードは束縛・定義の名前にできない。
- 型を書くところに書いたトレイトは、「`:dyn` を付けて書く」と案内して断る。
名前は評価しない。関数・マクロ・グローバル変数・型・トレイト、型のメソッドとトレイトのメソッドを名指し、名指すものが無ければチェックのエラーにする。名前の解決は、ほかの名前と同じ関数（`find_named` など）による。文は今のチェッカーのもの。
- 構造体のパターン `(Type :slot pattern... :slot...)`（`typeck::pattern`）。書いたスロットはそのパターンで照らし、パターンの無いスロットは同じ名前の変数に束縛し、書かないスロットは照らさない。先頭は照らす値の型でなければならない。文は今のチェッカーのもの。
- `recv::member`（`typeck::instance`）。受け手はローカルかグローバル変数で、その値のフィールド、タプルの要素（番号）、または受け手の型の引数を取らないインスタンスメソッドの呼び出し `(member recv)`。`(setf t::0 v)` はタプルの要素を設定する。`#{..}` のリテラルは、タプルの型の `new` を呼ぶ。
- `format` の `~/name/` 指令（`typeck::format`）。指令が何を呼ぶかは引数の型で決まるので、引数を先にチェックし、決まっていない数のリテラルは既定の型にしてから、`(name arg colon at)` をその場の呼び出しとしてチェックする。呼ぶものは typelisp で書いた関数かメソッドで、引数をそのまま受けるもの。1 つの指令が受けうる引数が別々の定義を呼ぶときと、リストの要素を受けうるときは断る。制御文字列の名前を呼ぶ定義のリンク名に置き換え、呼ぶ定義を木（`Node::FormatCalls`）に持たせる。lower のときに `Requests` が集め、フォームが成功したらセッションに残す（`compile-file` が起動時に登録する）。文は今のチェッカーのもの。ジェネリックな定義を呼ぶ指令は、まだ扱わない。
- ジェネリックな型の `print-object` の特殊化。印字は実行時に値の型でメソッドを選ぶので、呼び出しが特殊化を頼むことがない。lower のときに、ジェネリックな型の箱を作るノード（構築、関数とメソッドの呼び出し）が、その具体化に `print-object` が当てはまれば（`impl` の `:where` を満たせば）特殊化を頼む。当てはまらない具体化は組み込みの形で印字し、エラーにしない。境界の判定は、チェック中のものと同じ関数（`bounds::meets_at`）を決まった型で使う。
- 印字とメッセージの型の書き方（`typelisp_mem::NameView`）は、新しいチェッカーの登録表から作る。モジュールが取り込んだ型と、`std::prelude` が再公開する型のうち名前が空いているものを、最後の段で書く。フォームの前と後、モジュールに入るときに作り直す。
- `module`（`typeck::module`）と `pub`。`module` の本文の各フォームは子のモジュールで最上位のフォームとしてチェックし、すぐ効く必要のあるもの（`defmacro` など）はその場で評価器に入れる。`pub` は定義の印（`Definer::public`）。ほかのモジュールの `pub` でない関数・変数・マクロは、パスからは無いものとして扱う（「unresolved path」）。パスでグローバル変数を読める。
- 型の書き方：関数の型 `(fn (A &rest B) R)`、`::` のパス、リストの形 `(Name A)`、タプルの型 `#{A B}`。
- `deftrait`（`typeck::deftrait`）と、型へのトレイトの `impl`（`typeck::trait_impl`）。`Self` と関連型はトレイトの型パラメータで、`Self` が 0 番、`k` 番目の関連型が `1 + k` 番。`impl` の各メソッドは型のメソッドとして登録し、シグネチャはトレイトのものの `Self` と関連型を位置で置き換えたものと一致させる。`impl` のメソッドの型の中では、関連型の名前はその `impl` が決めた型を表す（`TypeScope::name_types`）。スーパートレイトの `impl` が先にあることも確かめる。
- トレイトの既定の本体。`deftrait` で 1 回だけチェックする。`Self` はそのトレイトを境界に持つ型パラメータで、関連型はトレイトのほかの型パラメータ。`impl` が省いたメソッドは型のメソッドとして登録し、本体はトレイトの既定の本体を、トレイトの型パラメータを `impl` の型に置き換えて作る（ジェネリックな `impl<T>` なら呼び出しの位置で特殊化する）。省いたメソッドを先に登録するので、書いたメソッドから呼べる。
- 期待する型への広げ方（`typeck::widen`）。`Sexpr` が期待されるところへは、`Sexpr` の符号がある値を広げる（`Symbol` と `Sexpr` はそのまま、ほかは `AsSexpr`）。`Option<Sexpr>` は `Sexpr` に狭めない。`rational` へは `int` と `ratio`。呼び出しの結果の型を先に期待と合わせるところでは、広げる先の型なら食い違いをエラーにせず、値をチェックしたところで決める。
- ソースに書いた箱（`typeck::collection_literal`）。`#(..)` は新しい `Vector`、`#nA(..)` は新しい `Array`、`#{..}` は新しいタプルを作るフォームに書き換え、その位置でチェックする（フォームは今のチェッカーのもの）。要素は評価しないので、記号・パス・リストは quote する。要素の型は、期待する型か（データが期待されるところでは `Option<Sexpr>`）、無ければ要素が決める（最初の要素を別にチェックし直さない）。要素が無く、期待する型も無いものは、今のチェッカーと同じ文で断る。ほかの箱は、プログラムが S 式のデータに入れたもので、それ自身に評価する（型は `Sexpr`）。
- `(%type-member Type member)` を頭に持つ呼び出し（チェッカーが書くフォーム）：型の変種か静的メソッド。`Type<args>::member` はまだ扱わない。
- `Sexpr` の変種で値を作ること（`(Sexpr::cons a b)` など）。退いた `nil` と `bignum` は今のチェッカーと同じ文で断る。
- `quote`。記号は `Symbol`、ほかのデータは `Option<Sexpr>`。`quasiquote`：`,x` は `x` を `Option<Sexpr>` を期待してチェックし、`,@x` は prelude の `sexpr-append` でつなぐ。
- `defmacro`（`typeck::defmacro`）：引数と結果は `Option<Sexpr>`。`&optional`・`&key` の既定値は、それより前の引数を束縛してチェックする。本体は評価器が持つ。
- `list`（`typeck::list_form`）。各要素は `Option<Sexpr>` を期待してチェックし、`Sexpr` の cons 変種でつなぐ。`panic`（型は `!`）と `unwind-protect`（型は守られる式の型、後始末の値は捨てる）。
- `as`・`try-as`（`typeck::cast`）。変換は元の型のメソッドの呼び出しにする（表は旧チェッカーの `as_conversion`）。整数・浮動小数点数の族への変換は族の広い型で登録されているので、狭い型へはその後に幅の変換をつなぐ。トレイトオブジェクトへの `as` はまだ扱わない。
- `defun` の `&optional`・`&rest`・`&key`（`typeck::lambda_list`）と、それらを持つ関数・メソッドの呼び出し（`typeck::args`）。呼び出しは引数を 1 つずつそろえた呼び出しにする。省いた引数は、既定値（`defun` のときに引数を束縛せずにチェックし、core IR にして持つ）か `none`、既定値のない引数を渡したら `some` で包む。`&rest` の引数は 1 つの `Sexpr` のリストにする。既定値を持つ引数の型は、関数の型パラメータを含んではいけない。`defmethod` と型の `impl` のメソッドも同じ。トレイトの `impl` のメソッドは目印を書けない（トレイトのメソッドの引数の数は `deftrait` が決める）。
- 関数の値（`typeck::lambda`）：`lambda`、`labels`、`apply`、関数の型を持つ値の呼び出し、型パラメータと `&optional`・`&key` を持たない関数を値として取り出すこと。`lambda` と `labels` の関数の本体からは、外のループを抜けられない。`block` を扱うときは、`labels` の関数に名前の暗黙の block を付ける（旧チェッカーと同じ）。
- `let*`（入れ子の `let` にする）と、引数の数で意味が変わる呼び出し（`typeck::sugar`）：可変個の算術と比較、0 個・1 個の算術と比較、`(log x base)`、`(atan y x)`。書き換えた形をその位置でチェックする。3 つ以上の `append`・`concatenate`・`aref` はまだ扱わない。
- 1 つの本体を名指す道具（`typeck::tools`）：`compile`・`trace`・`untrace`・`disassemble`。名前は関数・マクロ・型のメソッドを指し、ジェネリックな定義は断る。1 つの具体化のためのメソッド（`Type<args>::member`）はまだ扱わない。
- `defun` の `:where` の境界（`typeck::bounds`、7.6）：境界のトレイトとスーパートレイトのメソッドをジェネリックな本体で呼ぶこと、呼び出しの位置で型引数が境界を満たすかを確かめること（境界の固定は `impl` が決めた関連型と単一化するので、固定から型引数が決まる。`impl` 自身の `:where` も確かめる）。`defmethod`・型の `impl`・トレイトの `impl` の `:where` も同じ（`impl` の `:where` は、メソッドごとに、その型パラメータの枠で読む）。トレイトの `impl` のメソッド自身の `:where` は、そのメソッドの境界で、`impl` が当てはまる条件にもなる（トレイトを通した呼び出しからは見えないため）。固定していない関連型は射影の型 `Type::Proj` にし、特殊化で `impl` が決めた型に置き換える（7.6）。
- 単純な `loop` と `break`・`return`（`typeck::looping`）。ループの型は、出口が解く穴にする。何も出ないループは `!`。
- 拡張した `loop`（`:for`・`:collect` など）。今のチェッカーの `loop_dsl::build` で単純なループと束縛に書き換え、その位置でチェックする。蓄積の初めの値は、蓄積するものが型を決める値にする（空の `Vector`、`none`、どの数の型にもなるゼロ）。今のチェッカーのように、蓄積する式を先に別にチェックしない。どの数の型にもなるゼロは、穴の種類 `Kind::Number` で、フォームの外側の束縛にする。
- `block` と `return-from`（`typeck::block`）。`return-from` は、同じ関数の中で、その名前のいちばん内側の `block` を抜ける。`defun`・`defmethod`・`impl` のメソッド・トレイトの既定の本体・`labels` の関数は、書いた名前の `block` を持つ（今のチェッカーと同じ）。`lambda` は持たず、外の `block` も抜けられない。型は、期待する型か、最初に値を返した出口が決める。`return-from` が名指さない `block` は、束縛のない `let` にする。
- `catch` と `throw`（`typeck::catch`）。タグは quote した記号で、運ぶ型はセッションで 1 つ（フォームをまたいで登録表に持つ）。フォームの中では `Cx` に集め、フォームを決めるとき（`Cx::settle`）に登録表に書く。本体が `!` の `catch` の型はタグの型。ジェネリックな本体の型パラメータを運ぶタグはまだ扱わない。今のチェッカーのタグは写さない（島のタグは島のモジュールの記号なので、プログラムのものと別）。
- `setf`：変数（`defconstant` は断る）、フィールド `var::field`（構造体の `set-field`）、呼び出しの形の場所 `(accessor recv key...)`（受け手の型の `set-accessor`、`get` なら `set` も）。
- `incf`・`decf`・`rotatef`・`shiftf`（`typeck::modify`）。`setf` のフォームに書き換え、その位置でチェックする。呼び出しの形の場所の引数は先に一時変数に束縛し、1 回だけ評価する。シンボルマクロの場所は、その形の場所にする（引数も 1 回だけ評価する）。
- マクロの呼び出し（`typeck::macros`）。書かれたままの引数で展開し、展開したものを呼び出しの位置でチェックする。最上位では、定義のフォームとして読む前に展開する。マクロの本体は評価器が持ち（`MacroExpander`）、チェッカーは呼び出せる引数の数（`MacroShape`）だけを持つ。
- 定義の名前の規則（`typeck::define`）：予約語、std::prelude が与える名前を `(shadow ...)` なしで定義しないこと、関数・変数・マクロの名前空間と型・トレイト・別名・C 構造体の名前空間でそれぞれ名前が 1 つの意味であること、再定義の方針（`RedefPolicy`）、組み込みを置き換えないこと。
- 新しいチェッカーが定義した型とメソッドを、セッションの名前表に公開する（後のフォームでパスが読めるように）。
- 標準ライブラリの中の定義（`typeck::library`）。標準ライブラリのモジュールで定義したフォームの後に、`std` がそのモジュールたちの定義をすべて取り込み、`std::prelude` が `prelude_offers` の定義と、その関数と変数の型が名指す型を再公開する。名前は標準ライブラリのモジュールをまたいで 1 つ（型の名前はすべてのモジュールで 1 つ）。標準ライブラリの型の固有の `impl` は、標準ライブラリのどのモジュールでも書ける。
- ドキュメント文字列（`Doc` の表）：`defun`・`defmacro`・`defvar`・`defstruct`・`defenum`・`deftrait`・`defmethod`・`impl` のメソッド・既定の本体を持つトレイトのメソッド。
- `Option` が期待されるところの `()` は `none`。`Option<Sexpr>` の受け手は `Sexpr` のメソッドにも答える（`Sexpr` にないものは `Option` のもの）。
- 1 つの最上位フォームの登録は、成功したときだけ確定する。

### 9.2 まだ扱っていないもの

新しいチェッカーがこれらに出会うと `unimplemented!()` で止まる。

- トレイト：自分の型パラメータや `:where` を持つトレイトのメソッド、`&optional`・`&rest`・`&key` を持つトレイトのメソッド、自分の型パラメータを持つメソッドをトレイトのものとして使うこと、prelude のトレイトの既定の本体（チェック済みの木が無い）、2 つ以上の blanket `impl` が持つメソッド、対象のほかに型パラメータを宣言する blanket `impl`、blanket `impl` が与える関連型、型パラメータが型のものと順に並ばない `impl`、型パラメータの無い型への `impl<...>`。
- 1 つの具体化のためのメンバー：`Type<args>::member` の呼び出し、型引数がまだ決まっていない受け手でのそのメソッドの呼び出し、`use` で入ったそれ。
- ジェネリックな本体の中で：ジェネリックな定義を呼ぶ `~/name/`、型パラメータを運ぶ `catch` のタグ、C に渡すジェネリックな関数。
- 型がまだ決まっていない値：関数としての呼び出し、`apply`、`:dyn` への変換、境界を満たすかの判定、何も決めない型引数の `:where`。
- そのほか：トレイトオブジェクトの `match`、`&optional`・`&key` を持つメソッドを値として使うこと、型の名前でない `defmethod` の受け手、大域変数が持つ関数の呼び出し、トレイトのメソッドをパスで呼ぶこと、型のメンバーを値として使うこと、`macrolet` のマクロの本体から C にコールバックを渡すことや `~/name/` で定義を呼ぶこと。

### 9.3 今のチェッカーと振る舞いが変わる点

切り替えのとき（2026-11-11）、これらに合わせてテストの期待を直した。

- 名前が見えない型と、ほかの型の中の C のワードを両方含む型（`(vector ptr)`）は、見えない名前として断る（今のチェッカーは C のワードとして断る）。
- `loop` の `:thereis` に `Option` でない式を書いたときのエラー。今のチェッカーは式を先にチェックして専用の文で断るが、新しいチェッカーは書き換えたフォームをチェックするところで断る（`is-some` が見つからない、など）。
- 型引数の推論がフォーム全体で行われる。`(Tree::Node (Tree::Leaf) "a" (Tree::Leaf))` は今のチェッカーでは `T` を推論できずに断られるが、新しいチェッカーでは通る。
- 網羅性を入れ子のパターンまで見る。`((Full (Circle r)) ..) (Empty ..)` は今のチェッカーでは通り、実行時に `no matching match arm` で止まる。新しいチェッカーは `(Full (Rect _ _))` が漏れているとして断る。
- 網羅していないときのメッセージは、漏れている値を 1 つ示す（「`(Rect _ _)` is not covered」）。
- `Option<Sexpr>` の `match` で、裸の `none` を変種として受け入れる（裸の名前は変種という規則のまま）。今のチェッカーは `(none)` と書くことを求める。
- `:where` の境界は、定義が宣言した型パラメータにしか付けられない。今のチェッカーは `(defun f<T> ... (:where (shape U)) ...)` を黙って受け入れる。
- 宣言していない型変数を使うテスト（`(impl Box<T> ...)`、`(defmethod m ((v Vector<T>)) ...)`）は断られる。宣言を足す（`impl<T>`、`m<T>`）。
  - `impl<T>` を足すだけで今のチェッカーでも通るテストは、足した（2026-11-11）。
  - 今のチェッカーと答えが変わるので、切り替えのときに直すテスト：`method_type_params_test` の `an_undeclared_type_variable_is_still_unknown` と `unknown_type_test` の `a_method_s_type_variables_are_the_ones_its_receiver_writes`（今のチェッカーは `impl<T>` の中の宣言していない名前を断らない）、`toplevel_defmethod_test` の `on_a_user_type_and_a_generic_type`（今のチェッカーは `second-elem<T>` の `T` が受け手の型パラメータと同じ名前だとして断る）。

- ジェネリックな本体は 1 回だけチェックするので、型パラメータで決まらない境界の固定は定義のところで断る。`(defun outer<U> ((w wrap<U>)) int (get-int w))` は、`get-int` が `Item` を `int` に固定するので断る（今のチェッカーは特殊化まで待つ。`trait_test` の `forwarding_a_wrapped_open_type_variable_...` の 2 件）。
- フィールドの読み出し `self::v` は、フィールドを直接読む。getter の具体化は作らない（`monomorph_test` の `a_method_on_a_generic_type_specializes_at_the_call_site` の 2 つ目の確かめ）。

- 数値リテラルの型はフォームの残りで決まるので、`(the i32 (let ((x 42)) x))` は通る（`int_default_test` の `an_unannotated_literal_is_an_int`）。

- 呼び出し `(name x ...)` の第 1 引数は 1 回だけチェックする。今のチェッカーは、`x` を試しにチェックし、メソッドがなければもう一度チェックするので、関数名がどこかの型のメソッド名でもあると、第 1 引数に入れ子にした呼び出しに深さの指数の時間がかかる（深さ 20 で 26 秒）。

- ジェネリックな本体の `format` で、型パラメータの引数は「どんな値でも印字する指令」しか受けない（`~c` や `~{` は断る）。本体は 1 回だけチェックするので、すべての型について成り立つことだけを認める。今のチェッカーは特殊化ごとに照らし合わせ直していた。

### 9.4 1 回の走査でチェックする

木の各ノードは 1 回だけチェックする。推論の状態（穴とその解）は 1 つの表で、走査に沿って育つだけで、写しを取ることも巻き戻すこともない。

- 呼び出しの第 1 引数は期待する型なしでチェックし、その型でメソッド表、なければ関数表を引く。関数なら、チェック済みの引数をパラメータの型と単一化する（rustc の `check_expr_method_call` と同じ形）。
- 期待する型でしか決まらないものは、期待する型がないときに推論変数にする。数値リテラルは整数（浮動小数）にしかなれない穴になり、フォームの終わりで決まっていなければ既定の型にして、そこで範囲を確かめる（rustc の `next_int_var` と数値の fallback）。
- 型をその場で見なければならないところ（受け手のメソッドを引く）では、決まっていない数値の穴を既定の型として見る。メソッドが見つかったときだけその型に決める。`(+ 1 x)` は `int` の `+` で、`(id8 1)` の `1` は `u8`。
- `Sexpr`・`rational` への広げ（`typeck::widen`）と `:dyn` への変換（`typeck::dyn_trait`）は、チェック済みの木に後から変換を足す形で、チェックし直さない。
