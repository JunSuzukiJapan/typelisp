# typelisp-mode (Emacs)

Основной режим Emacs для редактирования исходного кода typelisp (`.typl`).
Версия для VS Code находится в [../vscode/](../vscode/README_ru.md). Обе используют одни и те же
таблицы ключевых слов и одни и те же правила отступов, и `cargo test --test editor_keyword_sync_test`
проверяет это автоматически (см. конец документа).

## Возможности

- Подсветка синтаксиса
  - Специальные формы и управляющие конструкции (`defun` `let` `if` `match` `loop` `lambda` `setf`
    `as` `apply`, `print`/`println`/`format`, семейство `pprint` и т. д.)
  - Определяемые имена (`NAME` в `(defun NAME ...)` как имя функции, в `(defstruct NAME ...)` как
    имя типа, в `(defvar (NAME ...))` как имя переменной; то же с `pub`, как в
    `(pub defun NAME ...)`)
  - Ключевые слова пространств имён и объявлений (`pub` `module` `use` `load` `impl` `where`) и
    маркеры лямбда-списка (`&rest` `&optional` `&key`)
  - Встроенные функции (`car` `map` `foldl` `unwrap` `parse-int` `message` `sexpr-car` и т. д.)
  - Примитивные типы (включая `bignum` / `ratio`), встроенные типы, встроенные типы ошибок
    (`ParseIntError` и т. д.), пользовательские типы `Capitalized` и тип трейт-объекта
    `:dyn Trait`
  - **Места использования пользовательских типов** (имена `defstruct`/`defenum`/`deftrait` обычно
    пишутся строчными буквами (`rect` `todo-item` `board`), поэтому правило `Capitalized` их не
    находит). При подключении к `typl-lsp` они раскрашиваются по semantic tokens сервера (это
    работает и с `eglot`; см. ниже). Без подключения режим переходит к сбору имён типов,
    определённых в буфере
  - Литералы (`true` `false`, числовые литералы (десятичные / `0xff` / `1.5` / `1/3`), литералы
    символов вроде `#\Space`, строки, ключевые слова вроде `:name`)
  - Управляющие директивы `format` внутри строк (`~a` `~5,'0d` `~{...~}` и т. д.)
  - Глобальные переменные с «наушниками» в стиле CL (`*print-pretty*` и т. д.)
- Комментарии
  - Строчные комментарии `;`
  - **Вкладываемые** блочные комментарии `#| ... |#`
- Навигация по S-выражениям и отступы в стиле Lisp
- Указатель определений через `imenu` (функции / методы / макросы / типы / трейты / `impl` /
  переменные / модули)
- Команды, запускающие CLI `typl` (ниже)

## Сочетания клавиш

| Клавиша | Команда | Что делает |
|---|---|---|
| `C-c C-c` | `typelisp-run-buffer` | Сохраняет и запускает `typl FILE` (через `compile`, поэтому можно перейти к строкам с ошибками) |
| `C-c C-z` | `typelisp-repl` | Запускает REPL `typl` в буфере comint |

Расположение `typl` задаётся через `typelisp-program` (по умолчанию `"typl"`).
Диагностика имеет вид `error: FILE:LINE:COL: ...`, который понимает `compilation-mode`, поэтому
`next-error` / `C-x \`` сразу переходит к нужному месту.

## Установка

```elisp
(add-to-list 'load-path "/path/to/typelisp/editor/emacs")
(require 'typelisp-mode)
```

Файлы `.typl` автоматически открываются в `typelisp-mode` (режим зарегистрирован в
`auto-mode-alist`).

С `use-package`:

```elisp
(use-package typelisp-mode
  :load-path "/path/to/typelisp/editor/emacs"
  :mode "\\.typl\\'")
```

## Языковой сервер (`typl-lsp`)

Собранный `typl-lsp` можно использовать из `eglot` (входит в Emacs 29+) или `lsp-mode`.

```sh
cargo build --release --bin typl-lsp
```

С `eglot`:

```elisp
(with-eval-after-load 'eglot
  (add-to-list 'eglot-server-programs
               '(typelisp-mode . ("/path/to/typelisp/target/release/typl-lsp"))))
(add-hook 'typelisp-mode-hook #'eglot-ensure)
```

С `lsp-mode`:

```elisp
(with-eval-after-load 'lsp-mode
  (lsp-register-client
   (make-lsp-client
    :new-connection (lsp-stdio-connection "/path/to/typelisp/target/release/typl-lsp")
    :major-modes '(typelisp-mode)
    :server-id 'typl-lsp)))
(add-hook 'typelisp-mode-hook #'lsp)
```

Поддерживаются диагностика (синтаксические ошибки и ошибки типов, а также предупреждения о
переопределении, передаваемые через `textDocument/publishDiagnostics`), hover, переход к определению
(goto-definition), автодополнение (`:` зарегистрирован как символ-триггер) и semantic tokens.
Ссылки между файлами через `use` разрешаются (сервер ищет вверх `typelisp.toml` корня проекта;
подробности в [Справочнике по синтаксису 3.11](../../docs/ru/reference/syntax.md#311-файлы-и-модули-многофайловые-проекты)).
Несохранённые правки в открытых буферах сразу отражаются в диагностике как файлов, от которых они
зависят, так и файлов, которые зависят от них.

### Подсветка имён типов (semantic tokens)

Через `textDocument/semanticTokens` сервер сообщает **позиции, которые проверка типов действительно
разрешила как имена типов**. Поскольку это не сопоставление текста:

- Типы, пришедшие из других файлов через `use`, тоже раскрашиваются (область, до которой
  разрешение внутри буфера в принципе не дотягивается)
- Вызовы **функции** с тем же именем, что у типа, не раскрашиваются (проверка разрешила их как
  функции, поэтому токен там вообще не записывается)

Со стороны клиента:

- **`eglot` (Emacs 31 и новее)**: eglot рисует токены сам (`eglot-semantic-tokens-mode`).
  `typelisp-mode` не вмешивается
- **`eglot` (Emacs 30 и старше)**: эта версия eglot не обрабатывает semanticTokens. Поэтому
  **`typelisp-mode` сам отправляет запрос и рисует результат оверлеями**
  (`typelisp-semantic-tokens-mode`, включается автоматически при подключении eglot)
- **`lsp-mode`**: встроенная поддержка (установите `lsp-semantic-tokens-enable` в `t`). В этом
  случае `typelisp-mode` не вмешивается

`scripts/emacs-semantic-smoke.el` действительно подключается через eglot и проверяет ту сторону,
которая отвечает за отрисовку в используемом Emacs. С любым клиентом запасной способ внутри буфера
отступает, пока сервер отвечает (чтобы два набора правил не раскрашивали один и тот же буфер).

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `typelisp-semantic-tokens` | `t` | При использовании eglot из Emacs 30 и старше — раскрашивать ли по semantic tokens сервера |
| `typelisp-semantic-tokens-idle-delay` | `0.6` | Секунды простоя после правки перед повторным запросом (держите больше, чем `eglot-send-changes-idle-time`) |

## Примечания

- typelisp при чтении переводит символы в нижний регистр, но подсветка учитывает регистр, чтобы
  отличать имена типов, начинающиеся с заглавной буквы.
- Отступы определяет отдельная функция `typelisp-indent-function`, которая смотрит в
  `typelisp-indent-specs` (ассоциативный список). Режим хранит собственные записи даже для форм,
  чьи имена совпадают с Emacs Lisp (`defun` `let` `if` ...), потому что свойства символов
  **глобальны**, и настройки для typelisp там изменили бы отступы других Lisp-буферов той же
  сессии. К тому же формы typelisp отличаются по устройству даже при совпадении имени с Emacs Lisp —
  у `(defun NAME (PARAMS) RETTYPE ...)` три элемента заголовка, а у `if` всегда три элемента с
  обязательным `else`, — поэтому и значения общими быть не могут.
  Проверено, что `indent-region` не меняет ни одного байта ни в одном файле `.typl` в `examples/`,
  и что удаление всех отступов с последующей повторной расстановкой восстанавливает оригинал
  (версия для VS Code удовлетворяет тому же критерию на тех же файлах).

## Обнаружение расхождений в определениях редакторов

Таблицы ключевых слов ведутся в двух местах — здесь и в версии для VS Code. Чтобы определения
редакторов не отставали от продвигающейся реализации, на стороне Rust есть тест:

```sh
cargo test --test editor_keyword_sync_test
```

Он действительно загружает prelude, обходит реестр и сообщает **имена, которые неизвестны одному из
редакторов**. У специальных форм нет представления во время выполнения, поэтому они читаются между
`// SPECIAL-FORM DISPATCH BEGIN` / `END` в `crates/typelisp-front/src/check/checker.rs` (не удаляйте
эти комментарии). Если тест не проходит, добавьте названные имена в определения **обоих**
редакторов.

Тот же тест сверяет и легенду semantic tokens (`SEMANTIC_TOKEN_TYPES` в `src/bin/lsp.rs` и таблицы
обоих редакторов должны совпадать по именам и порядку). Расхождение не вызывает ошибки во время
выполнения; оно лишь меняет местами цвета всех токенов, поэтому закреплено автоматической проверкой.
