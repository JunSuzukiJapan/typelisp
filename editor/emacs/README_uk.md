# typelisp-mode (Emacs)

Основний режим Emacs для редагування вихідного коду typelisp (`.typl`).
Версія для VS Code міститься в [../vscode/](../vscode/README_uk.md). Обидві використовують однакові таблиці
ключових слів і однакові правила відступів, а `cargo test --test editor_keyword_sync_test` перевіряє це
механічно (див. кінець цього документа).

## Можливості

- Підсвічування синтаксису
  - Спеціальні форми та керівні конструкції (`defun` `let` `if` `match` `loop` `lambda` `setf` `as`
    `apply`, `print`/`println`/`format`, родина `pprint` тощо)
  - Визначені імена (`NAME` у `(defun NAME ...)` як ім'я функції, у `(defstruct NAME ...)`
    як ім'я типу та у `(defvar (NAME ...))` як ім'я змінної; те саме з `pub`, як-от
    `(pub defun NAME ...)`)
  - Ключові слова просторів імен і оголошень (`pub` `module` `use` `load` `impl` `where`) і маркери
    списку параметрів лямбди (`&rest` `&optional` `&key`)
  - Вбудовані функції (`car` `map` `foldl` `unwrap` `parse-int` `message` `sexpr-car` тощо)
  - Примітивні типи (зокрема `bignum` / `ratio`), вбудовані типи, вбудовані типи помилок
    (`ParseIntError` тощо), користувацькі типи з великої літери (`Capitalized`) і тип трейт-об'єкта `:dyn Trait`
  - **Використання користувацьких типів** (імена `defstruct`/`defenum`/`deftrait` зазвичай пишуть
    малими літерами (`rect` `todo-item` `board`), тож правило `Capitalized` їх не ловить).
    У поєднанні з `typl-lsp` вони розфарбовуються семантичними токенами сервера (це працює і з `eglot`;
    див. нижче). Без підключення режим переходить до збирання імен типів, визначених у буфері
  - Літерали (`true` `false`, літерали чисел (десяткові / `0xff` / `1.5` / `1/3`), літерали знаків,
    як-от `#\Space`, рядки, ключові слова на кшталт `:name`)
  - Керівні директиви `format` усередині рядків (`~a` `~5,'0d` `~{...~}` тощо)
  - Глобальні змінні в стилі CL із зірочками (`*print-pretty*` тощо)
- Коментарі
  - Рядкові коментарі `;`
  - **Вкладені** блокові коментарі `#| ... |#`
- Навігація S-виразами та відступи в стилі Lisp
- Покажчик визначень через `imenu` (функції / методи / макроси / типи / трейти / `impl` /
  змінні / модулі)
- Команди, що запускають CLI `typl` (нижче)

## Прив'язки клавіш

| Клавіша | Команда | Що робить |
|---|---|---|
| `C-c C-c` | `typelisp-run-buffer` | Зберегти й запустити `typl FILE` (через `compile`, тож можна переходити до рядків із помилками) |
| `C-c C-z` | `typelisp-repl` | Запустити REPL `typl` у буфері comint |

Розташування `typl` задається через `typelisp-program` (типово `"typl"`).
Діагностика має вигляд `error: FILE:LINE:COL: ...`, який уміє розбирати `compilation-mode`, тож
`next-error` / `C-x \`` переходить просто до місця.

## Встановлення

```elisp
(add-to-list 'load-path "/path/to/typelisp/editor/emacs")
(require 'typelisp-mode)
```

Файли `.typl` відкриваються в `typelisp-mode` автоматично (режим зареєстровано в `auto-mode-alist`).

З `use-package`:

```elisp
(use-package typelisp-mode
  :load-path "/path/to/typelisp/editor/emacs"
  :mode "\\.typl\\'")
```

## Мовний сервер (`typl-lsp`)

Після збирання `typl-lsp` його можна використовувати з `eglot` (вбудований в Emacs 29+) або `lsp-mode`.

```sh
cargo build --release --bin typl-lsp
```

З `eglot`:

```elisp
(with-eval-after-load 'eglot
  (add-to-list 'eglot-server-programs
               '(typelisp-mode . ("/path/to/typelisp/target/release/typl-lsp"))))
(add-hook 'typelisp-mode-hook #'eglot-ensure)
```

З `lsp-mode`:

```elisp
(with-eval-after-load 'lsp-mode
  (lsp-register-client
   (make-lsp-client
    :new-connection (lsp-stdio-connection "/path/to/typelisp/target/release/typl-lsp")
    :major-modes '(typelisp-mode)
    :server-id 'typl-lsp)))
(add-hook 'typelisp-mode-hook #'lsp)
```

Підтримується: діагностика (синтаксичні помилки та помилки типів і попередження про перевизначення,
що надсилаються через `textDocument/publishDiagnostics`), наведення, перехід до визначення, автодоповнення
(`:` зареєстровано як символ-тригер) і семантичні токени. Посилання між файлами через `use` розв'язуються
(сервер шукає вгору файл `typelisp.toml` кореня проєкту; подробиці в
[Довіднику із синтаксису 3.11](../../docs/uk/reference/syntax.md#311-файли-та-модулі-багатофайлові-проєкти)).
Незбережені правки у відкритих буферах редактора одразу відображаються в діагностиці як файлів, від яких
вони залежать, так і файлів, які залежать від них.

### Підсвічування імен типів (семантичні токени)

Через `textDocument/semanticTokens` сервер повідомляє **позиції, які перевіряльник справді розв'язав як
імена типів**. Оскільки це не зіставлення тексту:

- Типи, що приходять з інших файлів через `use`, теж розфарбовуються (діапазон, якого розв'язання
  всередині буфера принципово не досягає)
- Виклики **функції** з такою самою назвою, як у типу, не розфарбовуються (перевіряльник розв'язав їх
  як функції, тож токен там узагалі не записується)

З боку клієнта:

- **`eglot` (Emacs 31 і новіші)**: eglot сам малює токени (`eglot-semantic-tokens-mode`).
  `typelisp-mode` не втручається
- **`eglot` (Emacs 30 і старіші)**: ця версія eglot не обробляє semanticTokens. Тому
  **`typelisp-mode` сам надсилає запит і малює результат оверлеями**
  (`typelisp-semantic-tokens-mode`, вмикається автоматично, коли eglot підключається)
- **`lsp-mode`**: рідна підтримка (установіть `lsp-semantic-tokens-enable` у `t`). У цьому разі
  `typelisp-mode` не втручається

`scripts/emacs-semantic-smoke.el` справді підключається через eglot і перевіряє той бік, що малює, в
Emacs, який використовується. З будь-яким клієнтом запасний варіант у межах буфера відступає, поки сервер
відповідає (щоб два набори правил не розфарбовували той самий буфер).

| Налаштування | Типове значення | Що робить |
|---|---|---|
| `typelisp-semantic-tokens` | `t` | У eglot Emacs 30 і старіших: чи розфарбовувати за семантичними токенами сервера |
| `typelisp-semantic-tokens-idle-delay` | `0.6` | Секунди бездіяльності після правки перед повторним запитом (тримайте більшим за `eglot-send-changes-idle-time`) |

## Примітки

- typelisp переводить символи в нижній регістр під час читання, але підсвічування залежить від регістру,
  щоб можна було відрізнити імена типів, що починаються з великої літери.
- Відступи визначаються окремою функцією `typelisp-indent-function`, яка звертається до
  `typelisp-indent-specs` (асоціативного списку). Режим тримає власні записи навіть для форм, назви яких
  збігаються з Emacs Lisp (`defun` `let` `if` ...), бо властивості символів **глобальні**, і налаштування
  typelisp там змінили б відступи інших буферів Lisp у тому самому сеансі.
  До того ж форми typelisp відрізняються за будовою, навіть коли ділять назву з Emacs Lisp:
  `(defun NAME (PARAMS) RETTYPE ...)` має три елементи заголовка, а `if` має фіксовані три
  елементи з обов'язковою гілкою `else`. Тож значення теж не можна ділити.
  Усі файли `.typl` у `examples/` перевірено: `indent-region` не змінює жодного байта,
  а вирівнювання всіх відступів і повторне відступання відновлюють оригінал (версія для VS Code
  відповідає тому самому стандарту на тих самих файлах).

## Виявлення розбіжностей у визначеннях редакторів

Таблиці ключових слів підтримуються двічі, тут і у версії для VS Code. Щоб визначення
редакторів не відставали, поки реалізація рухається вперед, на боці Rust є тест:

```sh
cargo test --test editor_keyword_sync_test
```

Він справді завантажує prelude, обходить реєстр і повідомляє про **імена, яких не знає котрийсь із
редакторів**. Спеціальні форми не мають представлення під час виконання, тому їх читають між
`// SPECIAL-FORM DISPATCH BEGIN` / `END` у `crates/typelisp-front/src/check/checker.rs` (не видаляйте ці
коментарі). Якщо тест падає, додайте названі імена до **обох** визначень редакторів.

Той самий тест порівнює також легенду семантичних токенів (`SEMANTIC_TOKEN_TYPES` у
`src/bin/lsp.rs` і таблиці в обох редакторах мають збігатися за назвами та порядком). Розбіжність не
спричиняє помилки під час виконання; вона лише міняє місцями кольори всіх токенів, тому її закріплено
механічно.
