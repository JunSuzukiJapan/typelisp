# typelisp (VS Code)

Расширение VS Code для редактирования исходного кода typelisp (`.typl`).
Версия для Emacs находится в [../emacs/](../emacs/README_ru.md). Обе используют одни и те же таблицы
ключевых слов и одни и те же правила отступов, и `cargo test --test editor_keyword_sync_test`
проверяет это автоматически (см. ниже).

## Возможности

- **Подсветка синтаксиса** (грамматика TextMate; языковой сервер не нужен)
  - Специальные формы и управляющие конструкции (`defun` `let` `if` `match` `loop` `lambda` `setf`
    `as` `apply`, `print`/`println`/`format`, семейство `pprint`)
  - Определяемые имена (`(defun NAME ...)` как функция, `(defstruct NAME ...)` как тип,
    `(defvar (NAME ...))` как переменная; то же с `pub`, как в `(pub defun NAME ...)`) и оба имени
    в `(impl Trait Type)`
  - Ключевые слова пространств имён и объявлений (`pub` `module` `use` `load` `impl` `where`) и
    маркеры лямбда-списка (`&rest` `&optional` `&key`)
  - Встроенные функции, примитивные типы (включая `bignum` / `ratio`), встроенные типы ошибок,
    пользовательские типы `Capitalized` и тип трейт-объекта `:dyn Trait` (в том числе внутри
    обобщённых аргументов)
  - Числовые литералы (десятичные / `0xff` / `1.5` / `3.0e10` / `1/3`), литералы символов вроде
    `#\Space`, ключевые слова вроде `:name` и глобальные переменные с «наушниками» вроде
    `*print-pretty*`
  - **Управляющие директивы `format` внутри строк** (`~a` `~5,'0d` `~{...~}` `~^` и т. д.)
  - Строчные комментарии `;` и **вкладываемые** блочные комментарии `#| ... |#`
- **Места использования пользовательских типов** (semantic tokens)
  - Имена `defstruct` / `defenum` / `deftrait` обычно пишутся строчными буквами (`rect`
    `todo-item` `board`), поэтому правило `Capitalized` их не находит, а грамматика TextMate
    работает построчно и не видит файл целиком. Semantic tokens видят, и это устраняет ситуацию,
    когда в языке со статической типизацией именно аннотации типов оставались без цвета
  - При подключении к `typl-lsp` расширение получает **позиции, которые проверка типов
    действительно разрешила как имена типов**. Поэтому типы, пришедшие из других файлов через
    `use`, раскрашиваются, а вызовы **функции** с тем же именем, что у типа, — нет (проверка
    разрешила их как функции, поэтому токен там вообще не записывается)
  - Если сервер не подключён или не собран, расширение переходит к текстовому поиску, который
    разрешает имена внутри файла. Это приближение: он не находит типы из других файлов и не может
    отличить функцию с тем же именем, что у типа
- **Отступы Lisp** (в VS Code нет встроенных отступов для Lisp, поэтому их реализует расширение)
  - Форматирование документа, форматирование выделения и форматирование при вводе (Enter и `)`,
    когда включён `editor.formatOnType`)
- **Outline / breadcrumbs / `Ctrl+Shift+O`** (функции, методы, макросы, типы, трейты, `impl`,
  переменные, модули)
- **Интеграция с `typl-lsp`** (диагностика, hover, переход к определению, автодополнение, semantic
  tokens)
- **Команды CLI `typl`** (запуск, REPL)

Всё, кроме языкового сервера, работает с одним только расширением, поэтому даже в копии, где
`typl-lsp` не собран, доступны подсветка, отступы, Outline и (ограниченная файлом) подсветка типов.

## Установка

Расширения нет в Marketplace, поэтому его нужно собрать и установить локально.

```sh
cd editor/vscode
npm install
npm run compile
```

Затем один из вариантов:

- **Попробовать в хосте разработки**: откройте `editor/vscode` в VS Code и нажмите `F5`
- **Установить насовсем**: создайте `.vsix` командой `npx @vscode/vsce package`, затем в
  представлении расширений выберите «...» → «Install from VSIX...»

Файлы `.typl` автоматически открываются в режиме typelisp.

## Сочетания клавиш

| Клавиша | Команда | Что делает |
|---|---|---|
| `Ctrl+Alt+R` | `typelisp.runFile` | Сохраняет и запускает `typl FILE` |
| `Ctrl+Alt+Z` | `typelisp.repl` | Запускает REPL `typl` |

В палитре команд есть также `typelisp: Restart Language Server`.

## Настройки

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `typelisp.program` | `typl` | Путь к CLI `typl` |
| `typelisp.languageServer.enable` | `true` | Подключаться ли к `typl-lsp` |
| `typelisp.languageServer.path` | (пусто) | Путь к `typl-lsp`. Если пусто, поиск идёт в таком порядке: `target/release/typl-lsp` рабочей области, `target/debug/typl-lsp`, `PATH` |
| `typelisp.trace.server` | `off` | Записывает обмен JSON-RPC по LSP |

Языковой сервер собирается так:

```sh
cargo build --release --bin typl-lsp
```

Ссылки между файлами через `use` разрешаются поиском вверх `typelisp.toml` корня проекта
(подробности в [Справочнике по синтаксису 3.11](../../docs/ru/reference/syntax.md#311-файлы-и-модули-многофайловые-проекты)).

## Problem matcher для задач

Расширение предоставляет problem matcher с именем `typelisp`. `typl` выводит диагностику в виде
`error: FILE:LINE:COL: message`, поэтому её можно сразу показывать на панели «Проблемы»:

```jsonc
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "typl: run",
      "type": "shell",
      "command": "typl ${file}",
      "problemMatcher": "$typelisp"
    }
  ]
}
```

## Разработка

```sh
npm run compile   # tsc
npm run watch     # пересборка при изменениях
npm test          # node --test (грамматика, отступы, символы, ссылки на типы, манифест)
```

Тесты охватывают только те части, которым не нужен модуль `vscode`. Для этого `src/indent.ts` и
`src/symbols.ts` написаны как чистые функции, и только `src/extension.ts` обращается к API
редактора.

- `src/test/grammar.test.ts` — по-настоящему разбивает текст на токены грамматикой тем же движком,
  что и VS Code (`vscode-textmate` + `vscode-oniguruma`), и проверяет результат.
  Oniguruma отличается от регулярных выражений Emacs в деталях (например, не считает литералом `]`
  в начале класса символов), и такие различия обнаруживаются только при запуске настоящего движка.
- `src/test/indent.test.ts` — для каждого файла `.typl` в `examples/` требует, чтобы **удаление
  всех отступов и их восстановление побайтно совпадало с закоммиченным содержимым**.
  Режим Emacs удовлетворяет тому же критерию на тех же файлах, и именно это делает утверждение
  «оба редактора совпадают» проверенным.
  Кроме того, `src/test/fixtures/emacs-indent-reference.txt` — эталонный вывод, полученный реальным
  запуском `indent-region` в буфере `typelisp-mode` в Emacs. Ожидаемое значение — не пересказ
  реализации на TS, а **то, что действительно выдаёт другой редактор**, поэтому точность переноса
  проверяется напрямую (включая `let*` `do` `doiter` `labels` `impl` `pprint-logical-block`,
  префиксы quote и другое).
- `src/test/symbols.test.ts` — содержимое Outline и обнаружение ссылок на типы запасным способом.
  Число определений должно точно совпадать с независимым подсчётом форм определения в начале строк.
  Правила границ для ссылок на типы намеренно согласованы с запасным способом версии для Emacs
  (VS Code использует lookbehind; Emacs выражает то же множество, поглощая один предшествующий
  символ).
- Токены сервера, основанные на разрешении имён (`crates/typelisp-front/src/check/semantic.rs`),
  проверяют `cargo test --test lsp_semantic_test` и `scripts/lsp-semantic-smoke.py` (управляет
  настоящим процессом через stdio). Клиент Emacs проверяет `scripts/emacs-semantic-smoke.el` через
  настоящее подключение eglot.
- `src/test/manifest.test.ts` — `package.json` единственная часть, которую не проверяет
  компилятор, поэтому этот тест проверяет, что объявленные команды и вызовы `registerCommand`
  образуют одно и то же множество, на что ссылаются сочетания клавиш, что настройки, которые
  читает код, объявлены, и что problem matcher умеет разбирать то, что действительно выводит `typl`.

### Обнаружение расхождений в определениях редакторов

Таблицы ключевых слов ведутся в двух местах — в версии для Emacs и в версии для VS Code. Чтобы
определения редакторов не отставали от продвигающейся реализации, на стороне Rust есть тест:

```sh
cargo test --test editor_keyword_sync_test
```

Он действительно загружает prelude, обходит реестр и сообщает **имена, которые неизвестны одному из
редакторов**. У специальных форм нет представления во время выполнения, поэтому они читаются между
`// SPECIAL-FORM DISPATCH BEGIN` / `END` в `crates/typelisp-front/src/check/checker.rs` (не удаляйте
эти комментарии). Если тест не проходит, добавьте названные имена в определения **обоих**
редакторов.

Тот же тест сверяет и легенду semantic tokens (`SEMANTIC_TOKEN_TYPES` в `src/bin/lsp.rs` и таблицы
обоих редакторов должны совпадать по именам и порядку). Расхождение не вызывает ошибки во время
выполнения; оно лишь меняет местами цвета всех токенов, поэтому закреплено автоматической проверкой.

## Примечания

- typelisp при чтении переводит символы в нижний регистр, но подсветка учитывает регистр, чтобы
  отличать имена типов, начинающиеся с заглавной буквы.
- Отступы определяет `INDENT_SPECS` в `src/indent.ts`. Это перенос `typelisp-indent-specs` из
  версии для Emacs с теми же значениями и правилами. Места, где форма отличается по устройству от
  одноимённой формы Emacs Lisp, перенесены как есть: заголовок `(defun NAME (PARAMS) RETTYPE ...)`
  состоит из трёх элементов, у `if` всегда три элемента с обязательным `else` и т. д.
- Содержимое `#| ... |#` при форматировании получает новые отступы. Это совпадает с поведением
  `indent-region` в Emacs.
