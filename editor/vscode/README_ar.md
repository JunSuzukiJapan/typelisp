# typelisp (VS Code)

امتداد VS Code لتحرير مصدر typelisp (`.typl`).
نسخة Emacs في [../emacs/](../emacs/README_ar.md). وتتشارك النسختان جداول الكلمات المفتاحية نفسها
وقواعد الإزاحة نفسها، ويتحقق `cargo test --test editor_keyword_sync_test` من ذلك آليًا (انظر
أدناه).

## الميزات

- **تلوين الصياغة** (قواعد TextMate؛ ولا حاجة إلى خادم لغة)
  - الصيغ الخاصة وبنى التحكم (`defun` `let` `if` `match` `loop` `lambda` `setf` `as`
    `apply` و`print`/`println`/`format` وعائلة `pprint`)
  - الأسماء المعرَّفة (`(defun NAME ...)` على أنها دالة و`(defstruct NAME ...)` على أنها نوع و
    `(defvar (NAME ...))` على أنها متغير؛ والأمر نفسه مع `pub` كما في `(pub defun NAME ...)`) وكلا
    اسمَي `(impl Trait Type)`
  - كلمات مفتاحية لمساحات الأسماء والإعلانات (`pub` `module` `use` `load` `impl` `where`) وعلامات قائمة
    الوسائط (`&rest` `&optional` `&key`)
  - الدوال المضمنة والأنواع الأولية (بما في ذلك `bignum` / `ratio`) وأنواع الأخطاء المضمنة وأنواع المستخدم
    ذات الحرف الأول الكبير `Capitalized`، ونوع كائن السمة `:dyn Trait` (داخل الوسائط العامة أيضًا)
  - ثوابت الأعداد (عشري / `0xff` / `1.5` / `3.0e10` / `1/3`) وثوابت المحارف مثل `#\Space` والكلمات
    المفتاحية مثل `:name` والمتغيرات العامة ذات علامات النجمة مثل `*print-pretty*`
  - **موجِّهات تحكم `format` داخل السلاسل النصية** (`~a` `~5,'0d` `~{...~}` `~^` وهكذا)
  - التعليقات السطرية `;` والتعليقات الكتلية **القابلة للتداخل** `#| ... |#`
- **استخدامات الأنواع المعرَّفة من المستخدم** (الرموز الدلالية)
  - أسماء `defstruct` / `defenum` / `deftrait` عادةً بأحرف صغيرة (`rect` `todo-item`
    `board`)، فلا تلتقطها قاعدة `Capitalized`، وتعمل قواعد TextMate سطرًا بسطر ولا ترى الملف كله.
    أما الرموز الدلالية فتستطيع، وهذا يصلح الحالة التي كانت لغة ذات أنواع ساكنة تترك فيها توصيفات أنواعها
    وحدها بلا تلوين
  - وعند الاتصال بـ `typl-lsp` يستلم الامتداد **المواضع التي حلّها الفاحص فعلًا على أنها أسماء أنواع**.
    فتُلوَّن الأنواع القادمة من ملفات أخرى عبر `use`، ولا تُلوَّن استدعاءات **دالة** بالاسم نفسه كنوع (فقد
    حلّها الفاحص على أنها دوال، فلا يُسجَّل رمز هناك أصلًا)
  - وعندما لا يكون الخادم متصلًا أو لم يُبنَ يرجع الامتداد إلى مسح نصي يحلّ داخل الملف. وهذا تقريب: فلا يجد
    أنواعًا من ملفات أخرى، ولا يميّز دالة بالاسم نفسه كنوع
- **إزاحة Lisp** (ليس في VS Code إزاحة Lisp مدمجة، فينفّذها الامتداد)
  - تنسيق المستند وتنسيق التحديد والتنسيق أثناء الكتابة (Enter و`)`، عند تفعيل
    `editor.formatOnType`)
- **المخطط / فتات الخبز (breadcrumbs) / `Ctrl+Shift+O`** (دوال وتوابع وماكرو وأنواع وسمات و`impl`
  ومتغيرات ووحدات)
- **التكامل مع `typl-lsp`** (تشخيصات وhover وانتقال إلى التعريف وإكمال ورموز دلالية)
- **أوامر واجهة `typl`** (تشغيل، REPL)

كل شيء عدا خادم اللغة يعمل بالامتداد وحده، فحتى في نسخة لم يُبنَ فيها `typl-lsp` تتوفر ميزات التلوين
والإزاحة والمخطط وتلوين الأنواع (داخل الملف).

## التثبيت

الامتداد ليس على Marketplace، لذا ابنِه محليًا وثبّته.

```sh
cd editor/vscode
npm install
npm run compile
```

ثم إما:

- **جرّبه في مضيف تطوير**: افتح `editor/vscode` في VS Code واضغط `F5`
- **ثبّته بصورة دائمة**: اصنع `.vsix` بـ `npx @vscode/vsce package`، ثم استخدم
  "..." ← "Install from VSIX..." في عرض الامتدادات

تُفتح ملفات `.typl` في وضع typelisp تلقائيًا.

## اختصارات المفاتيح

| المفتاح | الأمر | ما يفعله |
|---|---|---|
| `Ctrl+Alt+R` | `typelisp.runFile` | يحفظ ويشغّل `typl FILE` |
| `Ctrl+Alt+Z` | `typelisp.repl` | يبدأ الـ REPL الخاص بـ `typl` |

وفي لوحة الأوامر أيضًا `typelisp: Restart Language Server`.

## الإعدادات

| الإعداد | الافتراضي | ما يفعله |
|---|---|---|
| `typelisp.program` | `typl` | مسار واجهة `typl` |
| `typelisp.languageServer.enable` | `true` | هل يُتصل بـ `typl-lsp` |
| `typelisp.languageServer.path` | (فارغ) | مسار `typl-lsp`. وعندما يكون فارغًا يبحث الامتداد عن `target/release/typl-lsp` في مساحة العمل، ثم `target/debug/typl-lsp`، ثم `PATH` |
| `typelisp.trace.server` | `off` | يسجّل حركة LSP JSON-RPC |

ابنِ خادم اللغة بـ:

```sh
cargo build --release --bin typl-lsp
```

تُحَلّ المراجع بين الملفات عبر `use` بالبحث صعودًا عن `typelisp.toml` في جذر المشروع (وللتفاصيل انظر
[مرجع الصياغة 3.11](../../docs/ar/reference/syntax.md#311-الملفات-والوحدات-مشاريع-متعددة-الملفات)).

## مطابِق المشكلات (problem matcher) للمهام

يوفر الامتداد مطابِق مشكلات باسم `typelisp`. فـ `typl` تطبع التشخيصات على الصورة
`error: FILE:LINE:COL: message`، فيمكن أن تذهب مباشرة إلى لوحة Problems:

```jsonc
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "typl: run",
      "type": "shell",
      "command": "typl ${file}",
      "problemMatcher": "$typelisp"
    }
  ]
}
```

## التطوير

```sh
npm run compile   # tsc
npm run watch     # يبني عند التغيير
npm test          # node --test (القواعد والإزاحة والرموز ومراجع الأنواع والبيان)
```

تغطي الاختبارات الأجزاء التي لا تحتاج إلى وحدة `vscode` فقط. ولهذا كُتب `src/indent.ts` و
`src/symbols.ts` على صورة دوال نقية، ولا يلمس واجهة المحرر إلا `src/extension.ts`.

- `src/test/grammar.test.ts` — يحلل بالقواعد فعليًا باستخدام المحرك نفسه كما في VS
  Code (`vscode-textmate` + `vscode-oniguruma`) ويفحص النتيجة.
  فـ Oniguruma تختلف عن التعابير النمطية في Emacs في التفاصيل (فمثلًا لا تعامل `]` في بداية فئة محارف
  على أنها حرفية)، ولا تُكتشف فروق كهذه إلا بتشغيل المحرك الحقيقي.
- `src/test/indent.test.ts` — لكل ملف `.typl` تحت `examples/` يشترط أن
  **تسوية كل الإزاحة ثم استعادتها تطابق المحتوى المُودَع بايتًا ببايت**.
  ويستوفي وضع Emacs المعيار نفسه على الملفات نفسها، وهذا ما يجعل "اتفاق المحررين" ادعاءً مُتحققًا منه.
  وإضافة إلى ذلك فإن `src/test/fixtures/emacs-indent-reference.txt` خرج مرجعي جُمع بتشغيل
  `indent-region` فعليًا في مخزن `typelisp-mode` في Emacs. فالجانب المتوقع ليس إعادة صياغة لتنفيذ TS بل
  **ما ينتجه المحرر الآخر فعلًا**، فتُفحص أمانة النقل مباشرة (ويشمل `let*` و`do` و`doiter` و`labels` و`impl`
  و`pprint-logical-block` وبوادئ الاقتباس وغيرها).
- `src/test/symbols.test.ts` — محتويات المخطط واكتشاف مراجع الأنواع في الرجوع الاحتياطي. ويجب أن يطابق
  عدد التعريفات بالضبط عدًّا مستقلًا لصيغ التعريف في بدايات الأسطر. وقواعد حدود مراجع الأنواع
  مُواءَمة عمدًا مع الرجوع الاحتياطي في نسخة Emacs (يستخدم VS Code lookbehind؛ وتعبّر Emacs عن المجموعة
  نفسها باستهلاك محرف سابق واحد).
- الرموز التي يقودها الحل في الخادم (`crates/typelisp-front/src/check/semantic.rs`)
  يفحصها `cargo test --test lsp_semantic_test` و`scripts/lsp-semantic-smoke.py` (الذي
  يقود عملية حقيقية عبر stdio). ويفحص عميل Emacs
  `scripts/emacs-semantic-smoke.el` عبر اتصال eglot حقيقي.
- `src/test/manifest.test.ts` — `package.json` هو الجزء الوحيد الذي لا يفحصه المترجم، فهذا يفحص
  أن الأوامر المعلَنة واستدعاءات `registerCommand` هي المجموعة نفسها، وما تشير إليه اختصارات المفاتيح، وأن
  الإعدادات التي تقرؤها الشيفرة معلَنة، وأن مطابِق المشكلات يستطيع تحليل ما تطبعه `typl` فعلًا.

### اكتشاف الانجراف في تعريفات المحررات

تُصان جداول الكلمات المفتاحية مرتين، في نسخة Emacs ونسخة VS Code. ولمنع تخلف تعريفات المحررين بينما يمضي
التنفيذ قدمًا يوجد اختبار في جانب Rust:

```sh
cargo test --test editor_keyword_sync_test
```

يحمّل المكتبة القياسية فعلًا، ويمر على السجل، ويبلّغ عن **الأسماء التي لا يعرفها أي من المحررين**. وليس
للصيغ الخاصة تمثيل وقت التشغيل، فتُقرأ من بين
`// SPECIAL-FORM DISPATCH BEGIN` / `END` في `crates/typelisp-front/src/check/checker.rs` (لا تحذف هذين
التعليقين). وإذا فشل فأضف الأسماء المبلَّغ عنها إلى تعريفات **كلا** المحررين.

ويقارن الاختبار نفسه أيضًا أسطورة الرموز الدلالية (`SEMANTIC_TOKEN_TYPES` في
`src/bin/lsp.rs` والجداول التي يحملها المحرران يجب أن تتفق في الأسماء والترتيب). وعدم التطابق لا يسبب خطأ
وقت التشغيل؛ بل يبدّل ألوان كل رمز فقط، لذلك يُثبَّت آليًا.

## ملاحظات

- تحوّل typelisp الرموز إلى أحرف صغيرة عند القراءة، لكن التلوين حساس لحالة الأحرف ليمكن تمييز أسماء
  الأنواع التي تبدأ بحرف كبير.
- تتحدد الإزاحة بـ `INDENT_SPECS` في `src/indent.ts`. وهي نقل لـ
  `typelisp-indent-specs` في نسخة Emacs، بالقيم والقواعد نفسها. والمواضع التي تختلف فيها صيغة في الشكل
  عن صيغة Emacs Lisp بالاسم نفسه تُنقَل كما هي: ترويسة
  `(defun NAME (PARAMS) RETTYPE ...)` لها ثلاثة عناصر، و`if` ثابتة على ثلاثة عناصر مع `else` إلزامية،
  وهكذا.
- يُعاد إزاحة محتويات `#| ... |#` عند التنسيق. وهذا يطابق سلوك `indent-region` في Emacs.
