# typelisp (VS Code)

typelisp सोर्स (`.typl`) को संपादित करने के लिए VS Code एक्सटेंशन।
Emacs संस्करण [../emacs/](../emacs/README_hi.md) में है। दोनों समान कीवर्ड तालिकाएँ और समान इंडेंटेशन नियम साझा करते हैं, और `cargo test --test editor_keyword_sync_test` इसे यांत्रिक रूप से जाँचता है (नीचे देखें)।

## सुविधाएँ

- **सिंटैक्स हाइलाइटिंग** (TextMate ग्रामर; भाषा सर्वर की ज़रूरत नहीं)
  - विशेष फ़ॉर्म और नियंत्रण संरचनाएँ (`defun` `let` `if` `match` `loop` `lambda` `setf` `as` `apply`, `print`/`println`/`format`, `pprint` परिवार)
  - परिभाषित नाम (`(defun NAME ...)` फ़ंक्शन के रूप में, `(defstruct NAME ...)` टाइप के रूप में, `(defvar (NAME ...))` वेरिएबल के रूप में; `(pub defun NAME ...)` की तरह `pub` के साथ भी यही) और `(impl Trait Type)` के दोनों नाम
  - नेमस्पेस और घोषणा कीवर्ड (`pub` `module` `use` `load` `impl` `where`) और लैम्ब्डा सूची मार्कर (`&rest` `&optional` `&key`)
  - बिल्ट-इन फ़ंक्शन, आदिम टाइप (`bignum` / `ratio` सहित), बिल्ट-इन त्रुटि टाइप, `Capitalized` उपयोगकर्ता टाइप, और trait ऑब्जेक्ट टाइप `:dyn Trait` (जेनेरिक आर्ग्युमेंट के भीतर भी)
  - संख्या लिटरल (दशमलव / `0xff` / `1.5` / `3.0e10` / `1/3`), `#\Space` जैसे कैरेक्टर लिटरल, `:name` जैसे कीवर्ड, और `*print-pretty*` जैसे earmuff वाले ग्लोबल
  - **स्ट्रिंग के भीतर `format` नियंत्रण निर्देश** (`~a` `~5,'0d` `~{...~}` `~^` आदि)
  - पंक्ति टिप्पणियाँ `;` और **नेस्ट हो सकने वाली** ब्लॉक टिप्पणियाँ `#| ... |#`
- **उपयोगकर्ता-परिभाषित टाइप के उपयोग** (सिमैंटिक टोकन)
  - `defstruct` / `defenum` / `deftrait` के नाम आमतौर पर छोटे अक्षरों में होते हैं (`rect` `todo-item` `board`), इसलिए `Capitalized` नियम उन्हें नहीं पकड़ता, और TextMate ग्रामर पंक्ति-दर-पंक्ति काम करता है और पूरी फ़ाइल नहीं देख सकता। सिमैंटिक टोकन देख सकते हैं, जो उस स्थिति को ठीक करता है जिसमें स्टैटिक रूप से टाइप की गई भाषा में केवल उसके टाइप एनोटेशन बिना रंग के रह जाते थे
  - `typl-lsp` से जुड़े होने पर, एक्सटेंशन **वे स्थितियाँ पाता है जिन्हें चेकर ने वास्तव में टाइप नाम के रूप में हल किया**। इसलिए `use` से दूसरी फ़ाइलों से आने वाले टाइप रंगे जाते हैं, और टाइप के समान नाम वाले **फ़ंक्शन** के कॉल नहीं रंगे जाते (चेकर ने उन्हें फ़ंक्शन के रूप में हल किया, इसलिए वहाँ पहले से कोई टोकन दर्ज नहीं होता)
  - जब सर्वर जुड़ा न हो या बना न हो, तो एक्सटेंशन फ़ाइल के भीतर हल करने वाले पाठ स्कैन पर लौट जाता है। यह एक सन्निकटन है: यह दूसरी फ़ाइलों के टाइप नहीं खोज सकता, और टाइप के समान नाम वाले फ़ंक्शन में भेद नहीं कर सकता
- **Lisp इंडेंटेशन** (VS Code में Lisp इंडेंटेशन अंतर्निहित नहीं है, इसलिए एक्सटेंशन उसे लागू करता है)
  - Format Document, Format Selection, और टाइप करते समय फ़ॉर्मैट (Enter और `)`, जब `editor.formatOnType` सक्षम हो)
- **आउटलाइन / ब्रेडक्रम्ब / `Ctrl+Shift+O`** (फ़ंक्शन, मेथड, macro, टाइप, trait, `impl`, वेरिएबल, मॉड्यूल)
- **`typl-lsp` इंटीग्रेशन** (डायग्नोस्टिक, hover, परिभाषा पर जाना, कम्प्लीशन, सिमैंटिक टोकन)
- **`typl` CLI कमांड** (चलाना, REPL)

भाषा सर्वर को छोड़कर सब कुछ केवल एक्सटेंशन से काम करता है, इसलिए ऐसे चेकआउट में भी जहाँ `typl-lsp` बना नहीं है, हाइलाइटिंग, इंडेंटेशन, आउटलाइन, और (फ़ाइल-लोकल) टाइप हाइलाइटिंग उपलब्ध हैं।

## इंस्टॉलेशन

एक्सटेंशन Marketplace पर नहीं है, इसलिए इसे लोकल रूप से बिल्ड करके इंस्टॉल करें।

```sh
cd editor/vscode
npm install
npm run compile
```

फिर इनमें से कोई एक:

- **डेवलपमेंट होस्ट में आज़माएँ**: VS Code में `editor/vscode` खोलें और `F5` दबाएँ
- **स्थायी रूप से इंस्टॉल करें**: `npx @vscode/vsce package` से `.vsix` बनाएँ, फिर Extensions व्यू में "..." → "Install from VSIX..." का उपयोग करें

`.typl` फ़ाइलें अपने-आप typelisp मोड में खुलती हैं।

## की बाइंडिंग

| की | कमांड | यह क्या करता है |
|---|---|---|
| `Ctrl+Alt+R` | `typelisp.runFile` | सहेजें और `typl FILE` चलाएँ |
| `Ctrl+Alt+Z` | `typelisp.repl` | `typl` REPL शुरू करें |

कमांड पैलेट में `typelisp: Restart Language Server` भी है।

## सेटिंग

| सेटिंग | डिफ़ॉल्ट | यह क्या करती है |
|---|---|---|
| `typelisp.program` | `typl` | `typl` CLI का पाथ |
| `typelisp.languageServer.enable` | `true` | क्या `typl-lsp` से जुड़ना है |
| `typelisp.languageServer.path` | (खाली) | `typl-lsp` का पाथ। खाली होने पर, एक्सटेंशन वर्कस्पेस का `target/release/typl-lsp`, फिर `target/debug/typl-lsp`, फिर `PATH` खोजता है |
| `typelisp.trace.server` | `off` | LSP JSON-RPC ट्रैफ़िक लॉग करें |

भाषा सर्वर को इससे बिल्ड करें:

```sh
cargo build --release --bin typl-lsp
```

`use` के ज़रिए फ़ाइलों के पार संदर्भ प्रोजेक्ट रूट की `typelisp.toml` को ऊपर की ओर खोजकर हल होते हैं (विवरण के लिए [सिंटैक्स संदर्भ 3.11](../../docs/hi/reference/syntax.md#311-फ़ाइलें-और-मॉड्यूल-बहु-फ़ाइल-प्रोजेक्ट) देखें)।

## टास्क प्रॉब्लम मैचर

एक्सटेंशन `typelisp` नाम का प्रॉब्लम मैचर देता है। `typl` डायग्नोस्टिक `error: FILE:LINE:COL: message` रूप में प्रिंट करता है, इसलिए वे सीधे Problems पैनल में जा सकते हैं:

```jsonc
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "typl: run",
      "type": "shell",
      "command": "typl ${file}",
      "problemMatcher": "$typelisp"
    }
  ]
}
```

## डेवलपमेंट

```sh
npm run compile   # tsc
npm run watch     # बदलाव पर बिल्ड
npm test          # node --test (ग्रामर, इंडेंटेशन, सिंबल, टाइप संदर्भ, मैनिफ़ेस्ट)
```

परीक्षण केवल उन हिस्सों को कवर करते हैं जिन्हें `vscode` मॉड्यूल नहीं चाहिए। इसके लिए, `src/indent.ts` और `src/symbols.ts` शुद्ध फ़ंक्शन के रूप में लिखे गए हैं, और केवल `src/extension.ts` एडिटर API को छूता है।

- `src/test/grammar.test.ts` — ग्रामर से वास्तव में टोकनाइज़ करता है, VS Code जैसे ही इंजन (`vscode-textmate` + `vscode-oniguruma`) से, और परिणाम जाँचता है। Oniguruma विवरण में Emacs के रेगुलर एक्सप्रेशन से भिन्न है (उदाहरण के लिए, वह कैरेक्टर क्लास की शुरुआत के `]` को शाब्दिक नहीं मानता), और ऐसे अंतर केवल वास्तविक इंजन चलाकर ही मिलते हैं।
- `src/test/indent.test.ts` — `examples/` के नीचे हर `.typl` फ़ाइल के लिए, माँगता है कि **सारी इंडेंटेशन समतल करके पुनर्स्थापित करने पर कमिट की गई सामग्री से बाइट-दर-बाइट मेल हो**। Emacs मोड उन्हीं फ़ाइलों पर उसी मानक को पूरा करता है, और यही "दोनों एडिटर सहमत हैं" को सत्यापित दावा बनाता है। इसके अलावा, `src/test/fixtures/emacs-indent-reference.txt` Emacs `typelisp-mode` बफ़र में `indent-region` वास्तव में चलाकर इकट्ठा किया गया संदर्भ आउटपुट है। अपेक्षित पक्ष TS इम्प्लीमेंटेशन का पुनःकथन नहीं बल्कि **वह है जो दूसरा एडिटर वास्तव में बनाता है**, इसलिए पोर्ट की निष्ठा सीधे जाँची जाती है (इसमें `let*` `do` `doiter` `labels` `impl` `pprint-logical-block`, quote उपसर्ग और अन्य शामिल हैं)।
- `src/test/symbols.test.ts` — आउटलाइन की सामग्री और फ़ॉलबैक द्वारा टाइप संदर्भों की पहचान। परिभाषाओं की संख्या पंक्तियों की शुरुआत में परिभाषा फ़ॉर्म की स्वतंत्र गिनती से ठीक मेल खानी चाहिए। टाइप संदर्भों के सीमा नियम जानबूझकर Emacs संस्करण के फ़ॉलबैक से मिलाए गए हैं (VS Code lookbehind उपयोग करता है; Emacs उसी समुच्चय को एक पूर्ववर्ती कैरेक्टर खर्च करके व्यक्त करता है)।
- सर्वर के हल-आधारित टोकन (`crates/typelisp-front/src/check/semantic.rs`) `cargo test --test lsp_semantic_test` और `scripts/lsp-semantic-smoke.py` (जो stdio पर वास्तविक प्रोसेस चलाता है) से जाँचे जाते हैं। Emacs क्लाइंट `scripts/emacs-semantic-smoke.el` से वास्तविक eglot कनेक्शन पर जाँचा जाता है।
- `src/test/manifest.test.ts` — `package.json` एक ऐसा हिस्सा है जिसे कंपाइलर नहीं जाँचता, इसलिए यह जाँचता है कि घोषित कमांड और `registerCommand` कॉल एक ही समुच्चय हैं, की बाइंडिंग किसका संदर्भ लेती हैं, कोड जो सेटिंग पढ़ता है वे घोषित हैं, और प्रॉब्लम मैचर वह पार्स कर सकता है जो `typl` वास्तव में प्रिंट करता है।

### एडिटर परिभाषाओं में विचलन का पता लगाना

कीवर्ड तालिकाएँ दो बार बनाए रखी जाती हैं, Emacs संस्करण और VS Code संस्करण में। इम्प्लीमेंटेशन के आगे बढ़ने पर एडिटर परिभाषाओं के पीछे रह जाने से रोकने के लिए, Rust की ओर एक परीक्षण है:

```sh
cargo test --test editor_keyword_sync_test
```

यह वास्तव में prelude लोड करता है, रजिस्ट्री पर चलता है, और **वे नाम रिपोर्ट करता है जिन्हें कोई भी एडिटर नहीं जानता**। विशेष फ़ॉर्म का कोई रन-टाइम प्रतिनिधित्व नहीं है, इसलिए उन्हें `crates/typelisp-front/src/check/checker.rs` में `// SPECIAL-FORM DISPATCH BEGIN` / `END` के बीच से पढ़ा जाता है (इन टिप्पणियों को न हटाएँ)। यदि यह विफल हो, तो रिपोर्ट किए गए नामों को **दोनों** एडिटर परिभाषाओं में जोड़ें।

वही परीक्षण सिमैंटिक टोकन लेजेंड की भी तुलना करता है (`src/bin/lsp.rs` में `SEMANTIC_TOKEN_TYPES` और दोनों एडिटर जो तालिकाएँ रखते हैं उन्हें नाम और क्रम में मेल खाना चाहिए)। बेमेल होने पर कोई रन-टाइम त्रुटि नहीं होती; यह केवल हर टोकन के रंग आपस में बदल देता है, इसलिए इसे यांत्रिक रूप से पक्का किया गया है।

## टिप्पणियाँ

- typelisp पढ़ते समय सिंबल को छोटे अक्षरों में बदलता है, लेकिन हाइलाइटिंग अक्षर-भेद वाली है ताकि बड़े अक्षर से शुरू होने वाले टाइप नाम अलग पहचाने जा सकें।
- इंडेंटेशन `src/indent.ts` के `INDENT_SPECS` से तय होती है। यह Emacs संस्करण के `typelisp-indent-specs` का पोर्ट है, उन्हीं मानों और नियमों के साथ। जहाँ कोई फ़ॉर्म उसी नाम के Emacs Lisp फ़ॉर्म से आकार में भिन्न है, वे जस के तस आगे लाए गए हैं: `(defun NAME (PARAMS) RETTYPE ...)` के शीर्ष में तीन तत्व हैं, `if` अनिवार्य `else` के साथ तीन तत्वों पर तय है, आदि।
- `#| ... |#` की सामग्री फ़ॉर्मैट करते समय दोबारा इंडेंट होती है। यह Emacs के `indent-region` के व्यवहार से मेल खाता है।
