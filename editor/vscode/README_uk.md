# typelisp (VS Code)

Розширення VS Code для редагування вихідного коду typelisp (`.typl`).
Версія для Emacs міститься в [../emacs/](../emacs/README_uk.md). Обидві використовують однакові таблиці
ключових слів і однакові правила відступів, а `cargo test --test editor_keyword_sync_test` перевіряє це
механічно (див. нижче).

## Можливості

- **Підсвічування синтаксису** (граматика TextMate; мовний сервер не потрібен)
  - Спеціальні форми та керівні конструкції (`defun` `let` `if` `match` `loop` `lambda` `setf` `as`
    `apply`, `print`/`println`/`format`, родина `pprint`)
  - Визначені імена (`(defun NAME ...)` як функція, `(defstruct NAME ...)` як тип,
    `(defvar (NAME ...))` як змінна; те саме з `pub`, як-от `(pub defun NAME ...)`) і
    обидві назви в `(impl Trait Type)`
  - Ключові слова просторів імен і оголошень (`pub` `module` `use` `load` `impl` `where`) і маркери
    списку параметрів лямбди (`&rest` `&optional` `&key`)
  - Вбудовані функції, примітивні типи (зокрема `bignum` / `ratio`), вбудовані типи помилок,
    користувацькі типи з великої літери (`Capitalized`) і тип трейт-об'єкта `:dyn Trait` (також усередині
    узагальнених аргументів)
  - Літерали чисел (десяткові / `0xff` / `1.5` / `3.0e10` / `1/3`), літерали знаків, як-от
    `#\Space`, ключові слова на кшталт `:name` і глобальні змінні із зірочками, як-от `*print-pretty*`
  - **Керівні директиви `format` усередині рядків** (`~a` `~5,'0d` `~{...~}` `~^` тощо)
  - Рядкові коментарі `;` і **вкладені** блокові коментарі `#| ... |#`
- **Використання користувацьких типів** (семантичні токени)
  - Імена `defstruct` / `defenum` / `deftrait` зазвичай пишуть малими літерами (`rect` `todo-item`
    `board`), тож правило `Capitalized` їх не ловить, а граматика TextMate працює порядково й не бачить
    усього файлу. Семантичні токени бачать, і це виправляє стан, коли в мові зі статичною типізацією
    без кольору залишалися лише анотації типів
  - У поєднанні з `typl-lsp` розширення отримує **позиції, які перевіряльник справді розв'язав як імена
    типів**. Тому типи, що приходять з інших файлів через `use`, розфарбовуються, а виклики
    **функції** з такою самою назвою, як у типу, — ні (перевіряльник розв'язав їх як функції, тож токен
    там узагалі не записується)
  - Коли сервер не підключений або не зібраний, розширення переходить до текстового сканування, яке
    розв'язує імена в межах файлу. Це наближення: воно не знаходить типи з інших файлів і не
    відрізняє функцію з такою самою назвою, як у типу
- **Відступи в стилі Lisp** (у VS Code немає вбудованих відступів для Lisp, тому розширення реалізує їх
  саме)
  - Format Document, Format Selection і форматування під час набору (Enter та `)`, коли ввімкнено
    `editor.formatOnType`)
- **Структура / навігаційний ланцюжок / `Ctrl+Shift+O`** (функції, методи, макроси, типи, трейти, `impl`,
  змінні, модулі)
- **Інтеграція з `typl-lsp`** (діагностика, наведення, перехід до визначення, автодоповнення, семантичні
  токени)
- **Команди CLI `typl`** (запуск, REPL)

Усе, крім мовного сервера, працює самим лише розширенням, тож навіть у робочій копії, де `typl-lsp` не
зібрано, доступні підсвічування, відступи, структура та (в межах файлу) підсвічування типів.

## Встановлення

Розширення немає в Marketplace, тому зберіть його локально й встановіть.

```sh
cd editor/vscode
npm install
npm run compile
```

Далі або:

- **Спробувати в середовищі розробки**: відкрийте `editor/vscode` у VS Code і натисніть `F5`
- **Встановити назовсім**: створіть `.vsix` командою `npx @vscode/vsce package`, потім у поданні
  Extensions виберіть «...» → «Install from VSIX...»

Файли `.typl` відкриваються в режимі typelisp автоматично.

## Прив'язки клавіш

| Клавіша | Команда | Що робить |
|---|---|---|
| `Ctrl+Alt+R` | `typelisp.runFile` | Зберегти й запустити `typl FILE` |
| `Ctrl+Alt+Z` | `typelisp.repl` | Запустити REPL `typl` |

У палітрі команд є також `typelisp: Restart Language Server`.

## Налаштування

| Налаштування | Типове значення | Що робить |
|---|---|---|
| `typelisp.program` | `typl` | Шлях до CLI `typl` |
| `typelisp.languageServer.enable` | `true` | Чи підключатися до `typl-lsp` |
| `typelisp.languageServer.path` | (порожньо) | Шлях до `typl-lsp`. Якщо порожньо, розширення шукає `target/release/typl-lsp` робочого простору, потім `target/debug/typl-lsp`, потім `PATH` |
| `typelisp.trace.server` | `off` | Журналювати трафік JSON-RPC протоколу LSP |

Зберіть мовний сервер так:

```sh
cargo build --release --bin typl-lsp
```

Посилання між файлами через `use` розв'язуються пошуком угору файлу `typelisp.toml` кореня проєкту
(подробиці в [Довіднику із синтаксису 3.11](../../docs/uk/reference/syntax.md#311-файли-та-модулі-багатофайлові-проєкти)).

## Зіставлення проблем для завдань

Розширення надає зіставлювач проблем (problem matcher) з назвою `typelisp`. `typl` виводить діагностику у
вигляді `error: FILE:LINE:COL: message`, тож вона може потрапляти просто в панель Problems:

```jsonc
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "typl: run",
      "type": "shell",
      "command": "typl ${file}",
      "problemMatcher": "$typelisp"
    }
  ]
}
```

## Розробка

```sh
npm run compile   # tsc
npm run watch     # збирання при зміні
npm test          # node --test (граматика, відступи, символи, посилання на типи, маніфест)
```

Тести охоплюють лише ті частини, яким не потрібен модуль `vscode`. Для цього `src/indent.ts` і
`src/symbols.ts` написано як чисті функції, а API редактора зачіпає лише `src/extension.ts`.

- `src/test/grammar.test.ts` — по-справжньому токенізує граматикою, тим самим рушієм, що й VS Code
  (`vscode-textmate` + `vscode-oniguruma`), і перевіряє результат.
  Oniguruma відрізняється від регулярних виразів Emacs деталями (наприклад, не вважає `]` на початку
  класу символів літералом), і такі відмінності знаходяться лише запуском справжнього рушія.
- `src/test/indent.test.ts` — для кожного файлу `.typl` у `examples/` вимагає, щоб
  **вирівнювання всіх відступів і їх відновлення збігалися із закоміченим вмістом байт у байт**.
  Режим Emacs відповідає тому самому стандарту на тих самих файлах, і саме це робить твердження
  «обидва редактори збігаються» перевіреним.
  Крім того, `src/test/fixtures/emacs-indent-reference.txt` — це еталонний вивід, зібраний справжнім
  запуском `indent-region` у буфері `typelisp-mode` в Emacs. Очікуване — це не переказ реалізації на TS, а
  **те, що насправді видає інший редактор**, тож вірність перенесення перевіряється безпосередньо (воно
  охоплює `let*` `do` `doiter` `labels` `impl` `pprint-logical-block`, префікси цитування тощо).
- `src/test/symbols.test.ts` — вміст структури та виявлення посилань на типи в запасному варіанті.
  Кількість визначень має точно збігатися з незалежним підрахунком форм визначення на початку рядків.
  Граничні правила для посилань на типи навмисно узгоджені із запасним варіантом версії для Emacs (VS Code
  використовує lookbehind; Emacs виражає ту саму множину, споживаючи один попередній символ).
- Токени сервера, керовані розв'язанням (`crates/typelisp-front/src/check/semantic.rs`),
  перевіряються `cargo test --test lsp_semantic_test` і `scripts/lsp-semantic-smoke.py` (який керує
  справжнім процесом через stdio). Клієнт Emacs перевіряється
  `scripts/emacs-semantic-smoke.el` через справжнє підключення eglot.
- `src/test/manifest.test.ts` — `package.json` є єдиною частиною, яку компілятор не перевіряє, тому цей тест
  перевіряє, що оголошені команди та виклики `registerCommand` утворюють ту саму множину, на що
  посилаються прив'язки клавіш, що налаштування, які читає код, оголошені, і що зіставлювач проблем
  уміє розібрати те, що `typl` справді виводить.

### Виявлення розбіжностей у визначеннях редакторів

Таблиці ключових слів підтримуються двічі, у версії для Emacs і у версії для VS Code. Щоб визначення
редакторів не відставали, поки реалізація рухається вперед, на боці Rust є тест:

```sh
cargo test --test editor_keyword_sync_test
```

Він справді завантажує prelude, обходить реєстр і повідомляє про **імена, яких не знає котрийсь із
редакторів**. Спеціальні форми не мають представлення під час виконання, тому їх читають між
`// SPECIAL-FORM DISPATCH BEGIN` / `END` у `crates/typelisp-front/src/check/checker.rs` (не видаляйте ці
коментарі). Якщо тест падає, додайте названі імена до **обох** визначень редакторів.

Той самий тест порівнює також легенду семантичних токенів (`SEMANTIC_TOKEN_TYPES` у
`src/bin/lsp.rs` і таблиці в обох редакторах мають збігатися за назвами та порядком). Розбіжність не
спричиняє помилки під час виконання; вона лише міняє місцями кольори всіх токенів, тому її закріплено
механічно.

## Примітки

- typelisp переводить символи в нижній регістр під час читання, але підсвічування залежить від регістру,
  щоб можна було відрізнити імена типів, що починаються з великої літери.
- Відступи визначаються `INDENT_SPECS` у `src/indent.ts`. Це перенесення `typelisp-indent-specs` версії для
  Emacs з тими самими значеннями та правилами. Місця, де форма відрізняється за будовою від форми
  Emacs Lisp з тією самою назвою, перенесено як є: заголовок
  `(defun NAME (PARAMS) RETTYPE ...)` має три елементи, `if` має фіксовані три елементи з
  обов'язковою гілкою `else` тощо.
- Вміст `#| ... |#` перевирівнюється під час форматування. Це відповідає поведінці
  `indent-region` в Emacs.
